# 怎样确认游戏规则

先提出一个具体问题，例如“同一帧先加Buff还是先造成伤害”，不要一次研究整个技能。
找到数值后，还要确认单位、条件、版本和使用时机。

## 去哪里找

| 来源               | 适合回答的问题                               |
| ------------------ | -------------------------------------------- |
| TableCfg           | 成长、装备属性、技能展示关系、图标与文本键   |
| SkillData          | 动作顺序、条件、调度帧、子技能和输入映射     |
| BuffData           | 持续时间、叠层、属性修改、事件监听和结束动作 |
| VFS与Unity资源     | 投射物、能力实体、动画及未公开的配置         |
| IL2CPP代码与内存   | 通用执行器、调用顺序、资源写入及实际对象关系 |
| 游戏面板与逐帧实测 | 最终可见结果与输入效果                       |
| combat-spec        | 已写成规格和测试的研究结论                   |

旧版Endaxis、社区资料和AI总结用于提出假设或核对体验，不能直接当游戏规则。
同版本直接运行证据通常强于间接解释，但每份证据都有观察范围：一次余额读数不能证明初值，
一段代码没有写字段不能证明字段为零，静态方法也可能被IFix热更新替换。

## 如何形成结论

1. 固定游戏或数据版本，查原始配置。
2. 必要时查资源对象、方法和调用链，区分文件偏移与运行时地址。
3. 静态材料不能回答顺序或状态变化时，再做探针或游戏实验。已有转储先离线分析。
4. 记录确定的结论、推断和未知部分。说明检查了什么，也说明没有检查什么。
5. 将重要顺序写成combat-spec测试，再决定Endaxis需要怎样实现。
6. 修改转换器和运行时，使用真实配置或时间轴验证结果。

简单静态字段不必都做运行时采集。游戏实验应固定等级、潜能、技能等级和装备，避免多个条件一起变化。
采集和读取方式见 [本地环境说明](local-environment.md)，不要求用户手动完成已经授权的启动操作。

## 每份证据应写什么

- 问题与结论；结论是已确认、推断还是未知。
- 数据版本、原始ID、资源逻辑路径、文件哈希和工具提交。
- 具体字段、代码范围、实验条件或可重复的操作。
- 尚未确认的分支、热更新状态或版本对应关系。
- Endaxis采用的规则；若省略了原生行为，说明为什么不影响当前模拟。

机器绝对路径、账号信息和转储位置只写 `.local/`。
不要把新TableCfg和旧转储直接混用；先核对版本和相关代码范围，再决定哪些结论需要重测。

## 从证据到生成数据

转换器必须报告未知类型、字段或动作，不能填零或读取旧生成物补缺。
人工配置应独立、明确，不能藏在输出函数中。不完整预览不能作为完整模拟数据发布。
资源取得完整、动作解析完整、实际行为可执行是不同的检查，不能互相替代。

combat-spec记录原生行为；Endaxis实现排轴需要的部分。两者范围不同，但简化必须有依据。

## 人工补充与正式输出

少量有证据、但原始数据无法唯一确定的内容可以放在独立配置中，必须写明原因、来源和适用版本，
并进入生成报告。这不是自由填写规则的许可；项目兼容常量也不能称为已确认的原生字段。

正式定义只保留执行或查询需要的身份和数据。方法地址、探针结果和解释过程留在证据中，
不能把尚未解释的ID包装成可执行行为。每项生成能力要覆盖未知输入失败、代表样本和实际执行；
全量审计与真实样本对照根据改动范围执行，不能只看输出文件能否通过类型检查。
