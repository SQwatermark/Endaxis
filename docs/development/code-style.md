# 代码规范

本文约束手写源码、转换器和资源导出工具。具体运行语义见架构文档，检查命令见[开发指南](README.md)。

## 先保证正确，再决定是否抽象

**错误抽象不如有依据、边界清楚的特例。正确表达原生行为，优先于代码复用、统一配置和减少分支。**

不能因为两个动作、Buff 或界面看起来相似，就认定它们遵循同一规则。抽象前要核对状态来源、触发顺序、
时间域、输入边界和结束条件；成功后的提示不能代替成功前的可输入窗口。

证据只足以支持某个对象时，允许保留明确命名的专属实现。注明适用范围、证据和未知项，通过显式入口接入，
并保留该对象的回归测试。不要为了消灭特例而虚构通用字段、放宽验证或修改原有行为。

## 用修改范围检验架构

**新增或修改功能时，如果牵涉的代码面超出预期，必须先审视职责和依赖设计，再继续扩展。**

- 动手前明确预期涉及的模块、输入输出和状态归属；小改动可简述，不要求另建方案文档。
- 同一种信息需要在多个模块反复补字段、补转发、补恢复或补导出，或每新增一个同类消费者都要
  修改公共机制时，应暂停机械接线，检查是否缺少统一入口、职责错位、公式重复或依赖方向不合理。
- 区分首次建立公共能力的必要贯通与每次扩展都会重复付出的成本。需要跨层修改时说明各层为什么
  必须改变，以及下一个同类功能能否通过已有入口接入；不能只用“全链路需要”解释修改范围。
- 先收束已经确认的结构问题，再继续消费者接入；测试通过不能代替架构判断，也不能靠增加枚举样本
  掩盖结构问题。将可执行的边界约束落实为类型、统一接口或针对行为的回归检查。
- 不设文件数量门槛，不为减少文件数合并无关职责，也不为尚未出现的需求搭建通用框架。
- 实现困难且需要深入改动数据定义或计算流程时，必须评估收益并做功能取舍。贡献分析等解释功能
  优先复用已有事实；收益不足的路径保留明确的未归因状态，不为覆盖率扭曲模拟内核或猜造比例。

验收说明应交代实际修改范围与预期的差异、原因及处理结果。规范不要求额外审批或停下等待确认。

## 禁止把专属规则伪装成通用规则

通用编译、战斗运行时、结果投影、编辑器和资源导出流程不得隐含对象特例。
已有公共能力能准确表达时，规则归对应定义；确有独立原生行为时，使用边界清楚的专属实现，不能混进公共算法。

以下写法都禁止：

- 在公共算法中用 `slug`、角色 ID、专属 Buff ID、技能 ID、装备 ID、显示名称或字符串前缀暗中切换规则。
- 把分支改成通用文件里的白名单、映射表、集合、正则或固定哈希。换一种写法不会改变规则归属。
- 在通用组件里直接写某个干员的颜色阈值、图标路径、计数布局和命中高亮条件。
- 为了让一个样本通过，补默认伤害、放宽校验、跳过动作，或读取旧生成文件填补证据。
- 为绕过这条规定，把同一份特例表搬到 `utils`、`constants` 或一个名叫 `config` 的通用代码文件。

修改现有代码时，先确认是在搬移规则归属，还是在改变规则本身。只有前者能在行为保持不变的前提下直接整理；
后者必须先检查原生证据，不能借“重构”跳过审查。

## 规则应该放在哪里

| 内容                                   | 归属                                                     |
| -------------------------------------- | -------------------------------------------------------- |
| 伤害、Buff、条件、触发、资源与动作顺序 | 从原始数据生成的对象定义，使用公共动作和条件表达         |
| 公共动作尚不能表达的行为               | 证据不足以抽象时保留专属实现；确认公共语义后再提取能力   |
| 干员专属名称                           | 对应干员配置与生成定义；通用 UI 只读取元数据             |
| 对象特有的输入窗口、成功判定或特殊提示 | 先核对原生证据，不能仅凭某个 Buff 或界面现象新增通用配置 |
| 头像选择、专属图标别名、本地化重复条目 | 对应对象的资源配置；导出器执行同一套读取规则             |
| 不能用现有通用图形表达的专属 HUD       | `src/ui/operators/` 下的独立外观组件，通过显式注册表装配 |
| 公共元素反应、系统 Buff 和原生枚举     | 有来源依据的系统定义或协议适配层                         |

优先从原始字段和动作结构推导行为。只有产品侧的选择或源数据无法表达的展示信息，才增加对象配置。
配置中的引用必须校验；重新生成后不能丢失。展示元数据不得改变模拟结果。
当前干员产品配置在 `tools/game-data-compiler/config/operators.json`；武器、装备和套装的特殊资源别名在
`tools/game-data-compiler/config/equipmentAssets.json` 的对应对象项中。共享资源若声明不同来源，导出必须报冲突。

专属外观组件只接收数值、进度和状态，不重新计算伤害、Buff 寿命或触发条件。
外观注册表可以连接外观身份与组件；通用容器只负责选择、缩放和传参，不能继续包含专属绘制分支。

## 如何区分合理分派与身份特例

按 `dealDamage`、`applyBuff` 等公共动作种类分派是正常的。按真实原生组件类型解码，也属于来源适配：
必须读取和校验该组件的字段；若对象确有不同实现，应明确隔离，不能暗中改变同一公共操作的含义。

一个原生类恰好以干员命名，不代表需要改掉协议名称。需要检查的是代码是否实现该类本身的语义，
还是凭对象名称猜规则。公共状态标签、系统 Buff 和装备类别也不能只因名字固定就删掉。

显式标为测试、回归样本或交互演示的数据可以指定角色和装备，但不得参与生产规则选择。
保留样本时要检查实际调用入口，不能仅靠把文件命名为 `fixture` 来获得例外。

## 运行时数据与逻辑分离

新增及正在迁移的可恢复运行时遵守以下规则，完整边界见[战斗运行时切面](../architecture/runtime-checkpoints.md)：

- 可变状态使用独立的数据结构，不能包含方法、业务回调、类实例或闭包。处理程序通过稳定编号引用。
- 算法不持有当前状态。只在受控步进内取得本次状态并同步执行；开局初始化也属于受控执行阶段。
- 不把步进取得的数据引用留在成员、模块变量、计时器或跨步进回调中。需要继续执行的动作保存为数据。
- 观察层只能取得独立副本或不可变结果。恢复先准备完整目标，再整体替换，不执行结束、注销或初始化动作。
- 已有调用口逐步迁移时，可以连接尚未迁移的宿主，但必须复用同一算法并写清缺口，不能公开残缺的整场快照。
- 不为防止内部代码违规而给每次读写套通用 Proxy；状态所有权与调用边界要在代码结构中清楚表达。

## 修改时怎样验证

正式发布前可以直接调整数据格式、内部接口和生成结构，不为开发中的旧版本增加兼容层或迁移包袱。
这不免除原生语义和当前功能的验证；正式发布后再根据已发布格式明确兼容范围。

- 已有原生证据支持公共语义后，再用另一组对象 ID 验证身份无关性。换名测试本身不能证明可以抽象。
- 验证缺失配置、错误引用和不满足条件的情况，不得把未知情况默认为成功。
- 元数据与结果绑定时使用本次发布的定义快照，避免旧模拟读取新草稿的规则。
- 资源配置迁移要比较输出路径和源文件选择；行为转换改动要比较生成结果并跑真实场景。
- UI 拆分检查原有数值、模式、布局和缩放，不用固定源码文本代替行为测试。

## 禁止手工编辑生成产物

**带有生成声明或由生成流程维护的文件，禁止直接手改。** 干员产物统一使用 `.generated.ts` 后缀，
例如 `src/data/operators/rossi.generated.ts`；是否属于生成产物也要结合文件声明和生成流程判断。

必须先修改原始配置、来源适配或生成器，再通过正式生成入口更新产物。随后检查生成差异和相关回归。
不能用“先手补，之后再比对一致”替代正式生成，也不能为减少输出差异而补改生成结果。
生成受阻时应修复阻塞并重跑，不得跳过生成步骤交付。

手写文件通过 Codex 的 `apply_patch` 接口修改，方便查看差异；生成产物由现有生成器写入。
大检查串行执行，保留已有未提交工作。
