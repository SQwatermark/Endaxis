## 开始工作

在实际工作区检查 `git status --short --branch`、`git log -5 --oneline`、
`git worktree list` 和 `git remote -v`。保留已有修改，不按旧日志猜测机器或分支。
拉取前检查工作区和跟踪分支，只在可以快进时使用 `git pull --ff-only`。

依赖和脚本以根 `package.json`、锁文件及工具README为准。
运行 `npm run dev` 后读取实际服务地址，不要假定端口与历史记录一致。

## 修改和验证

修改前阅读[代码规范](code-style.md)。错误抽象不如有依据的特例，先保证原生行为正确。
禁止在公共算法中暗藏对象规则；能用定义准确表达的归定义，确有独立行为的保留边界清楚的专属实现。

- Codex通过 `apply_patch` 修改文件，方便用户查看差异。命令行用于读取、测试和Git操作。
- 类型清理保留可选参数、undefined、只读约束和联合类型之间的关系，不为减少工具类型而复制定义。
- 动态输入在明确的入口校验，不用双重断言或any掩盖类型错误。
- 测试围绕可能出错的行为。生命周期要检查执行顺序，绑定要检查连续更新和真实属性路径。
- 大检查串行运行。Vitest可用 `--maxWorkers=1`；不要同时启动多份类型检查或加载整个内存转储。
- 根据改动选择检查范围。部分通过不能写成全量通过；环境失败也要记录。

```powershell
npm run type-check
npm run type-check:game-data
npx vitest run <相关测试文件> --maxWorkers=1
git diff --check
```

格式化只针对修改文件。提交前检查暂存内容，避免带入缓存、原始游戏数据、私有路径和IDE文件。

## 游戏数据

如何判断证据和记录结论，见 [怎样确认游戏规则](evidence.md)。
先核对来源版本和证据，再改转换器。先生成候选、比较差异，再通过正式入口生成并检查一致性。
禁止直接手改生成产物；干员 TS 文件统一使用 `.generated.ts` 后缀，由转换器维护。
必须修改源配置或生成器，再通过正式入口生成；手改后比对一致不能替代这一步。
转换器测试通过不等于所有干员已经重生成。
真实时间轴对照必须保留原输入，不能修改原轴来消除差异。
具体命令只维护在 [转换器README](../../tools/game-data-compiler/README.md)。

## 写文档

直接说明做什么、为什么、在哪里找。必要的代码名配上用途解释。
架构变化更新架构页；任务进展替换当前交接；机器变化更新 `.local/`。
删除旧文档前核对独有内容和引用链接，不为了减少文件数量丢失证据。

## 如何判断工作完成

先保证已确认行为准确，再保证代码清楚，最后根据测量优化性能。
不能为了抽象统一抹平真实差异，也不能因某个类型或文件存在就称功能已接入。

新增能力需要说明输入、输出和状态归谁管理；定义、转换、执行与必要的显示必须形成实际调用。
不支持的情况明确报错，错误保留稳定代码和定位路径，界面负责翻译。
不要用空回调、默认倍率或静默跳过伪装支持。

按问题选择验证：公式测边界，运行时测顺序与结果，应用入口用真实场景，复杂界面做交互验证。
测试应检查行为，而不是要求源码文本固定。涉及稳定身份或存档变化时，另查重开项目和撤销。
重要注释解释用途、状态归属和清理时机，不只是把字段名翻译一遍。
