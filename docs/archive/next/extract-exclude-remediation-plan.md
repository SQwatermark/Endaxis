## 为什么需要整改

这里的问题不只是语法冗长：

1. **实现范围冒充领域类型。** 被动事件限制为两个，Buff 转换输出又抄一份事件白名单，
   武器再筛一份语义事件。新增事件需要到处补类型，不能由公共协议自然贯通。
2. **从“不是哪些东西”反推“是什么”。** Exclude 会自动接纳未来新成员；如果剩余类型用于
   路由、目标、公式或装配所有权，新增成员可能未经审核进入错误路径。
3. **缺少权威成员定义。** 多处从同一个大联合筛出同一个成员，再取它的 parameters 或字段。
   这通常不是新的业务类型，而是定义层缺少稳定可引用的成员身份。
4. **筛选可能静默变成 never。** Extract 的过滤条件拼错或上游改名不一定在筛选处报错；
   Exclude 的排除项拼错也可能什么都没排掉。类型检查“绿了”不等于边界表达正确。
5. **工具类型与 as 叠加会掩盖结构缺失。** 筛选不是运行时检查，断言更不是构造器验证。

但不做全面禁用：泛型键过滤、真正的局部联合收窄、类型测试有合理用途。
目标是消除重复的领域定义与隐含边界，不是把 Extract 改名成另一个万能泛型。

## 已确认的重点问题

### P0：事件链的筛选表达了宿主实现进度（A，15 处）

- `operators.ts` 的 abilityEventResponses 只允许出生/结束；UpgradeEvent 又筛 CombatEventTrigger。
- `buffLifecycleSequenceRuntime.ts` 使用互补的 Extract/Exclude 将事件分到 Ability 与 semantic。
  `combatRuntimeAssembly.ts` 又重复列举 semantic 事件成员。
- `buffProjectionTypes.ts` 复制长事件名单，甚至重复列出 skillEnd；这份名单不是优化 IR 不变量。
- `domains/weapon/runtimeDefinition.ts` 单列语义事件支持范围并限制筛选字段。
- 本机刚抽出的 `abilityEventPayload.ts` 也使用 Exclude 维护负载转换能力范围，纳入同样整改，
  不因是刚写的代码而保留例外。
- `healthDamage.ts` 的 source/target 事件分类可能有真实原生方向依据，不能和宿主限制一并删；
  将方向归属回公共发布元数据，逐项核对。

目标：统一事件身份和载荷，发布/订阅/条件读取同一对象；宿主仅绑定生命期、所有者和黑板。
原生广播、内部同步钩子、战斗事实记录需分类，不能用一张随意宽化的联合强行混合。
能力不足由明确的转换/运行时诊断报告，不通过各层不同的类型白名单隐藏。
与 [事件响应架构](event-response-architecture.md) 合并执行，不另建第二套事件整改项目。

### P0/P1：反向分类名单已经不一致（B，3 处）

- `combatProgram.ts` 通过排除 10 类节点定义 ResolvedCombatOperationStep。
- `definitionHelpers.ts` 只排除 7 类来定义 ImmediateStepKind。
  scheduleProjectileFinishCallback 没被后者排除，而步骤协议要求它携带 body；step 构造器只
  构造 kind/parameters/key，再断言为筛出的完整节点。这是需要优先封住的类型安全缺口，
  不等于当前生成数据已实际生成坏节点。
- `compileScenarioRuntimeAssembly.ts` 排除 6 个键后，把其他所有装配字段认定为环境依赖；
  将来新增一个场景字段，会自动落到环境一侧，所有权不是显式决策。

目标：动作类别（操作叶子/结构节点/控制转移等）和构造器所需字段有同一份权威描述；
即时构造器可接受集合与运行执行器集合不必相等，但各自含义必须明确且完整覆盖受检。
新增 kind 必须触发分类与构造测试，不允许依赖补排除名单。
装配环境与场景参数正向定义职责，再组合成总装配类型，不由总类型减若干键倒推环境。

### P1：转换器将输出子集当成 IR（C，20 处，另含 A 中事件项）

- `formalBuildDefinition.ts` 从 EquipmentModifierDefinition 裁出构筑公共修正，再限制 output、
  comboSkill 等值。重点复核它为何仍以 Equipment 为根，而非真正公共 Build 修正定义。
- `buffProjectionTypes.ts` 对伤害/治疗处理器、失衡条件、时钟及生命周期字段再次裁剪。
- `combatActionProjectionTypes.ts` 对伤害类型、时间膨胀曲线、属性来源等限定子集。

每项先判断：

1. 若只是“当前生成器能输出哪些合法正式数据”，复用完整正式成员，支持范围在转换分支与诊断中维护。
2. 若编译阶段真的保证了不同表示，例如常量已解析、跳转已绑定、黑板值尚未物化，则允许明确 IR；
   必须写清输入、输出、建立不变量的 pass、消费者、为何不能直接使用正式类型。
3. 原生/场景中确实不可能的值需要证据，不因为当前样本没出现而从数据契约删除。

不将全部 IR 扁平化，也不为每个原生字段造独立文件；按实际领域和编译阶段适量分组。

### P1：目标、伤害与操作排除（D，10 处）

- HealTarget/contextTarget 在契约与编译结果各排除一次。
- BuffApplicationTarget 的多目标、当前能力实体分别被不同执行入口排除。
- `combatActionLeafProjection.ts` 在动态 Map 查询结果上使用 `as Exclude<...>`；检查条件
  与断言名单并非同一表达式，必须追踪上游集合建立，改成可验证的正向目标解析结果。
- `ResistibleDamageType` 排除 true/lifeDrain；需按公式证据定义可受抗性影响的类别，
  不能保证未来 DamageType 自动适用抗性。
- 养成操作排除 none 有实际 requireOperation 守卫，属于有验证的收窄候选，不应先判为 bug；
  三处需统一引用同一个“有效操作”定义，并保留对 None 的显式拒绝。

目标：权威目标类型描述基数/实体类别和上下文要求，特定步骤引用正确成员；运行时做真实检查，
而不是把不支持的目标用断言排掉。保持单敌人场景简化与原生事实分层。

### P2：重复筛出成员，补齐可直接引用的定义（E，145 处；F，36 处）

E 包括运行时、编辑器和定义辅助函数反复筛步骤、条件、modifier、HUD、目标引用。
F 包括原始 NativeActionNodeSource.body 与 NativeConditionSource 的控制结构、家族收窄。

- 参数已有权威表时直接索引，例如 CombatStepParameters['applyBuff']；不要先筛完整步骤再取参数。
- 完整步骤必须保留 body/whenTrue/options 等结构字段，不能误用参数表代替整个节点。
- 已有 ResolvedCombatStepForKind 应评估作为公共受约束成员入口，不在每个执行器重新筛一次。
- 明确原生成员已命名时直接引用；否则在原始类型所属模块建立一次成员映射，再由映射组成联合。
- 某一个函数确实只处理一种判别成员，且不会越层定义业务范围，可以保留局部收窄；
  但相同筛选反复出现时应优先归并。不要产生 145 个仅包一层 Extract 的新别名。
- 所有 UI 组件继续服从契约驱动 Inspector 架构，不能借类型整改再手写一套字段清单。

### P1/P3：UI 分类和泛型工具区别处理（G，12 处）

- 专属 HUD 的 numeric 外观使用 Exclude<..., 'liinoMusic'>，已经自动包含 typhoeaArrows，
  后者又有独立 buffCounters 分支。类型允许的重叠是事实；是否有合法 numeric 变体需查
  prefab/生成数据，不能直接宣称该变体非法。改为有依据的 appearance → 配置对应关系。
- 敌人可编辑字段、曲线数值字段使用排除非数值键推导数值字段，新增其他类型字段时有误纳风险；
  优先复用属性描述的字段类别或明确参数接口。
- GameTextFamily 与颜色来源的子集要正向描述各路径能力，避免新增 family 被误纳。
- 两处 Extract<keyof T, string> 是泛型字符串键约束候选，保留通常比另造领域类型合理。
- Parse/OpenProjectResult 的失败分支可以引用共同的命名结果成员，或保留局部收窄；
  不复制错误结构，不为清零数量过度设计。

### 测试跟随所有阶段（T，40 处）

区分“构造一个合法联合成员”的测试与“验证编译类型边界”的测试。
前者引用权威成员；后者允许工具类型，但必须证明筛选非 never，并有正、负样例。
专门检查 as/assertion 是否绕过了缺子节点、非法目标、未实现事件等本来要验证的限制。
类型测试不能只证明一个裁剪后的中间类型符合它自己，必须包含真实契约输入与真实编译输出。

## 后续维护：保留结构与行为验证，不建立枚举式门禁

1. 新增领域名单或IR边界时审查生产者与消费者，不以语法名单或许可表代替设计判断。
2. 既有审计结论作为设计背景保留，不维护逐文件、符号和表达式的自动允许清单。
3. 通过类型穷尽与负例检查“上游新增成员”：动作 kind、事件、目标、装配字段新增时必须审查归属，
   不允许自动通过补集进入默认处理器；类型检查仍需结合真实转换与运行回归。
4. 支持状态用明确的 supported/scenario-omitted/blocked 诊断说明；类型可表示不等于功能已实现。
5. 每个清单编号最终标明：删除重复 / 改为权威成员 / 保留且有依据 / 随旧模块删除。
   不能仅把表达式搬到别的文件就把该项关闭。

## 验证与证据边界

- 契约、转换器和应用类型检查按项目串行；需运行 Inspector 类型准备/架构测试，避免泛型结构
  改造使字段描述失效。类型检查成功不是运行时行为证明。
- 事件改造覆盖同步修改可见性、同级注册顺序、停用/注销、once/重入、来源遮蔽及实例隔离。
- 对生成器做全量 31 干员公共闭包与候选生成核对，检查武器/装备公共路径，不能只跑静态 TS。
- 保留既有真实私有三轴及公开轴回执/资源/伤害基线；纯类型整改应不变，真实缺陷造成变化需证据解释。
- 不改原始轴凑通过，不手改生成数据，不因 Exclude 有风险便放开全部枚举，不把未取证机制默认支持。
- 本轮审计不需要修改 combat-spec 原生规则；实施时遇到缺失证据再同步取证，不凭类型相似推断游戏。
