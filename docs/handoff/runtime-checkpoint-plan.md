# 战斗切面任务与验收计划

更新日期：2026-09-15。本文是当前任务清单，只保留仍有用的结论、下一步和验收标准。当前结果见
[当前交接](current-context.md)，最终设计见[战斗运行时切面](../architecture/runtime-checkpoints.md)。

## 总目标

提供一套完整、可恢复、可分支的战斗数据切面，用于编辑器试算和旧轴转换。共同历史只推进一次，
候选分支可以增加不同的后续输入，失败或放弃后能立即回到同一保存点。

切面只知道已经提交和已经发生的事情。尚未提交的技能、连续组后续计划、切人、人工标记和单块种子
留在外部输入排程器中。

## 不可破坏的边界

1. 数据和逻辑分开；切面中不得保存函数、闭包、类实例或事件处理器。
2. 保存和恢复不执行游戏规则，不触发事件、不扣资源、不消费随机数。
3. 公开保存点位于完整帧边界；同帧阶段与原生顺序保持一致。
4. 切面只有分支和回退，不合并分支。
5. 恢复先完整预检和装配，成功后一次替换；失败不改变原分支。
6. 实例身份、订阅顺序、随机进度和 float32 运算顺序必须保留。
7. 不用从头重算掩盖恢复缺口，不吞掉合法输入触发的异常。
8. 固定程序可以只读共享，兄弟分支的可变数据不能共享。
9. 发布前允许修改内部接口，不为已废弃的实验入口增加兼容层。
10. 重型检查串行、单 worker 执行；不同时运行全量测试、类型检查和内存快照。

## T7：整理切面数据基础模块

### 目标

当前许多纯数据结构各占一个文件，难以看出完整层次。T7 要把切面数据形成一个明确的基础模块，使用
少数文件表达数据树，同时保留各业务运行模块的独立性。

### 调查步骤

1. 列出所有进入 `CombatStateGraph` 的类型、创建函数、复制方式、所有者和导入方向；
2. 区分纯数据定义、固定程序、运行对象、恢复装配和临时执行上下文；
3. 建立当前 import 图，找出循环依赖风险和只被一个类型引用的小文件；
4. 统计整理前的状态文件数量、总行数和跨目录导入数，作为可量化基线。

### 目标结构

先根据依赖图验证，再在以下层次附近收束，不预先强制具体文件名：

- 战斗根、共享数据和输入数据；
- 环境、敌人和干员数据；
- 技能、动作、Buff 与事件宿主数据；
- 能力实体、投射物和其他动态实例数据。

预计形成约 4–6 个纯数据文件和一个清楚的公开入口。若某组类型合并后产生循环依赖或让文件难以阅读，
可以保留一个独立文件；目标是看清层次，不是追求最少文件数。

### 边界

- 只移动纯数据类型、简单创建函数和不含业务规则的复制辅助；
- 不把运行类、动作执行器、恢复逻辑或游戏规则集中到基础模块；
- 不建立导出一切的巨大 barrel，避免隐藏依赖和循环；
- 不改变存档协议、运行时字段、Map/Set 语义或 `structuredClone` 结果；
- 不在同一批修改中顺便改游戏规则或优化内存表示。

### 实现结果

- 新建 `src/core/combat/state`，使用五个文件表达环境、动作、能力、动态实例和完整战斗根；
- 删除 39 个只有单一或少量状态定义的 `runtime/*State.ts` 文件；
- 把原先夹在时钟、编号器、连携、目标上下文和标记运行模块里的状态类型也移入基础模块；
- 资源和生命初始快照校验、SkillAffix 状态变更、预施法监听变更仍留在运行层；
- 运行目录不再定义或转发切面 `*State` 类型，调用方直接导入所需数据层。

### 完成记录

- 当时的类型检查结果受增量缓存影响，不能作为干净检查证据；2026-09-15 笔记本禁用缓存复现并修复
  91 条诊断后完整检查通过，检查命令已固定禁用增量缓存；
- 切面与正式应用广域回归 180 个文件、1835 项通过；
- 旧轴转换 7 个文件、55 项通过，1 项按原设置跳过；
- 真实转换轴在期望和固定种子模式下，完整状态、结果和有序回执与不分支执行一致；
- 真实轴额外发现并修复了自然结束的 `finishByAction` Buff 被恢复预检误判为缺失的问题。

### 质量与验收

- `CombatStateGraph` 从一个入口即可读懂完整所有权树；
- 状态专用生产文件数量明显减少，剩余独立文件都有清楚理由；
- TypeScript 依赖无新增循环，运行模块只导入自己需要的层；
- 整理前后真实轴的完整状态、结果和有序回执一致；
- 180 文件广域回归与旧轴转换回归通过；
- 文档中的数据树与实际类型一一对应。

## T8：分析并降低总内存

### 目标

当前长轴审计的进程 RSS 峰值约 574–585 MiB，可观察 JavaScript 堆峰值约 216–289 MiB。T8 要先说明
内存由什么组成，再降低真实转换和编辑器试算的峰值；不能只做 GC 调参或提高堆上限。

### 测量阶段

在同一进程、同一真实轴上记录以下边界：

1. Node 启动后；
2. Vite 和 TypeScript 模块加载后；
3. 游戏数据仓库加载后；
4. 场景编译后；
5. 战斗装配完成后；
6. 推进到保存点后；
7. 保存状态图与回执视图后；
8. 候选分支推进后；
9. 结果投影后；
10. 释放候选、保存点和结果并强制 GC 后。

每个边界至少记录：

- `heapUsed`、`heapTotal`、`external`、`arrayBuffers` 和 RSS；
- V8 各 heap space 大小；
- `CombatStateGraph` 各顶层子树的可序列化大小；
- 固定程序目录、回执历史、`receiptEntries` 数组和最终投影的数量与近似大小；
- 同一对象是否被编译结果、活动装配、保存点和发布结果重复持有。

必要时生成单次 heap snapshot 查 retained path。快照一次只分析一个阶段，完成后删除本机大文件，不把
快照提交进仓库。

### 优先检查的假设

- Vite SSR 与 TypeScript 转换缓存占据大量进程基线；
- 游戏数据仓库一次加载了转换不需要的全部定义；
- 编译结果与运行装配同时保留重复的大型动作程序或黑板数据；
- `receiptHistory` 已共享，但 `receiptEntries` 和多个投影又物化完整数组；
- 保存点完整克隆了当前候选并不需要的状态层；
- V8 为短时峰值扩张后保留 heap pages，使 RSS 不立即下降。

这些都只是待验证假设。没有分项数字前不据此改结构。

### 优化原则

1. 先删除重复持有和不必要物化，再考虑压缩数据表示；
2. 固定程序保持不可变共享，不用深拷贝换取表面隔离；
3. 结果消费者优先使用回执视图或增量查询，避免重复完整数组；
4. 只对确认的状态热点引入分块或写时复制；
5. 优化后必须保持完整状态、结果、回执和随机序列一致；
6. 同时报告绝对峰值、基线差值和释放后留存，不能只挑一个下降数字。

### 验收

- 给出可复现的分阶段内存表和主要 retained path；
- 至少解释 RSS 与 JavaScript 堆差额的主要来源；
- 对确认热点完成一批范围可控的优化；
- 长轴分支和完整旧轴转换的峰值有可重复下降，释放后无持续增长；
- 180 文件广域回归、真实轴结果对照和旧轴转换回归全部通过。

### 已完成的第一批优化

- 分阶段测量确认主要稳定增量来自编辑模拟入口连带加载的完整游戏数据，不是切面状态图或投影结果；
- 主线程把当前场景所需定义捕获成纯数据包，后台 Worker 恢复小型只读仓库；
- 数据包仅在首次请求、定义版本变化或引用集合变化时发送，拖动技能块不会反复组装；
- 真实轴完整仓库和小仓库的 5866 条回执及最终结果逐字节一致；
- Vite SSR 测量中 Worker 稳定堆约从 124.6 MiB 降至 53.1 MiB，模块数从 696 降至 278。

后续仍需测量实际浏览器主线程和 Worker 的生产环境堆组成，再决定是否拆分编辑器完整定义目录。
不能用 Vite SSR 的转换缓存数字冒充浏览器节省量。
