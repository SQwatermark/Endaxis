# 背景、目标与历史

## 1. Endaxis 是什么

Endaxis 是一个面向《明日方舟：终末地》的战斗时间轴编辑器。用户可以配置队伍中的干员、武器、装备和敌人，把技能放到时间轴上，观察技力、终结技能量、失衡、元素附着、伤害和其他战斗状态随时间的变化。

它的目标不只是画出一条好看的轴，而是让时间轴成为可计算、可诊断、可复现的战斗方案：

- 用户输入可编辑的构筑与操作序列；
- 系统计算角色面板和技能实际参数；
- 模拟器按明确顺序执行技能、资源、Buff、伤害和事件；
- 投影层把模拟回执转成折线、技能块、连接、警告和日志；
- 存档只保存用户意图，不把可重算结果当成事实持久化。

仓库的公开上游关系是：

- `SQwatermark/Endaxis`：当前工作仓库的主要远端；
- `Lieyuan621/Endaxis`：`SQwatermark/Endaxis` 的上游；
- 当前本地仓库同时配置了这些远端，用于研究、合并和贡献小模块。

## 2. 项目最初如何推进

早期工作从阅读 `analysis/database` 等 AI 总结文档开始，但很快发现这些文档准确性不足。此后将 AKEDatabase 及其数据源视为核心静态数据入口，并建立了“先验证、再修文档、最后写代码”的路线。

工作大致经历了以下阶段：

1. 梳理旧版 Endaxis 的战斗模型、面板计算和 UI。
2. 用游戏内面板截图验证角色、武器、装备、词条等级和精锻的数值规则。
3. 研究武器技能、连携窗口、技能变体、资源消耗和合法性诊断。
4. 将 AKEDB 的富文本、干员描述、武器和装备数据接入导出脚本。
5. 建立本地 VFS 浏览器，解决 AKEDB 不提供的原始资源、二进制配置、模型、动画、音频和 Shader 读取。
6. 用 IL2CPP 静态与运行时证据研究客户端真实战斗代码。
7. 建立 C# Combat Spec，把反编译结论写成可执行、可测试的行为规格。
8. 设计 Endaxis Next，在不破坏旧版 `/timeline` 的前提下重写核心架构。

这些阶段不是互相替代的。静态数据、运行时代码、C# 规格、生成器和 Next 各自负责不同层次的问题。

## 3. 为什么不能只继续修改旧版

旧版已经具备可用的时间轴编辑、干员/武器/装备配置和大量战斗逻辑，但长期迭代暴露了系统性问题：

- 项目存档混入派生字段、翻译后的名称、模拟结果或需要重算的对象，稳定身份和显示文本边界不清。
- 技能定义、实例、时间轴块和模拟对象之间语义重叠，部分字段类型没有完整声明。
- Action 执行顺序曾使用 `beforeDamage` / `afterDamage` 一类旁路标记，不如有序动作序列自然。
- 特殊干员机制容易散落在投影或合法性代码中，形成超大文件和重复条件解析。
- i18n 曾进入非 UI 层，甚至可能把本地化后的游戏名称写入存档。
- UI 状态、项目状态和运行时状态耦合，撤销重做曾因派生对象不稳定而出现问题。
- 同一事实可能由数据文件、旧配置、组件和模拟器各维护一份。
- 扩展活动机制、主题、多语言和新干员时，修改边界不清晰。

因此用户明确选择：在 `src/next` 建一个新模块，和旧版共享必要的数据文件，但不复用旧项目模型、旧模拟器、旧持久化结构或 UI 状态；完成后再切入口。

## 4. Next 的最终目标

最终希望获得一条从项目输入到结果展示都清晰可审计的流水线：

```text
用户存档
  -> 游戏目录定义解析
  -> 构筑与面板编译
  -> 技能编译与时间轴程序
  -> 确定性战斗运行时
  -> 结构化回执
  -> 折线、日志、警告和 UI
```

优先级由用户明确为：

1. 尽可能精准模拟、功能完备；
2. 尽可能代码清晰、易理解、易维护；
3. 在前两者不受损的前提下尽可能提高性能。

性能优化不得让模型复杂到难以验证。与游戏一致也不等于复制游戏内部命名；只有语义显而易见或确有必要时才沿用原生概念，否则使用 Endaxis 自己清晰稳定的领域名称。

## 5. 明确的产品范围

当前 Endaxis 假定：

- 主要模拟玩家主动攻击行为；
- 敌人通常有且只有一个；
- 技能由用户放上时间轴后会执行，合法性检查只显示警告，不阻止模拟；
- 暂不做投射物轨迹和范围命中判定，可先约定投射物在第 0 帧命中；
- 敌人的主动 AI、复杂选目标和中断行为优先级较低；
- 技能实例细节编辑暂缓，先贯通干员、武器、装备、敌人配置和时间轴编辑。

这些是编辑器产品边界，不代表游戏没有相关系统。C# Combat Spec 可以继续复刻游戏完整语义，而 Next 只接入对排轴有价值的部分。

## 6. UI 目标

新版 UI 要尽可能 1:1 保持旧版的视觉和交互，除非底层数据模型变化导致不可避免的差异。用户已明确要求：

- 干员、武器、装备选择槽和弹窗布局沿用旧版；
- 技能库点击、拖放、复制粘贴、框选、轨道选择等行为沿用旧版习惯；
- 顶部菜单、轨道头、资源折线、光标辅助线和技能块样式尽量一致；
- 快捷键必须有清晰作用域，弹窗和输入区域能拦截底层快捷键；
- 为多语言按需加载、界面主题切换和游戏文本翻译预留稳定边界；
- 不为了展示 Next 特性而自由设计一套新界面。

## 7. 什么叫“完成”

Next 不能因为目录里存在某个类型或组件就算完成。一个功能至少要闭环：

1. 有稳定领域定义；
2. 能从项目输入或游戏数据编译；
3. 运行时能执行并生成回执；
4. 投影能生成 UI 所需数据；
5. UI 能编辑或展示；
6. 有针对性测试和至少一个真实样本验证。

旧入口只有在关键功能、存档迁移和模拟对照达到验收条件后才应切换。此前 `/timeline` 仍是稳定旧入口，`/next/timeline` 是并行开发入口。
