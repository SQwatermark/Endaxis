# 战斗系统研究结论

本文是跨文档总览，只描述当前已经有较强证据支持的架构和重要边界。精确字段、RVA 和样本请继续查阅 `vfs-index-browser/docs/research`、`combat-spec/docs` 和 Endaxis `docs/research`。

## 1. 战斗系统的总体形状

终末地战斗不是把一个技能直接换算成一串伤害数字。客户端大致包含以下层次：

```text
角色构筑与 Deck
  -> 可用技能 / CardSkill / 技能替换
  -> 释放候选与条件检查
  -> Skill 实例与 Blackboard
  -> 技能时间轴和调度动作
  -> SequenceAction 中的有序子动作
  -> Buff、资源、伤害、附着、实体、事件
  -> AbilitySystem / BuffSystem / DamageSystem
  -> 属性、敌人状态和战斗日志发生变化
```

配置负责声明大量行为图，原生 C# 代码负责解释 Action、管理生命周期、计算属性和分发事件。少数规则可能在通用代码或 IFix 热更新中硬编码，不能仅凭某个干员 SkillData 判断全部语义。

## 2. 构筑与面板

游戏建立角色 Deck 时会综合：

- 干员基础定义；
- 等级与突破关键帧；
- 四维属性加点和天赋阵列；
- 天赋与潜能；
- 武器等级、词条等级、技能和潜能；
- 装备属性、精锻和三件套；
- 可能的场景或活动修正。

力量、敏捷、智识、意志是输入属性，不需要用户再提供一个独立的“主属性/副属性数值”；干员定义指定哪一种四维是主属性、哪一种是副属性，运行时按原生公式派生生命、攻击等面板。

已在游戏截图中验证过多个完整面板样本。用户曾确认一个庄方宜样本的预测值完全正确：攻击 `7534`、生命 `5990`、防御 `140`、力量 `99`、敏捷 `99`、智识 `307`、意志 `887` 等。这证明现有数据链能够在已覆盖构筑下从干员、武器和装备推导面板，但不等于所有活动修正和新版本数据都已自动闭环。

武器词条的重要结论：

- 三星武器通常两个词条，四星以上通常三个；
- 社区“武器 1 潜”实际对应 UI 中无额外潜能的初始状态；严谨建模应为额外潜能 `0..5`；
- 初始词条处于 `+1`，每个额外潜能再 `+1`，基质最多贡献 `+3`，因此词条等级上限可达 `+9`；
- 基质按位置一一适配武器的基础、附加和技能词条，适配的词条生效；
- 对 Endaxis 用户而言，直接编辑最终词条等级比单独建模基质选择更简洁。

## 3. 技能定义与 SkillPatch

一个干员技能通常不是单个 SkillData：

- 展示表决定名称、图标、类型和技能组；
- 根 SkillData 引用多个子技能、投射物或 Buff；
- SkillPatch 根据等级、天赋、潜能、武器或形态修改黑板和引用；
- BuffData 可能在事件中再次触发技能或动作；
- `presentationVariants` 只负责显示名称/说明，不应被误认为独立战斗身份。

黑板值 Map 的价值是复现原生“定义引用参数，Patch 修改参数”的结构，并保留同一个值被多个动作引用的关系。它不应成为随意堆放常量的地方；若某个数值只被一个语义步骤使用且不会被 Patch，直接写在使用位置更清晰。

## 4. 技能释放和资源检查

恢复出的技能可用性检查主干大致为：

```text
owner
  -> cooldown
  -> cost
  -> tag
  -> state
```

技能开始会处理冷却次数预占，成本可能在 `startCdTime` 指定的帧实际扣除。当前重要未知边界仍包括：生产释放路径是否总是调用完整可用性门禁，以及延迟扣费时资源被别的行为抢先消耗后，真实客户端对失败的最终处理。

这也是为什么 C# Spec 中不能自行决定“检查时锁定资源”或“扣费失败取消技能”。有新证据时需同时更新 Spec 和 Next；Spec 要 1:1，Next 只需确保排轴可见行为一致。

Endaxis Next 的产品规则是：用户放置的技能仍执行，资源不足等问题作为诊断输出，不阻断模拟。这样用户可以看到错误轴的后果并修改，而不是技能块消失。

## 5. 时间与技能块长度

原始数据中存在多种时间：

- 调度动作的开始帧；
- 技能成本帧；
- AllowNextSkill 的 `startFrame`；
- 通用中断保护帧；
- 自然结束时间；
- 动画或投射物命中时间。

这些字段语义不同，不能统称 `durationFrame`。针对编辑器技能块，当前设计选择一个“对排轴有体感意义的可接续时间”，可按以下近似推导：

```text
min(
  最早通用中断帧,
  对排轴有效的 AllowNextSkillAction.startFrame
)
```

自然结束帧对玩家何时可以接下一个动作往往没有直接价值。`defaultInterruptibleAfterFrame` 控制打断门槛，而技能块显示长度应使用清晰的 Endaxis 自有名称，避免与原生字段混淆。

投射物当前在 Endaxis 单敌人模型中先按第 0 帧命中。5 米命中时间等估算只适合实验，不应在证据不足时写入正式 DSL。

## 6. TimelineAction、SequenceAction 与同帧顺序

`TimelineAction` 负责把行为安排到技能时间轴上的帧。到达目标帧后，`SequenceAction` 按配置数组顺序同步执行子动作。

因此同一逻辑帧不等于“没有顺序”。trace 需要同时记录：

- `Frame`：逻辑帧；
- `Sequence`：该帧内同步动作的先后序号。

这正是 Next 采用有序 `ActionSequence.steps` 的依据。Buff、伤害、资源和事件都是 step，不再用 `beforeDamage` / `afterDamage` 旁路字段表达顺序。

## 7. 一个 hit 内 Buff 与伤害的关系

`DamageAction` 是一种执行动作；“hit”是一次可显示、可连接的伤害发生实例，两者不是完全同义。一个命中上下文可能包含多个动作或处理器。

已确认的重要规则：

- 同级 Action 的先后由 `SequenceAction` 数组顺序决定；
- 若 `CreateBuffAction` 位于 `DamageAction` 前，伤害计算可以读取刚生效的属性修正；
- 若 Buff 位于伤害后，该次伤害不会倒过来享受它；
- DamageModifier 内部动作、附着/状态和同级显式动作是不同机制，不能混成一个统一的“先 Buff 后伤害”规则；
- 最终需按全干员具体 Action 图盘点哪些 hit 的 Buff/附着在出伤前执行。

旧版 Endaxis 相关配置已经做过对照，但仍应以生成审计和全量样本为准。

## 8. 伤害、失衡和元素

伤害 step 至少需要表达：

- 伤害元素，如物理、电磁（`pulse`）、灼热、自然、寒冷等；
- 等级倍率或其他计算输入；
- 可选失衡值；
- 伤害标签，如普通攻击、重击、战技等；
- 特殊计算方式，如处决/破韧攻击。

Endaxis Next 将失衡作为伤害 step 上的可选字段，因为游戏配置中它可以和同一次伤害处于同一个执行单元；只有执行时序确实不同才拆成两个 step。`dealDamage` 和 `applyElementalInfliction` 默认目标都是单一敌人，不要求每处重复配置 `target`。

玩家主动伤害已研究到包括倍率、定值、属性乘加、破韧攻击、攻击者/目标修正、抗性、防御、暴击和最终生命扣除的多阶段链路。格挡、护盾、转移、部分随机和敌人主动受击表现仍可能未完全闭环。

## 9. Buff 系统

Buff 不是单纯的属性加成对象。它可能包含：

- 初始和启用动作；
- 层数和持续时间；
- 周期触发；
- 属性修改器；
- DamageModifier；
- Ability、Buff 或 Global 事件监听器；
- 消耗、延长和结束动作；
- 标签及按标签查询。

Buff tag 的原生意义需要按使用点区分，当前研究重点包括：

- 作为分类或查询键；
- 用于 `CheckBuffStackByTag` 等条件聚合层数；
- 参与实体标签准入或技能条件；
- 影响生命周期或事件监听范围。

不能因为多个 Buff 共享一个 tag 就把它们当作同一个 Buff，也不能把所有 tag 直接暴露为 Next 业务概念。Next 应把已知语义映射成稳定状态/机制，无法解释的 tag 保留在审计中。

## 10. 事件系统

原生系统存在多层事件：AbilityEvent、BuffEvent、GlobalBuffEvent 等。Combat Spec 的生成脚本已从 IL2CPP 证据生成完整枚举清单，并验证枚举名称、值和版本。

事件监听器通常在 Buff 或技能生命周期中注册，按系统注册和事件分发顺序执行。需要注意：

- “同帧更新”不意味着所有系统并行；注册顺序和分发层级会形成先后；
- `treatAsSkillType` 只改变某些技能类型判断，不应自动让伪连携消费真实连携窗口；
- 监听者需要区分原始技能类型和“被视为某类型”，不能只在 `onActionStart` 做一次特殊判断；
- Next 应使用稳定语义事件，例如 `reactionApplied`，原生事件 ID 和 tag 放在证据文件中。

## 11. 连携技与窗口

游戏中连携窗口不是打开后都能随意释放：

- 窗口会排队；
- 先触发的窗口必须先释放或过期；
- 同时打开时，轨道序号最低的窗口优先；
- 多段连携的第 N 段应匹配对应的第 N 个窗口，不能串用；
- 技能仅“被视为连携”并不等于它依赖或消费连携窗口。

Endaxis 的合法性诊断已经围绕这些规则设计过 `ComboWindowSegment` 和前置条件检查。Next 需要在运行时回执和诊断层延续这些语义，而不是把每个干员写死在投影函数中。

## 12. 普攻链、重击、下落攻击和处决

- 普攻是有序技能组，拖到时间轴时展开为 A1、A2……；
- 重击通常与普攻最后一段或输入方式相关，不能凭空释放；
- 原生通过技能标签/技能类型和事件链识别重击，而不是根据 UI 名称猜测；
- 下落攻击和处决在 Next DSL 中定义为独立技能组；
- 处决可包含伤害、失衡、技力回复和敌人独立处决倍率；
- 不同干员的下落攻击和处决参数可能不同，不能仅按职业或敌人 tier 推导。

## 13. 形态与技能互斥

双形态或强化状态不应通过复制整套干员身份实现。需要区分：

- 稳定技能组身份；
- 条件选择的战斗分支；
- 仅用于 UI 的展示变体；
- 终结技持续状态、Blackboard 或语义状态。

例如：

- 莱万汀强化普攻、强化战技、强化连携只在终结技持续期间释放；普通普攻和普通战技在该期间应提示改用强化版本；
- 诀的双形态来自 Deck 属性/状态选择，终结技强化期间可能禁止回能，并需满足特定准备状态才能再次释放终结技；
- 庄方宜包含强化技能和特殊剑实体机制，其干员专属概念留在干员定义或 mechanic 中，不塞进通用 DSL helper。

## 14. 已知尚未闭环的高价值问题

- 延迟扣费失败在生产释放路径中的真实状态处理；
- 所有系统同帧事件注册/更新顺序的完整来源；
- 部分 IFix 热更方法和新版本行为；
- 全干员复杂 Aura、实体数量条件、条件投射物和嵌套技能引用；
- 全量 Buff tag 的语义分类；
- 部分格挡、护盾、伤害转移和随机流；
- 投射物真实命中时间和距离模型；
- 新干员缺失根 SkillData 时的行为闭环。

这些未知项必须继续出现在审计和路线图里，不能因为 Next 已有一个相似接口就认为问题解决。
