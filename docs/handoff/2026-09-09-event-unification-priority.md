## 已观察到的问题与证据边界

- `packages/game-data-contract/src/operators.ts` 的被动 `abilityEventResponses` 将事件
  类型限制为 `Extract<AbilityEvent, 'abilityEntitySpawned' | 'abilityEntityFinished'>`，
  并内联定义了 event/priority/sequence 结构。
- `packages/game-data-contract/src/buffs.ts` 另外定义 `SkillBuffAbilityEventResponse`，

- 契约还已有 `listen` 等监听动作；需说明它与上述响应入口的真实语义分工，不能仅因
  来源动作名称或旧实现位置不同就各自维护事件解析、条件判断和执行分发。
- 前述被动两事件限制目前表达的是实现覆盖范围，尚无已列出的游戏证据证明被动天然

保留和复用它，明确真正重复的位置。此次仅记录优先级，不修改机制实现。

## 应建立的职责划分

1. **公共事件语义**：事件身份、payload、发生时机与顺序只保留权威定义。
2. **发布与分发**：同一事件使用公共发布/订阅机制；不同实体可以拥有各自事件中心，
   “统一”不是把所有实体事件塞进无归属的全局总线。
3. **监听宿主**：仅负责注册/注销时机、所有者身份、黑板、当前技能/来源上下文及实例
   状态。Buff 停用、被动卸载、技能结束等生命周期差异是合理差异，不应被抹平。
4. **条件与动作**：响应复用公共条件与步骤执行器，保持同步前置事件、优先级、重入、
   once 等状态的既有语义。不能为了统一形式改变原生执行顺序。
5. **特殊适配**：只有证据证明需要时才保留事件特有的 payload/上下文适配，并让不同
   监听宿主复用；不要让每个宿主都写一套按事件名分支的适配器。

不应仅把 `Extract<...>` 替换为 `AbilityEvent` 就宣布完成；那只会放宽类型，不能保证
事件真的可用。确实不支持的语义应明确校验报错，不静默丢弃或假装执行成功。
有原生依据的事件范围限制可以保留，但必须说明限制的是游戏语义，而非开发进度。

  的结构重复、能力范围与上下文需求。
- 转换器：原生事件动作解析、payload 映射、条件转换、优先级与序列转换；特别检查
  `buffRuntimeProjection.ts` 与 `domains/operator/passiveSkillDefinition.ts` 的异同。
- 编译/校验：`compileSkill.ts`、`compileOperatorUpgrades.ts`、对应定义校验器，
  避免一处允许、一处丢弃或另设一份不一致的事件白名单。
- 运行时：现有 Ability 事件中心、Buff 生命周期执行器、被动事件宿主、技能 listen，
  查明事件生产者到响应序列的每个环节，哪些共享、哪些重复、哪些差异有必要。
- 消费与编辑：公共定义的其他消费者是否另行列举事件、遗漏支持项或错误限制输入。
  本阶段只修与统一事件语义直接相关的问题。

## 执行顺序与验收标准

先形成“事件 → 原生来源 → 公共协议 → 转换 → 发布 → 监听宿主 → 执行动作”的映射，
列出共享点、重复点、未支持项和有证据的差异，再实施改造。

完成必须有以下证据：

- 事件新增或修正不再需要按 Buff/被动/技能逐个重复实现同一语义。
- 相同事件与相同响应在可比较的不同宿主上复用同一解析/分发/条件/执行路径。
- 测试覆盖注册、注销、实例隔离、所有者与来源、黑板、同步事件顺序、优先级，以及
  结束/停用后不再触发；具体保留项由原生证据决定，不凭直觉补规则。
- 目前已接入的能力实体生成/结束、Buff 事件与技能监听不回退，真实原轴的关键回执、
  伤害/资源结果保持不变；如变化，逐项说明真实缺陷及证据，不修改原始输入凑通过。
- 未支持机制显式记录，不通过宽化类型、删校验或吞事件制造“全量支持”。
- 更新协议与交接说明，清理被替代的重复实现，不留两套同时维护的主路径。

测试与类型检查串行，临时审计资料放忽略的 tmp。先做统一机制，不继续给不同监听器
各补一个事件的局部补丁。完成后恢复真实分享轴审计主线。
