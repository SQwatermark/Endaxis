# 战斗切面状态覆盖清单

更新日期：2026-09-14。本文记录 T0 对正式新版模拟的状态归属审查。它是
[任务安排与验收](../../handoff/runtime-checkpoint-plan.md)的技术附件，不另设任务顺序。

## 审查范围和分类方法

审查从 `CombatStateGraph` 向实际装配、标准环境、动作执行器和应用层调用方展开，同时搜索
`WeakMap`、`Map`、`Set`、数组、布尔生命周期位、订阅句柄、清理回调和局部闭包。每项按下列
五类归属：

| 分类       | 判断标准                                     | 保存和恢复方式                               |
| ---------- | -------------------------------------------- | -------------------------------------------- |
| 固定程序   | 编译结果、定义索引、步骤到稳定编号的映射     | 会话内只读共享；恢复时必须使用原目录         |
| 战斗数据   | 已发生输入造成、会影响以后结果的值和关系     | 进入完整数据图并整体复制；恢复后重新绑定程序 |
| 外部输入   | 尚未提交的技能块、切人、种子计划和转换候选   | 不进战斗切面；执行帧才提交                   |
| 步进临时值 | 只在一次同步调用栈内有效，稳定帧边界一定为空 | 不保存；禁止在执行中保存                     |
| 可重建绑定 | 回调函数、对象外壳、由数据 ID 定位的句柄     | 不复制旧对象；从已复制数据重新绑定           |

应用编辑器的撤销栈、模拟缓存和订阅者不属于战斗状态。它们仍须在 T3 遵守运行代号和结果
失效规则，不能让旧结果或旧句柄写入恢复后的分支。

## T0 结论

正式模拟中已发现的可变所有者均已归类，尚未接线项全部落入 T1 或 T2。T0 只证明基线可复现、
缺口有明确归属；它不证明整场可以恢复。Buff 子系统的数据和重绑协议已经覆盖当前生产定义，
下一步由 T2 在标准环境中重建来源宿主和动态对象目录，并在全部实例存在后统一解析跨容器关系。

T2 已先接入逻辑能力实体目录的基础恢复。构造器直接绑定复制后的目录数据，不调用 Spawn、Start 或
公共事件；关系阶段再解析子技能和子 Buff，reset 回调由实际持有者按保存编号接回。定向测试覆盖
局部寿命继续、实体黑板、定时标记到期、子 Buff 结束、reset 通知和原分支隔离。当前只证明目录
层协议。子技能状态现在保存自身技能身份和固定程序目录编号；目录持有具体已编译程序与伤害快照
槽位映射，同名的不同程序实例不会合并。恢复测试从保存的局部帧继续，只执行后续动作，不重放
开始动作或重复加入实体的子技能数组。标准环境构造器也可直接绑定复制后的生命、元素反应、倒地、Buff 进度、失衡 Buff 引用、
预施法监听和原生事件目录；测试证明按原订阅编号重绑事件，恢复分支受伤不影响原分支。资源账本
直接绑定保存的数据和动态限制，实体与施放编号从保存值继续。时间膨胀函数由同一切面树共享的
曲线程序目录按编号提供；恢复不发布开始事件，空目录会拒绝含曲线实例的状态。全局 Buff 父目录
可以接回已复制的子 Buff 与共享技力修正，恢复过程不调用目标施加端口。子技能程序、环境 Buff
容器、来源动作宿主与整场装配的统一调用尚未完成。

动作程序槽现由 `CombatOperationPrograms` 按编译节点身份统一编号，固定目录由切面树共享。
统一动作宿主现在包含全局 Buff、时间膨胀、能力实体寿命、连携候选、终结技能量回复限制、
定时标记、生命下限和技能施放继承八类关系。生产技能链把该宿主实际挂入
`SkillRuntimeState.operations`，能力实体子技能与来源技能共享同一份宿主状态。恢复分支对原步骤
执行结束时按固定程序槽只清理当前分支关系。事件宿主的启用状态、订阅引用和子 Buff 引用也已进入
纯数据；普通干员与能力实体被动保存共享黑板、启用与响应序列和动作宿主。装备贡献保存宿主、
黑板和响应序列，初始化程序保存启用/初始化序列及其动作宿主，潜能事件保存程序 key 与订阅。
这些状态均已进入整场数据图，复制恢复测试证明处理函数按原编号重绑，只修改新分支。反应式操作
链现与技能链使用同一动作宿主协议。剩余工作是完整装配的分阶段对象重建与统一关系绑定。

共享层已由 `CombatSharedRuntime` 统一新建或绑定，恢复分支直接使用复制图中的时钟、资源、回执、
演出、连携、膨胀、冷却和编号账本，不通过快照值重新构造近似状态。投射物目录可以先绑定纯数据，
再在所有宿主存在后事务式接回宿主和重置处理器；活动实例在关系完成前不能推进。标准环境向装配层
暴露按保存状态目录绑定原生订阅的端口，负责恢复事件目标上下文且不申请新编号。正式装配的新战斗
已经使用统一共享层，并按“共享层、环境、语义事件层”的依赖顺序构造；整场恢复入口仍要等其余
对象和跨容器关系全部接通后一次性开放。

整场恢复现在还有独立的只读预检阶段。它用当前固定干员程序核对候选图中的干员、技能、冷却、
被动、装备、初始化和潜能事件拓扑，并验证技能与共享冷却、技能与实体黑板、Buff 与实体黑板、
资源队伍与身份索引仍保留整图复制后的对象同一性。测试分别破坏缺失技能、冷却引用、队伍顺序和
资源身份索引，均在对象构造前失败。能力实体的目录键、容器创建标记、容器数据和共享黑板也在
这里核对。预检本身不算完整恢复；后续仍需创建并绑定全部来源宿主。

标准环境的实体容器阶段现可绑定整场候选图中的敌人和干员 Buff 状态。属性集合、实体黑板及容器
均直接引用保存数据，构造时不重新初始化面板值；测试核对三层引用的对象同一性。通用状态容器也
可从已有固定定义模板创建绑定保存 Map 的新外壳，且不会在绑定时改变层数或持续时间。活动 Buff
实例、生命周期动作和跨容器子实例关系仍属于下一绑定阶段。

`BuffDefinitionOperationTarget` 已把容器恢复分成实例与关系两个明确端口。实例阶段使用保存的
`definitionOwnerId` 和 `definitionId` 从当前固定目录编译生命周期程序，不会因不同干员存在同名
Buff 而误绑定。原来只保存在函数闭包中的跨实体来源属性读取目标，现记录为实体身份；恢复时必须
提供身份一致的当前分支读取端口。父子和 SkillAffix 对象关系仍留在所有实例完成后的关系阶段。

整场 Buff 协调器已覆盖三个顺序阶段：全部普通实例、全局父实例、全部跨对象关系。测试验证同名
定义按所有者解析、来源属性目标从当前实体目录重绑、缺失实体使候选永久失败，以及恢复全局父层
结束时只清理恢复分支的子实例。能力实体目录中标记为已创建的 Buff 容器也能批量重建目标外壳；
它直接复用保存的属性、实体黑板和容器数据，不重复施加出生标签。标记与数据不一致时在创建前
失败。协调器尚未由完整装配入口调用，下一步要把敌人、干员和能力实体目标一起交给它。

上一轮检查点定向回归通过 165 个文件、1765 项测试，类型检查通过。

普通干员技能另有 `CombatSkillPrograms` 固定目录。正式装配按完整技能身份登记原编译对象，并让
技能实例使用目录中的伤害快照槽位映射。同一身份若尝试绑定另一个程序对象会失败；恢复分支由此
可以复用原槽位，而不需要从可变快照数据猜测动作身份。整图预检还会为每个已保存技能生成包含
状态、当前定义和原固定绑定的准备项；传入空目录或另一棵切面树的目录会在创建对象前失败。

共享冷却恢复直接绑定 `CombatOperatorState.cooldowns` 中的账本。固定周期、提交帧和面板修正使用
正式装配的同一解析函数；连携冷却倍率回调只读取当前分支 Buff 目标。测试从进行中的冷却复制后
分别推进两条分支，并验证原分支不受影响；有无计时器与固定配置不符时在对象创建前失败。

普通技能宿主可由 `bindRestoredCombatOperatorSkills` 从预检项直接重建。绑定器核对技能状态引用的
冷却就是该干员恢复后的共享账本，并要求操作执行器携带同一份 `operations` 状态；固定伤害槽位
来自原 `CombatSkillPrograms`。测试在技能执行一帧后复制，恢复分支不重新施放或分配编号，之后
每帧的技能状态、能力系统状态和回执均与原分支一致。该绑定器尚未由完整装配候选调用。

`bindRestoredCombatOperatorAbilitySystem` 使用恢复后的技能对象和完整共享冷却目录绑定
`AbilitySystemState`。当前技能、处理中技能、技能槽、模式层、可操作边界和延迟请求均由现有
`AbilitySystemRuntime` 构造器核对。测试覆盖只有冷却、没有施放实例的技能：恢复后到达就绪只通知
一次，原分支计时不变；保存状态引用不存在技能时拒绝绑定。完整装配候选尚未调用该入口。

`bindRestoredCombatOperatorCore` 已把单名干员的共享黑板、状态、定时标记、共享冷却、普通技能和
能力系统组成一个有序恢复阶段。它要求恢复后的 Buff 目标直接绑定该干员保存的容器数据，并检查
实体黑板仍是同一对象；随后才创建技能操作链和能力系统。测试验证各层都引用候选图中的原数据，
技能仍共享实体黑板，且绑定过程不重新施放。来源宿主、Buff 子实例关系和整场装配入口仍待接入。

常驻被动恢复会从保存状态重建被动局部黑板、响应序列和启用序列，并按原订阅身份接到当前事件
目录；保存的启用状态不重放。装备事件恢复同样按贡献下标绑定黑板、响应和订阅。两类宿主持有的
子 Buff 都先按身份完整解析并缓存，任一缺失时不提交关系。测试验证事件只修改恢复分支、解析器
每个身份只调用一次，释放恢复宿主只结束恢复分支子 Buff。下一缺口是初始化和潜能事件来源。

养成/装备初始化恢复会把 `initializationSequence`、可选 `enableSequence`、黑板和统一动作宿主一起
接回。装备初始化的黑板必须与对应装备贡献状态保持对象同一性；直接养成初始化绑定自身保存黑板。
测试确认恢复不执行任何动作，装备宿主释放时仍持有恢复后的启用序列结束关系。下一缺口仅剩潜能
事件宿主和四类来源的统一装配阶段。

潜能事件恢复按原程序顺序绑定保存订阅，当前分支事件只进入当前处理函数。单干员来源协调器按正式
装配顺序组合装备、潜能、初始化和被动；所有来源建立后先检查子 Buff 所有权不重复，再对每个身份
解析一次并提交。整图预检已覆盖装备贡献集合、初始化身份与共享装备黑板、潜能程序顺序。

整场候选基础阶段直接绑定 `CombatSharedState` 与 `StandardCombatEnvironmentState`，并使用保存的
敌人、干员和能力实体数据收齐完整 Buff 目标表。普通 Buff 实例和全局父实例随后由同一协调器在
该目标表上恢复。当前测试包含一名干员，证明资源队伍、实体黑板和 Buff 容器保持复制图内的对象
同一性。下一步调用干员核心与来源阶段，再提交来源、能力实体和 Buff 间关系。

候选环境的原生事件重绑端口现与保存的语义事件状态组合成唯一事件中心。干员阶段先恢复全队核心，
再恢复来源宿主，并用候选 Buff 目标替换固定程序中原分支的目标引用。全队来源子 Buff 会在任何关系
提交前检查重复所有权和缺失实例。当前集成测试覆盖一名无动态技能的干员；下一步加入活动技能、
投射物，形成首个跨动态对象的纵向恢复样本。

能力实体关系协调器现按所属干员的当前编译定义恢复实体被动，并从同一切面树的固定程序目录恢复
进行中的子技能。保存数据中的旧定义对象不作为可执行逻辑。实体直属子 Buff 与被动子 Buff 会先检查
唯一所有者并完整解析；子技能不重放开始动作。实体目录也改为先构造整批关系、全部成功后再提交，
测试覆盖恢复后的下一帧继续执行以及中途解析失败后可重试。下一步把该阶段与干员来源做全局所有权
预检，再接回最终 Buff 对象关系。

投射物整场阶段现能直接绑定保存目录，并在关系阶段恢复命中回调。回调数据新增明确的定义干员，
解决 Buff 或嵌套实体作为运行时来源时无法可靠选择固定定义的问题。命中前不会提前创建回调技能，
命中后的宿主沿保存状态继续。投射物 reset 处理函数和 Buff recycle 处理函数均可按保存编号接回，
SkillAffix 对象引用已有统一路由。剩余装配工作是把这套路由放在 Buff 实例编译前配置，并在最终关系
阶段按“SkillAffix 引用、投射物宿主、Buff 对象关系”的依赖顺序一次提交。

本次新增协调器定向回归为 3 个文件、5 项测试通过，类型检查通过。整个当前未提交工作树另有
18 个文件、50 项既有失败，集中在生成数据、武器反应、UI 结构门禁和基础攻击链，不能作为检查点
