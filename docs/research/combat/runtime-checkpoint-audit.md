# 战斗切面方案审查（2026-09-13）

审查对象是 `8a7c7890` 的切面原型，以及 `961a9fda` 引入的旧轴接续窗口搜索优化。
目标是检查保存、分支试探、恢复是否可靠，并确认优化有没有改变转换结果。

结论：切面能力值得建设，但原型的分散保存与依次恢复方式不能作为可靠基础。它只覆盖了少数
账本，尚未接入正式装配。问题不只是缺几个字段，还包括隐藏状态、对象引用、恢复失败和未来输入
边界。现已撤下未接入的原型；改进后的完整方案见[架构设计](../../architecture/runtime-checkpoints.md)。

## 已确认的问题

下表中的原型文件名指 `8a7c7890` 时的代码；已经删除的文件可用 `git show 8a7c7890:<路径>` 查看。
运行时文件均在 `src/core/combat/` 下。

| 问题                       | 代码依据或复现                                                                                                                | 后果                                                                     | 修订方向                                                 |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ | -------------------------------------------------------- |
| 预检不能保证恢复完整       | `runtime/runtimeCheckpoint.ts` 先预检，再逆序调用各参与者恢复；后一个恢复可以在前一个已修改状态后抛错                         | 留下新旧混合状态，无法安全继续                                           | 在当前状态之外准备完整目标，最后只替换一个状态根对象     |
| 可以保存半帧               | 控制器只检查自身重入，没有与 `CombatSimulation.advanceFrame()` 的执行阶段关联                                                 | 帧号相同，但各模块处于不同阶段；恢复后既不能重跑整帧，也不能直接跑下一帧 | 只允许初始化后的稳定边界及完整帧结束边界                 |
| 回执只支持退回祖先         | 回执快照仅保存长度和边界对象；保存 A、恢复根、生成 B 后，恢复 A 抛出 `discarded branch`                                       | 已保留的候选分支不能再恢复，不符合通用切面的语义                         | 不可变分支日志，兄弟切面独立有效                         |
| 历史载荷仍可变             | `receipt/combatReceipt.ts` 记录时保留调用方的 `data` 引用；修改该对象后，恢复也看到新值                                       | 旧切面里的证据随未来修改变化                                             | 回执取得载荷所有权或复制成只读数据                       |
| 恢复输入游标仍知道未来     | `runtime/combatInputRuntime.ts` 保留构造时的全部输入；快照仅恢复消费游标和少量集合                                            | 试探中会继续执行原先准备的未来技能                                       | 未来计划留在调用方，按当前帧批次提交                     |
| 保存函数不等于保存函数状态 | `runtime/abilitySystemRuntime.ts` 的动作模式有闭包 `finished`；`events/abilityEventDispatcher.ts` 的注销回调有闭包 `disposed` | 回退后对象看似复活，实际却不能再次结束或注销                             | 状态用数据描述，函数只承担无私有状态的规则执行           |
| 句柄编号回退产生身份混淆   | 资源快照恢复 `nextRestrictionHandle`；旧分支句柄与新分支条目复用同一个数字                                                    | 旧句柄可能解除新分支的限制                                               | 内部确定性 ID 随状态恢复；外部句柄另带会话与运行代号     |
| 随机源有未公开内部状态     | `random/simulationRandom.ts` 保存随机函数，`mulberry32` 在闭包里更新整数；期望模式还有 `#evenIndices`                         | 只保存种子或函数引用，恢复后取样位置仍错误                               | 显式保存每条随机流的当前状态与期望计数                   |
| 部分“缓存”参与后续行为     | `runtime/skillInputGroupTiming.ts` 的回执游标和边界表；`runtime/combatRuntimeAssembly.ts` 的 `controlledByOperator`           | 连续组漏接续、主控事件漏发或重复                                         | 保存历史依赖状态；纯派生索引才能重建                     |
| 装配提前建立未来对象       | 完整轴在装配前生成各技能块运行时，并带入控制与随机计划                                                                        | 切面表面上只存当前帧，对象图却仍绑定旧未来                               | 区分预编译技能目录和实际施放实例；保留原生更新顺序       |
| 向后探测不能直接提交为前缀 | A 从 100 帧探测到 220 帧结束，但下一条其他轨道输入可能在 130 帧                                                               | 用 220 帧切面继续会跳过本应在 130 帧的输入                               | 分离已确认前缀与向后试探，保留较早基点；同帧输入成批重跑 |
| 二分搜索所需单调性不成立   | 原生允许接续窗口可以短暂开放，然后关闭，最后才到可打断边界；正式 `AbilitySystemRuntime` 同样如此                              | 漏掉最早窗口，给转换轴加入不必要延迟，可能改变后续伤害和衔接             | 已修为顺序探测；未来用切面降低每次探测成本               |

这些缺陷不代表当前正式模拟都已经出现对应错误。切面原型尚无生产消费者；前十一项说明如果
继续接入会出现什么风险。最后一项已经影响转换器的搜索行为，本次直接修复。

## 反例怎样验证

一次性反例位于本机 `tmp/checkpoint-audit/review.test.ts`，用
`tmp/checkpoint-audit/vitest.config.mts` 排除仓库对 tmp 的测试忽略规则。它们针对原型版本运行，
七项均复现了问题：

1. 两个参与者都通过预检，先恢复的对象变回旧值，后恢复的对象抛错，结果是一新一旧。
2. 第一子系统执行时调用保存，后一子系统尚未执行，控制器仍返回切面。
3. 根 → A → 恢复根 → B → 恢复 A，最后一步被拒绝。
4. 保存后把回执原始载荷从 1 改为 99，恢复后仍为 99。
5. 保存并恢复输入游标，再推进到第 10 帧，仍执行预装的 `old-future` 技能。
6. 保存含 `finish` 闭包的对象，结束一次后恢复，再结束不再执行。
7. 保存资源状态，在 A 分配限制句柄，恢复后在 B 分配同号句柄，旧句柄可删除 B 的限制。

命令为 `npx vitest run --config tmp/checkpoint-audit/vitest.config.mts --silent`。
这里的“7 项通过”指断言成功证明上述缺陷，**不是快照能力验收通过**。原型撤下后这些临时测试
不再适用于当前工作树；复核需要恢复审查版本。正式能力应按架构文档的验收清单另行实现。

转换器新增了正式回归测试 `tools/legacy-timeline/heuristicRetiming.test.ts`，使用真正的
`AbilitySystemRuntime.evaluatePlayerInputInterruption()` 判定输入许可：

- 前一技能在第 10 帧开始，后一技能旧位置为第 20 帧。
- 第 30～32 帧允许特定后续技能；窗口关闭后直到第 260 帧才允许一般中断。
- 修复前搜索返回 260，断言期待 30，因此失败。
- 修复后返回 30；同时保留无早期窗口、到 260 才开放的对照。

这验证的是正式输入窗口的非单调性，不是为了让测试通过而杜撰的假许可函数。

## 性能结论的修正

“模拟次数变少”不必然说明复杂度已经改善，必须同时看每次编译、重放、复制与整理的工作量。
切面可以消除从零重放，但如果每次复制不断增长的状态或日志，总成本仍可能是平方增长。
完整状态复制是首版正确性基线；日志分块共享，其他容器按测量决定是否需要写时复制。

撤销日志、任意对象图克隆、依赖恢复顺序的模块协议都暂不采用。这些方式让遗漏状态或一次写入的
代价很高，当前尚未显式管理闭包与动态对象，不宜先用这类机制承诺完整恢复。
借鉴的系统、具体取舍和后续验收统一维护在架构文档，不在此复制第二份实现路线。
