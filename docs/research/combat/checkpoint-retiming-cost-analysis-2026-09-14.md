# 旧轴截面转换耗时分析

## 测量范围

Windows 笔记本、PowerShell、Node v24.13.0，当前 `refactor/common-game-data` 未提交工作树。
使用 `Endaxis_Timeline_2026-08-31.json` 和 `mappings.2026-08-31.json`，共三场景、102 技能、
127 候选、128 试跑分支。串行执行，先暖机，再计时三次；每轮开始前显式 GC。

计时包含 `convertLegacyTimeline` 全部同步工作，不包含模块加载、读写文件、产物一致性比较。
分项采用嵌套计时，表中互不重复；逐帧推进包含该调用期间的分配和 GC，不能另加 CPU 采样的 GC 时间。
插桩结果均与未插桩转换结果深度一致。临时脚本及原始结果位于忽略目录 `tmp/`，不提交。

## 原固定 300 帧观察的构成

三次分项总耗时为 5.916、5.913、5.863 秒。以下使用总耗时居中的同一轮，不能把各分项中位数相加。

| 工作                        |        耗时 |  占比 | 数量      |
| --------------------------- | ----------: | ----: | --------- |
| 候选分支模拟                |    2.896 秒 | 49.0% | 38,710 帧 |
| 分叉时复制状态图            |    1.042 秒 | 17.6% | 128 次    |
| 保存截面时复制状态图        |    0.635 秒 | 10.7% | 103 次    |
| 恢复对象及关系绑定          |    0.593 秒 | 10.0% | 128 次    |
| 推进确认前缀                |    0.543 秒 |  9.2% | 3,501 帧  |
| 筛选、复制所需回执          |    0.071 秒 |  1.2% | 128 次    |
| 构筑/技能编译及新战斗初始化 |    0.036 秒 |  0.6% | 3 次      |
| 解析候选人工输入排程        |    0.032 秒 |  0.5% | 230 次    |
| 其余转换、校验与驱动开销    | 约 0.064 秒 |  1.1% | —         |

编译不是主要瓶颈。图复制合计约 1.68 秒，恢复绑定约 0.59 秒，两者应分开。
此次总模拟 42,211 帧，包括重复观察未来；不是三条轴各自最终长度的总和。

## 观察窗口过大

原实现先推进到候选输入后 300 帧，才检查显示结束和终结技时间膨胀。
128 次观察中，33,819 帧位于当前候选的 `SkillOperableBoundaryReached` 之后，约占候选模拟帧的 87%。
这只是潜在过度观察量，不能全部当作可直接删除：其他轨道的上一输入边界及尚未结束的终结技膨胀也可能必要。

诊断实验仅通过内存中的模块变换，将首段窗口改成 30 帧并保持最大观察范围 3,900 帧。
三次计时中位数约 4.22 秒，三轴产物/报告一致（排除观察次数统计）；分支数仍为 128，
观察次数变为 209，其中延长同一分支 81 次。它证明了过长窗口的成本，不是正式采用 30 帧的理由。

正式方向是在完整帧末、相关事实出现时判断是否足够。最大窗口只负责超时兜底。
初步真实轴验证发现：只等待当前候选边界不足，可能比另一轨道上一技能更早停止，使下一次排程缺少该轨道边界。
必须同时保留下一步计算所需的轨道边界，不能用未经确认的旧预测值补齐。

现已接入按事实停止：完整帧末出现当前技能及各轨道前一技能的显示边界，且已开启的终结技膨胀
全部结束，即停止当前观察；尚未满足时继续同一分支。原 300 帧保留为首段观察上限，不再强制跑满。
为保留原有输入窗口耗尽后的回退结果，被判不可中断的候选目前也先取得所需显示边界；
尚未改成一收到不可中断事实就结束。不能把该部分进一步优化当作已完成。

同进程串行暖机后各三次对照：固定观察中位数 5.804 秒，按事实停止 4.162 秒，约减少 28%。
项目及报告深度一致（比较排除运行计数，计数另外核对也一致）：仍为 102 技能、127 候选、128 分支。
总模拟帧从 42,211 减到 8,517；确认前缀仍为 3,501 帧，候选从 38,710 减到 5,016 帧。
此样本包含多轨道及终结技消费者，不代表全部输入组合已验证。

按事实停止后的独立分项三次为 4.175、4.128、4.143 秒；总耗时居中轮：

| 工作                     |        耗时 |
| ------------------------ | ----------: |
| 截面保存及分叉的图复制   |    1.653 秒 |
| 候选模拟                 |    1.106 秒 |
| 恢复绑定                 |    0.589 秒 |
| 确认前缀模拟             |    0.549 秒 |
| 回执读取                 |    0.086 秒 |
| 编译初始化及输入解析     |    0.065 秒 |
| 其余转换、停止判定及驱动 | 约 0.095 秒 |

逐帧检查使回执读取次数增加，但只扫描新回执，读取总耗时只从约 0.071 秒增到 0.086 秒。
不应把每次返回的全局回执游标之和当作扫描量。

## 复制中的历史负担

在同一转换中另取一个较大的状态图做诊断，含 5,277 条回执、107 个干员技能状态。
`v8.serialize` 得到 2,254,420 字节；仅在独立诊断副本中清空回执后，为 534,200 字节。
各克隆 15 次，完整图中位数 13.91 毫秒，去回执副本 5.73 毫秒。

这说明历史回执在该样本中占序列化体积约 76%、显著增加复制耗时，但这些数字不是堆内存峰值，
也不是所有截面的平均值。正式修复不能删除回执；可研究已确定历史的不可变分段共享，仅复制可变后缀。
共享前必须核实回执数据没有被后续写入，不能只凭 readonly 类型假定不可变。

## CPU 采样与优先级

另一次 1 毫秒采样显示 structuredClone、垃圾回收、实体黑板 snapshot 是热点。
`LogicalAbilityEntityRuntime.advanceFrame` 给时间增量和 Buff 生命周期钩子多次构造 snapshot，
每次包含 `ActionBlackboard.snapshot()` 的 `Object.fromEntries`；这属于逐帧临时对象分配，
与保存战斗截面的图复制不是一回事。需要检查具体钩子读取什么，再减少不必要的复制。

建议顺序：先按事实停止候选观察，再处理历史回执共享，最后按采样证据收缩逐帧快照分配。
输入解析和编译合计约 1.1%，当前不值得优先增加缓存复杂度。

## 长轴内存

2026-09-15 使用带主控切换的“弭洛卡骏”转换项目做长轴验收。该场景有 66 个输入、3600 帧，
在第 1800 帧保存。进程使用 `--expose-gc --max-old-space-size=1536`，先从同一保存点完整续跑并释放
96 次，使模块、JIT 和固定程序目录充分预热；随后再测 96 次。每条分支都推进到第 3600 帧并生成
正式应用结果，全部结果哈希为
`6fed3e00575c668e75bc035e01ed276f23cf96601c0484d9f090e05d1d6d6da9`。

测量基线堆为 150450408 字节；同步操作边界观察到的堆峰值为 226776232 字节，进程生命周期总 RSS
峰值为 602243072 字节。96 次测量完成、保存点仍被持有时，堆为 152091256 字节，比基线多
1640848 字节；丢弃保存点并再次强制 GC 后为 148172192 字节，比基线低 2278216 字节。因此没有
任何一个完整候选图在测量结束后残留。第一次和第 96 次分支释放后的堆分别为 148835064 和
152184552 字节，仍有约 3.2 MiB 的缓慢增长；它可能来自运行时缓存或 V8 稳定过程，本次不能证明
进程零增长。因此又单独测量多轮完整转换，避免继续复用同一个保存点掩盖进程级增长。

`process.resourceUsage().maxRSS` 能覆盖同步步骤之间来不及采样的进程 RSS 峰值；JavaScript 堆峰值
只在分叉后、续跑后和结果投影后三个边界采样，因此称为“可观察堆峰值”，不能冒充 V8 内部的瞬时
精确峰值。复现脚本为忽略目录中的 `tmp/audit-checkpoint-long-axis-memory.mjs`。

## 完整转换循环内存

同日使用 `C:\Users\Admin\Downloads\Endaxis_Timeline_2026-08-31.json` 和一次性映射文件
`tmp/mappings.2026-08-31.formatted.json`，在同一进程中反复调用完整 `convertLegacyTimeline`。
输入含 3 条轴、102 个技能块。进程仍限制为 1536 MiB 堆，先预热 3 次，再测量 12 次；每次都复制
输入，执行完整转换并生成报告。12 次结果哈希均为
`42017380fb63f3540f06c7d689a6ad896b8c64e4bc42efa8d3728a6f22304437`。

测量基线堆为 140457432 字节；转换结果仍存活的边界观察到堆峰值 303394592 字节，进程生命周期总
RSS 峰值 612876288 字节。第 1、4、7、10、12 次释放并强制 GC 后的堆分别为 140127520、
140760808、140692632、140936560、141084824 字节；没有随次数明显累积。最终堆为 139819304 字节，
比基线低 638128 字节；最终 RSS 比基线多 1495040 字节。RSS 不会在每次 JavaScript GC 后立即归还
操作系统，因此以释放后堆趋势判断是否仍有对象被引用，以进程最大 RSS 判断容量上限。

两项审计合起来说明：保存点反复分叉的重型状态能够释放，完整旧轴转换循环也没有观察到持续堆增长。
这不是对任意轴规模和任意 Node/V8 版本的零泄漏证明。复现脚本为忽略目录中的
`tmp/audit-legacy-conversion-memory.mjs`。

复现脚本：`tmp/checkpoint-cost-profile.mjs`、`tmp/checkpoint-cost-detail.mjs`、
`tmp/checkpoint-lookahead-experiment.mjs`；结果分别存入同名 JSON，CPU 样本为
`tmp/checkpoint-conversion.cpuprofile`。这些文件包含本机路径，保留在忽略目录。
按事实停止的对照为 `tmp/checkpoint-event-stop-benchmark.mjs/json`，分项结果为
`tmp/checkpoint-cost-profile-event.json`。旧轴工具 7 文件 55 项通过，最终全量验收仍未完成。
