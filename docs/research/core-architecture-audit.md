### 导入核查

方法：用仓库 TypeScript 解析器扫描 `.ts/.tsx` 的静态 import/export 和字面量动态 import，排除 `*.test.*`、`*.bench.*`，对生成器再区分 `test/` 支持代码；规范化相对路径与 `@/`。另查 Vue 页面中的服务装配与可变运行时引用。

- 核心到应用、UI、正式数据、平台、设计系统、工具以及 Vue/Pinia 的直接导入：未发现。
- 应用生产 TypeScript 到离线工具、契约到包外模块的直接导入：未发现。
- 生成器生产代码到主包有 10 条导入，指向图校验/数据节点、定义校验和数值比较。沿这些入口追踪的 16 个模块只包含上述纯逻辑和契约；没有通过共享代码加载 UI、应用状态或正式数据仓库。
- 生成器测试支持代码会引入正式仓库和模拟服务，用于对比优化前后行为；这是测试边界，不能误报成生产反向依赖。
- 检索 UI 未发现 `CombatRuntimeAssembly` 或 `stateGraph` 直接访问；正式结果由会话复制状态、固定回执后收集。UI 对项目通过编辑事务写入，但项目对象引用是否足够隔离留到数据归属阶段核对。

这些结果支持现有总体分层，不支持为了目录“更整齐”搬移职责。静态扫描不证明不存在运行时别名修改，也不穷举字符串计算式加载；Vite 的 `import.meta.glob` 已人工检查为生成定义装载。

### 初步关注点

1. 核心依赖约束目前主要靠约定和现有编译配置，而非覆盖应用全图的自动化禁止导入检查。属于防回归风险，尚无违规实例。
2. 场景编译输出同时携带固定程序与可变运行环境端口（`operatorRuntimeBindings`），并非可以随意序列化/复用的纯数据程序包。下一阶段检查这些端口的寿命和恢复规则，避免把“编译纯函数”误读成“所有返回对象永久不可变”。

### 恢复和失败的准确承诺

- 保存图与程序、回执是三个不同边界。程序目录共享的只是固定身份/程序，不应共享可变伤害数值、资源、Buff 进度或随机流。
- 标准恢复先预检，再建立共享账本/环境外壳、各宿主及关系。`bindRestoredCombatRuntimeFoundation.ts:105–155` 校验随机状态、设置以及恢复环境的对象身份。正式场景随机源绑定到保存图；低层自定义回调或取样器不能凭类型自动获得可恢复性。
- `CombatRuntimeSession.restore` 完整候选成功后才替换当前装配，失败保留之前的装配和阶段（`:173–195`）。但 advance 抛错不是自动回滚，当前分支被标记 faulted，之后只允许恢复有效保存点；不能把这两种失败混为一谈。
- 常驻监听器属于整场装配；装配提供被动、连携条件和装备事件各自的注销入口（`combatRuntimeAssembly.ts:3224–3357`），但没有统一会话 dispose 契约。整场回收仍依赖宿主和缓存释放引用。动态实体监听器有专属结束清理。尚无内存泄漏证据，不据此要求给所有运行时添加 dispose。

### 已确认的边界风险，尚非产品故障

静态定义和项目并非全链路深冻结：仓库索引保留定义引用，`ProjectEditorSession` 的构造、snapshot 和 command 都传递原项目引用。图编辑有单独的深冻结工具，但不能据此推断整个项目都受运行时保护。因而“不原地修改”仍是调用约定；错误命令可能先改旧对象再返回同一引用，导致无新 revision 却污染撤销历史。下一阶段验证真实写入口与回归覆盖，再决定是否需要只读类型或开发期冻结，不直接在全库添加克隆。

## 3. 子系统协作与时序

### 责任与顺序

| 路径             | 谁决定 / 谁写入 / 谁清理                                                               | 顺序及失败边界                                                                                                                          |
| ---------------- | -------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| 技能输入         | 应用排程提供当前输入；能力系统判断能否启动；协调器记录参数与诊断；输入运行时更新连续组 | 参数/种子登记 → 实例绑定与切人 → 原生路由/门禁诊断 → `canStartSkill` → 准备和执行。`executed` 才终止其他组；`rejected` 不能伪装成功     |
| 换槽             | 能力系统拥有槽位合法性；`combatSkillSlotCoordination` 拥有替换登记、冷却转移及成功回执 | 先记默认还原身份，验证旧撤销及新目标，再执行旧撤销→新切换→登记。旧 registrationId 结束不撤销新登记；在施放实例保持原身份                |
| 同步事件         | 事件目录拥有订阅 ID/优先级；分发器持有当前分支函数；宿主负责注销                       | callback → action → skill → combo；每阶段开始取处理函数快照。同阶段新增等下次，后阶段新增可被本次看到；同步嵌套必须恢复外层事件上下文   |

### 完整帧的架构约束

`combatFramePipeline.ts:31–84` 是真实顺序所有者：时钟由驱动推进；变速、切人、控制、资源、父 Buff/实体/投射物、敌方 Buff/生命/状态、角色状态与窗口先行，再提交技能输入、执行能力与投射物能力帧，最后处理外部事件。输入前归零的连携窗口不能在同帧被消费；本帧新注册者可以接收后置外部事件。新建与恢复共用此管线，不能各维护一份“等价”循环。

当前分层刻意区分三种信息：原生合法性诊断、时间轴显式执行意图、实际执行成功结果。告警并不必然阻止用户安排执行，`executed` 也不保证出现 `SkillStarted`（例如转 Buff 施放）。这属于已有产品/执行契约，不能以“更严格”为由改写。

### 失败与变更传播

- 换槽预校验保护已知装配不变量，不承诺任意外部回执回调抛错时整条操作回滚。事件/技能推进发生异常由会话 faulted 状态隔离；批量清理工具尽力执行其余清理；单错误直接抛出，多错误聚合为 AggregateError（`abilityEventHostLifecycle.ts:10–20`）。
- 扩展新事件需同时更新契约载荷、动作上下文绑定、发布者、宿主监听与恢复绑定及原生测试；仅给事件名加枚举不足够。
- 新增有状态宿主需同步确认固定程序目录、状态图、恢复身份、回执来源及结束清理；这是局部变更穿过多个模块的真实原因，不应把这些字段机械搬进万能上下文。
- 已完成的统一效果链、执行结果区分、换槽预校验和事件响应身份边界均有原生回归覆盖，本阶段没有把它们重新列为待修复。

验证：基线选取 9 个原生测试文件共 178 项通过，覆盖 runtime session、槽位替换、事件上下文/分发、Buff 回收、应用会话、模拟服务、Worker 和 UI 发布。该结果不是全部组合路径通过的声明；全实体类型的来源消失后延迟回调及注入异常仍需按场景补矩阵。

### H1：性能观察者异常可以使 Worker 请求永久悬空（已复现）

`workerScenarioSimulationService.ts:74–81` 先把 active 清空，再通知性能订阅者，最后才 resolve/reject 和 pump。若观察者抛错，当前 Promise 失去结算入口，待算请求没有发出；随后 dispose 只能拒绝待算请求，找不到已经移除的 active。协议解码抛错也位于同一个未保护完成路径，尚未独立注入复现。

实际订阅链为 Worker → `AdaptiveTimelineSimulationService.acceptSample` → `useScenarioSimulation` 的性能样本追加（`adaptiveTimelineSimulationService.ts:109–114`、`useScenarioSimulation.ts:89–95`）。当前样本追加只是冻结数组/对象，未发现正常数据必然抛错；这里复现的是观察者异常隔离缺陷，不是已观察到用户界面卡死。主线程服务也直接调用观察者，会把成功模拟变成失败，属于同一责任越界。

最小方向：请求结算和队列推进由服务掌握，使用明确的 try/catch/finally；性能观察不能决定模拟成败。需要约定观察错误的报告方式，不能无声吞掉。验收必须涵盖成功/失败响应、观察者抛错、协议恢复抛错、后续请求继续以及 dispose 后无悬空 Promise。

### H2：Worker 往返削弱已发布结果的不可变性（已复现）

`scenarioSimulationWorkerProtocol.ts:63–69` 重建冻结回执并冻结外层 run，却把结构化克隆后可变的其他嵌套对象直接展开。使用真实空场景模拟 2 帧，主线程的技力曲线点与 enemyVitals 为冻结对象；经 `toSimulationWorkerResult` → `structuredClone` → `fromSimulationWorkerResult` 后两者不再冻结，写曲线点成功。回执自身仍冻结，不受此问题影响。

这证明公开结果契约在两种后端不一致；未发现现有 UI 主动修改该点，也未证明战斗数值计算被污染。它允许消费者破坏已发布的展示事实，后续图表/缓存可能看到被修改的数据。

最小方向：在协议恢复边界恢复本地结果已有的嵌套不可变保证，避免重新克隆战斗图或全量生成定义。验收对同一真实结果进行结构化克隆往返，比较内容及代表性深层只读对象；同时覆盖技能规划中的嵌套 run。

上述两项的可执行最小复现、输出与限制见[结果边界复现](core-architecture-reproductions.md)。复现使用原仓库模块，没有改动生产实现，也未运行真实浏览器 Worker；structuredClone 使用 Node 的标准实现，观察者异常通过 Worker 替身触发真实桥接处理函数。
