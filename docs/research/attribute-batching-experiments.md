# 命中内属性批量读取：两种实现均未保留

**结论：不修改生产算法。** 普通模式的新采样和调用计数确实发现重复修正器扫描，但两种命中内批量读取都没有得到可重复的总耗时收益；第二种在 75 块冰队轴稳定退化约 7%。这些局部实验不足以触及主导成本，不能宣传加速或分配收益。

本轮是[可选执行跟踪](optional-execution-receipts.md)之后的新方向，与动作程序检查的局部实验独立。实验生产基线为 `16bd46e09adff8f581cbe5f28956eaf6bafcfe44`，普通回执和战斗日志行为保持不变；隔离工作树已恢复到该生产源码。没有提交候选算法、缓存或批量 API。

## 两个被拒绝的实现

1. **按属性临时分组，再复用原标量求值器。** 每次命中创建局部修正器分组，保留注册顺序，逐键调用原八槽公式。只筛查稠密和电队两轴：稠密两轮总中位数分别 **+4.94% / +1.28%**；电队 **−10.67% / +1.12%**。没有稳定收益，停止扩大验收。
2. **一次遍历累加各属性八槽，再生成快照。** 每个属性内部浮点加乘顺序和三阶段公式保持一致；同样只在当前同步命中中使用局部数据。六轴完整两轮结果如下，正值表示变慢。

## 语义和验收边界

- 两种候选每次运行的输入、方案、游戏数据、完整结果和有序回执摘要一致；没有用伤害差异换速度
- 第二种在全部六轴逐项深比较完整运行状态、完整结果、逐帧 HUD、被动 UI 曲线、Buff 时间段和切面结果，全部与基线一致。状态另做保留 Map/Set 顺序、别名引用、非有限数和负零的确定性图摘要，两版相等
- 伊冯轴切面 126 / 127 帧仍报已知 `missing projectile reset handler 0`，基线和候选一致；这两点是失败，不能称全部恢复通过
- 两种候选分别通过原生专项测试 2 文件 / 4 项，覆盖交错槽位、来源过滤、界限、重复键、浮点累计顺序、暴露状态修改、局部恢复以及缺失属性/定义行为。没有引入 CombatSpec 依赖
- 独立只读代码复核未发现普通数据状态模型下的语义缺陷；测试仍未穷举乘法溢出/下溢与整个状态图重绑定。因为性能已失败，没有进入候选全套 tests / types / build 接受阶段
- 候选源文件及实验测试均撤回，只保留报告。不能把少扫描解释成分配下降，更不能据此声称端到端加速

## 下一项较大调查，尚未启动

建议转向 **Buff 每帧扫描的有效工作比例与事件调度上限**：累计采样中 `combatBuffs.tick`、生成器和图执行上下文持续占用 CPU 与分配，但目前缺少“真的有到期事件/状态变化”的帧数证据。先分离到期/周期回调、持续属性变更、纯存续检查，量化可跳过空转的范围；只有省时上限足够大才设计按下一到期帧调度，并保留同帧顺序、同步重入和切面恢复。这里不建议重试已失败的图适配器复用，也不把调查当成已有收益。

本轮到此结束，不继续调批量阈值或堆叠微优化。
