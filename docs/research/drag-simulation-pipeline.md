# 拖动输入、模拟与结果发布的工作量

这份研究回答两个问题：新拖动位置会替换哪一部分旧任务，以及一次手势是否产生不再使用的模拟、传输和展示工作。基线为 `e8be553a4cf191ff402ed7d2cd2f870140df6b02`；没有修改生产调度或战斗规则。

## 边界与复现

输入是[六份公开轴夹具](../../tools/performance/fixtures/public-timelines/README.md)，保留各自完整时长、配置和输入。每份选一个未锁定、显式排程的技能，向后移动 12、18、24、30 帧，每个位置发送三次，共 12 次指针移动，随后在最终位置松手。

[离线审计工具](../../tools/performance/drag-pipeline-audit.test.ts)实际调用：

- `useTimelineCastMove` 的事件处理器与移动命令
- Vue `shallowRef`、同步 watcher、`useScenarioSimulation` 和正式编辑会话
- 自适应服务、Worker 客户端、实际 `scenarioSimulation.worker` 入口和正式模拟器
- 请求/响应两端的 `structuredClone`、正式协议恢复、发布展示快照

替换的只有 DOM 几何/指针载体、自动滚动时钟和 Worker 运输时钟。Worker 入口仍在 Node 同一进程执行，**不是真实浏览器 Worker、浏览器输入排队、组件更新、布局、绘制、帧率或交互延迟测量**。本地分支和 Worker 分支通过构造参数固定，不能拿此运行时间判断实际设备在默认阈值下选哪个后端。没有每帧生产日志或运行时插桩。

运行命令和输出见[工具说明](../../tools/performance/README.md#拖动调度与重复工作)。计数按因果顺序记录，不比较几百分点的墙钟差异。每个场景最后验证输入对象未修改、最终有序回执等于独立正式复跑、发布绑定最终场景、拖动状态已清理，以及一次撤销返回原输入。

## 实际链路

1. `useTimelineCastMove.beginCastMove` 捕获原场景、选区和显示起点，开始交互会话。`pointermove` 超过阈值后计算命中轨道、时间映射、吸附与多选限位；只有实际落点改变才替换 `scenario.value`。普通指针处理没有 rAF 节流；rAF 只用于边缘自动滚动。
2. `useScenarioSimulation` 以 `flush: 'sync'` 观察整个场景引用。默认延迟是 0。空闲立即调用服务；忙碌时只标记一次 `rerunRequested`，不为每次移动发送请求。
3. `AdaptiveTimelineSimulationService` 普通编辑使用 Worker。拖动开始时最近完整模拟 `totalMs <= 200` 则本次交互固定使用本地主线程服务，否则使用 Worker；结束手势后回到 Worker。两个后端有独立服务/前缀缓存。这个 200 ms 是后端选择阈值，不是拖动刷新频率、16.7 ms 帧预算或实际 UI 延迟。
4. Worker 客户端也是单 active + 最新 pending。新 pending 拒绝旧 pending，但不结束 active。只有真正泵送时才复制场景并发送；定义选择集合与 revision 未变时不重发游戏定义。
5. 本地 `ScenarioSimulationService.simulate` 虽然返回 Promise，战斗推进及结果投影是同步段。Worker 入口调用同一服务，完成战斗、曲线与诊断后去掉进程内 `receiptHistory`，发送完整纯数据结果。
6. 主线程接收后按序恢复回执历史和冻结曲线，再完成 Promise。普通新位置不会让 Worker 跳过旧请求的模拟、投影或传输。
7. 页面按 epoch、方案身份和发布序号判断是否发布。**同方案旧落点可以作为完整预览发布并标记 stale**；不是一律只发布最新请求。返回已发布的原引用、切项目/重置或更晚结果已发布时会挡住旧结果。
8. 发布触发 `usePublishedSimulationDisplay` 的同步显示身份/战斗日志捕获。`TimelineEditor.vue` 还有基于场景的全轨道 view model，以及基于发布回执的命中、Buff、控制、被动 UI 等 computed 投影。它们之后才进入 Vue 组件更新和浏览器绘制；本工具不统计后两者。computed 是惰性缓存，不能用源码里 computed 的数量当作一次拖动执行次数。

## 面板 250 ms 为什么不等于每秒四次可见刷新

`SimulationPerformanceAudit` 的最新值与 P95 直接读取 `sample.totalMs`；柱形拆成 `simulationMs` 与 `projectionMs`。起点和终点都在 `ScenarioSimulationService.simulate` 内，终点在性能订阅通知之前。因此面板包含战斗推进和服务内部曲线/诊断投影，但不包含：

- Worker 请求去代理、请求结构化克隆与线程消息排队
- Worker 结果协议转换和响应结构化克隆
- 主线程回执历史恢复、冻结与性能订阅通知
- 发布后的显示元数据/日志捕获、其他按需 UI 投影、Vue 更新、布局与 paint

Worker 模式的后续请求要等前次响应解码、Promise 恢复与同步发布捕获结束，才在 `runSimulation` 的 finally 内启动。这些串行工作会加在两轮模拟之间。默认没有额外防抖等待（0 ms），也没有普通 pointermove 的固定刷新定时器。250 ms 只能给出忽略一切额外工作的计算吞吐上界，不能直接倒数成画面刷新率。

审计另给协议转换加离线包装计时，并记录因果事件的相对时间。以下是一次完整六轴运行中，突发 Worker 分支的两次响应，共 12 个样本，仅用于确认漏计阶段确实存在：

| 离线阶段                                |   本次观测范围 |
| --------------------------------------- | -------------: |
| 响应 `structuredClone`                  |  5.34–34.28 ms |
| 正式主线程历史/曲线恢复                 |  1.55–10.55 ms |
| 发布→同步显示捕获完成                   |  0.73–11.54 ms |
| 首次响应进入→下一请求发送，六次串行间隙 | 11.07–47.82 ms |

这些范围不是经过配对、热身的性能估计；同进程 Node 克隆不等于浏览器跨线程传输，显示捕获也不包含组件渲染。各项有包含关系，不能将总间隙与子阶段相加。不要把它们用于预测用户机器的 FPS。

例如公开轴 `6a91c4241854aefb13172209` 的一次服务样本为 283.80 ms，面板之外还观察到响应克隆 12.45 ms、恢复 3.80 ms、同步显示捕获 1.71 ms；下一次发送距响应进入为 18.35 ms。另一轴 `6abbd0200ce683bcda839545` 的服务样本为 200.36 ms，而对应间隙为 34.65 ms。它们证明计时边界的缺口，不证明用户描述的具体刷新率由哪一项独占造成。

本地路径还有不同风险：后端在手势开始时选择一次，如果当时 ≤200 ms，但后续落点变成 250 ms，本次手势不会自动切换 Worker。同步计算会推迟后续输入与浏览器绘制；微任务中的发布也不保证立刻有一次 paint。必须用真实浏览器测输入到可见结果的时间、实际发布次数和实际绘制次数，不能由 Node 事件次数反推。

## 新请求会不会顶掉旧请求

| 位置                       | 新请求的实际影响                                            |
| -------------------------- | ----------------------------------------------------------- |
| 页面尚未启动的待算位置     | 合并成最新 `scenario`，中间位置没有调用模拟服务             |
| Worker 尚未发送的 pending  | 被新 pending 替换并以 `AbortError` 结算                     |
| 正在执行的 Worker 模拟     | 继续完成，响应到达后才发送下一项                            |
| 对 active 发出 AbortSignal | 消费者 Promise 拒绝；没有向 Worker 发送取消消息，CPU 仍继续 |
| 清缓存/换定义 revision     | 旧结果作废，旧计算不因此中断                                |
| 正常新请求                 | 不 terminate/recreate Worker                                |
| dispose / Worker 致命错误  | 终止 Worker 并结算已知任务                                  |
| 本地主线程同步段           | 无法被后续 pointer 事件抢占；事件等当前同步段返回           |

因此“取消等待”“不发布旧结果”“替换 pending”和“取消运行时计算”是四件不同的事。当前机制主要合并等待位置，保留进行中计算以免长任务持续重启而永远无法完成。

## 六份夹具的一致计数

以下不含首次显示和撤销各自的一次模拟。六份夹具均得到相同工作次数：

| 输入/调度                                         | 预览场景变化 |       拖动与松手总模拟 | 完整发布/显示捕获 | 明确无用的计算                           |
| ------------------------------------------------- | -----------: | ---------------------: | ----------------: | ---------------------------------------- |
| 12 次移动，每个不同位置完成后再继续，Worker       |            4 |                      5 |                 4 | 松手额外算原位置 1 次                    |
| 同上，拖动本地分支                                |            4 | 5（本地 4 + Worker 1） |                 4 | 松手额外算原位置 1 次                    |
| 12 次移动，首个 Worker 请求未返回前全部送达并松手 |            4 |                      2 |                 2 | 中间两位置未算；首旧位置作为完整预览发布 |

忙碌路径的具体顺序是：发送 +12 → 场景变为 +18/+24/+30，但没有更多发送 → 松手 → +12 完整响应并发布旧预览 → 发送 +30 → +30 完整响应并发布当前结果。没有取消或重启在跑模拟，也没有把 12 次移动都变成 12 次计算。

逐次完成路径的松手顺序是：+30 已发布 → 结束交互并切回 Worker → `scenario.value = baseScenario` 同步启动原位置请求 → 编辑会话提交最终场景 → 原位置完整模拟、投影、传输和主线程恢复 → 页面发现当前已回到已有发布场景，拒绝发布该结果 → 等待者由已有发布结果满足。这个请求**消耗工作却产生 0 次发布、0 次显示捕获**，且不是补算最终位置所必需。

这不是完整结果缓存命中。正式服务保留单前缀切面和继承前缀，不缓存整份最近结果；`useScenarioSimulation` 只在忙碌收尾时检查现有发布是否已经满足等待者。松手没有先经过这一保护，就先启动了原位置模拟。

## 其他已知重复入口

工具在第一份夹具的 Worker 分支额外检查三个边界：

- 空闲时对完全相同引用调用 `simulateNow`：仍会调用服务并重建完整结果。该 API 名称可能本来就表示强制重跑，不能直接全局改成缓存命中；应先区分“确保当前结果”与“强制重新计算”两个需求
- 只切换 `editor.prepExpanded`：场景 watcher 仍启动模拟。当前比较器只忽略图排版，其余展示字段仍被当作模拟变化；是否抽取模拟输入身份须用显式字段归属和失效测试，而不是不断增加随意的忽略白名单
- 只改技能节点图坐标：模拟被正确跳过，但发布对象换成绑定新场景的包装；`usePublishedSimulationDisplay` 仍会再次捕获显示元数据和战斗日志。这不等于所有回执 computed 都重跑，后者还受结果/数组引用缓存影响

同一吸附位置仍会执行移动命令后才比较 `previewFrame`，所以 12 次移动不等于只做 4 次几何/文档准备工作；已经确定的好处是只有 4 次场景替换和模拟调度。该部分应在真实指针/布局采样中确认占比，优先级低于已经观测到的多余完整模拟。

## Vue 展示链路：已证实工作与仍待测部分

以下继续以相同生产源码为基线。需要分清 Vue computed 的 JavaScript 工作、组件更新、DOM patch、样式/布局和浏览器绘制；当前离线工具只能测前一部分，不能把所有项都叫“Vue 渲染耗时”。

### 命中标记前存在未消费的旧效果投影

`TimelineEditor.vue` 的 `castHitMarkers` 在判断是否有模拟结果之前，先读取 `castHitEffects.value.get(castId)`：

- 有模拟结果时，随后直接由 `hitOccurrences` 生成实际命中标记与提示文字，并不消费前面的 `effects`
- 没有模拟结果时，`castHitEffects` 自身直接返回空 Map，所以后面的定义预览也拿不到效果内容
- 该 computed 在组件中的唯一消费者就是这一处读取；没有 provide、export 或其他消费者。其调用链只构造投影，不写入战斗或编辑状态

因此这里存在可以隔离的死工作，不能因为执行了就认为它贡献了显示内容。`castHitEffects` 又依赖整个 `scenario` / `viewModel`，会在移动落点时遍历全部兼容技能，再逐个过滤伤害、附着和反应回执。

[命中读取诊断](../../tools/performance/ui-hit-projection-audit.test.ts)使用 Vue SFC 解析器与 TypeScript AST 提取实际 computed、`castHitMarkers` 及三个标题函数，在隔离作用域内仅把旧效果 computed 的读取值换成空 Map。生产文件不改写；不是按源码字符串断言实现写法，也没有用一个手写的近似命中函数冒充实际入口。Vue refs、正式页面模型和实际命中投影照常执行，像素变换固定为单位比例。

六轴各检查已发布结果、旧结果配新落点、尚无结果、自定义匿名/条件图的无结果及已发布结果，共 30 个场景；每个场景比较初始与再移动一帧后的完整命中标记数据，包括身份、实际执行帧、位置、强制暴击、追加命中、层叠和中文提示。隔离前后全部相等。这里验证的是传给组件的标记数据，**不是浏览器截图或实际视觉回归**。

在有结果的每个状态中，六轴两次读取累计 `projectHitEffectsByCast` 从 612 次降为 0；单轴为 34–208 次。无结果路径原本就是 0。第一次完整读取还会拉起旧效果路径专用的一份 `hitReceipts` 预处理，不能只计逐技能函数。

一次离线阶段诊断中，旧效果 computed 的两次读取累计约 1.6–9.5 ms，逐技能函数只是其中约 0.1–1.7 ms；额外回执预处理包含在 computed 时间内。不要叠加这些包含项，也不要把隔离前后顺序运行的墙钟差当作配对性能收益。这个量级证明可避免工作，却不足以单独解释用户感受到的大幅刷新下降。

### 更宽的更新范围

1. `viewModel` 的输入是整个 `scenario.value`。`projectTimelineEditor` 每次映射四条轨道、重建技能库、逐技能解析定义/图命中点、生成新的技能与轨道模型。在上述场景仅移动一个 placement、保留未动轨道的文档引用后，四条轨道的模型引用仍全部改变。一个 computed 只计算一次并不代表它只处理发生变化的那个块
2. 技能模板直接遍历全部 `track.skillCasts`，没有按视口筛掉屏幕外技能。每次父模板求值，`castHitMarkers` 在该轨道两次 `.find`，随后生成新命中数组；`cooldownBarsForCast` / `enhancementBarsForCast` 对全局段列表做 filter/map，时间膨胀段也生成新数组。稳定 `key` 保留组件实例，不会让这些数组保持引用相等。它们是明确的更新范围和分配候选，但本研究没有统计实际组件更新次数
3. `skillEnhancementSegments` 同时依赖当前 `viewModel` 与已经发布的回执，即使 Worker 未产生新结果，场景变化也会使其遍历旧回执。纯技能几何变更与效果事实投影的失效边界值得分开核对
4. `TimelineResourceCurves` 的光标读数按序扫描曲线点；SP 光标随拖动更新。但路径几何有单独 `curvePaths` computed，光标没有作为其输入，不应宣称每个 pointermove 都重建完整 SVG 路径
5. 指针命中路径读取 `elementFromPoint` 与轨道 `getBoundingClientRect`，自动滚动读写滚动位置。是否触发强制布局取决于实际浏览器当时的脏布局状态，源码里有几何读取不等于已经测得 layout thrashing

离线提取入口还观察到：六轴两次页面模型构建约 1.8–18.6 ms，当前正式命中 occurrence 投影一次约 4.4–26.6 ms。后者基于 `publishedReceiptEntries` 缓存，在本诊断中严格保留页面的“发布投影 + 当前兼容过滤”两层 computed，不能把它误算成每次场景移动都重做。以上都不是完整前端刷新预算。

### 已排除的简单解释

- 查到的 deep watchers 监听显示设置、面板折叠与权重，不是对整个场景或完整回执做 deep watch
- 战斗日志使用打开/手动刷新时固定的快照，普通模拟发布只标 dirty，不会自动重建整张日志表
- 曲线使用 SVG，正常时间轴资源监控不是每次拖动调用 ECharts；ECharts 位于独立伤害分析对话框
- 默认模拟延迟仍为 0。finally 中可立即续跑本地同步段，但普通本地指针事件不能在同步内核里并发改变输入；不能仅凭微任务链就断言普通拖动必然饿死绘制

### 下一次浏览器记录要回答什么

需要在同一手势上配对输入、开始模拟、服务完成、结果发布、组件更新和可见绘制，并记录长任务、样式、布局与 paint；分别观察 Worker 和手势固定本地分支。重点查实际周期的长尾，不再把 18 ms 平均量级硬解释成明显的体感落差。

性能面板的 latest 是最近完成样本，在下一轮运行中保持原值，且样本没有后端、场景或请求 ID；规划路径的模拟样本也来自同一订阅。屏幕显示 250 ms 本身不能证明当前每一轮都只运行了 250 ms。浏览器记录还应固定缩放、可见图层、面板、轴和硬件，并检查性能面板样本究竟对应哪次请求。

若使用 rAF 辅助标记，只能称为绘制机会；`nextTick` 只保证 Vue 更新队列完成，两者都不能冒充已经发生的真实 paint。没有取得浏览器轨迹之前，不宣布前端已经找到耗时主因。

### 可直接执行的浏览器采集步骤

1. 在能访问预览的浏览器运行同一提交的应用，导入同一公开夹具。固定窗口大小、缩放、可见图层和右侧工具面板，记录浏览器版本、CPU 节流设置及操作系统。先等首次模拟完成；不要将首次模块加载混入稳定拖动样本
2. 打开开发者工具 Performance 面板，开启截图并保留主线程与 Worker 轨道。先录一次无额外探针的基线：连续拖同一个技能至少数秒、松手，再停止记录。保留拖动中和松手后的边界，避免把松手重复计算混入拖动刷新周期
3. 在 Main 火焰图中分别检查 pointer 处理、`runSimulation` Promise 恢复、Vue 更新、Recalculate Style、Layout 和 Paint；在 Worker 轨道检查计算是否连续。关注最慢的一两段间隙及长任务，不只看平均值。截图/帧轨道用于判断可见变化是否真的发生，不能仅数服务调用
4. 若需要定位“发布→Vue”的边界，可在 Sources 的 `useScenarioSimulation` 中，`publishedState.value` 赋值后的 `lastPublishedRunId = runId` 行设置条件断点表达式 `(performance.mark('endaxis:published:' + runId), false)`。它只生成 User Timing 标记，不暂停执行，也不改仓库文件。另录短样本；结束后删除断点，并与无探针基线对照，记录调试探针本身可能造成的开销
5. 导出 Performance trace，连同夹具 ID、移动技能 ID、拖动前后帧、可见图层和性能面板截图一起保存。trace 可能包含页面/环境信息，先本地检查后再决定是否共享；不要自动提交进仓库
6. 先回答：每次完整结果是否都发布？发布是否挤在一起？Vue/布局/paint 是否占了缺失时间？还是当前长任务尚未结束，而面板仍显示上一条 250 ms？只有这些时间边界对齐后，才选择细分缓存、减少组件更新或调整调度

这里没有承诺探针可提供精确 paint 时间；仍以浏览器 Performance 的实际记录为准。当前受限环境未完成上述真实浏览器采集。

### 未实施的最小修复候选

移除命中标记路径中没有被消费的 `castHitEffects` 读取及其 computed，在保留 `hitOccurrences` 和无结果定义预览的前提下，删除已经证明无用的投影链。现有诊断只在隔离作用域验证这个候选，没有提交生产修复。若落实，应保留上述五类标记数据检查，并补浏览器命中点与详情的实际交互验收；这项局部清理不能承诺解决整体拖动刷新问题。

## 优化优先级与验收门槛

1. **先去掉松手事务造成的原位置瞬时模拟**。保持预览与已提交文档职责、单次撤销和失败回滚，但避免把历史基准恢复广播成一个需模拟的中间状态。验收两类松手：最后预览已完成、最后预览仍在途；另测取消、失败、连续新手势和撤销。不能用全局延迟碰巧掩盖事务问题
2. **独立评估本地主线程后端选择**。默认 200 ms 允许明显超过一帧的同步 CPU 段，且 sample 只覆盖模拟服务推进/投影，不含请求去代理、结构化克隆、结果恢复、Vue 更新或 paint。不能据此宣称“200 ms 内拖动不卡”。需要真实浏览器 Event Timing/long task/rAF 证据后再选预算或策略；不先把所有位置做运行时抢占
3. **收窄模拟失效与显示捕获依赖**。把纯编辑显示变化与战斗输入变化分开，并避免相同 `run` 仅重新绑定场景时无条件全量捕获。要求验证种子、禁用、构筑、技能参数、定义 revision、继承等输入仍确实失效。不能简单深 JSON 比较或按干员 ID 特判
4. **再决定是否处理不消费结果的在途任务**。重置/取消时已开始任务仍会完成和传输；主动取消 active Promise 后，客户端仍可能恢复这个最终不消费的结果。可以先研究“已明确丢弃时跳过接收端恢复”，不要把一般 stale 完整预览也删掉。真正运行时协作取消需要可中断推进/让出与缓存寿命设计；频繁 terminate 会损失定义、编译和前缀复用，必须单独测吞吐与首个有效结果时间

当前没有证明前缀恢复、伤害内核或同方案旧预览本身是浪费；也没有浏览器 paint 结论。本研究优先给出可重复的工作数量和触发原因，保留原有结果、顺序、恢复语义。
