# 节点数量对模拟成本的影响

**结论：真实成本更接近“实例数 × 被访问的可达节点 × 生命周期次数”，但三者也不能单独预测总耗时。静态图大小不是运行指令数。当前没有保留任何生产优化。**

最显著的例子是庄佩梨杰：暖态实际触及的编译目录只有452个动作节点，却访问94,505次；提决佩洁有1,113个，访问60,420次但完整服务仍更慢。电队中仅4个节点的一张图就占45,616次访问（48.3%）。节点数量确实能放大遍历/分配，但应先定位是哪一张图、哪种生命周期、是否反复创建实例。

## 口径与方法

- 冻结当前版本 `41396fd94850dd61ab93e6fa483b9f344312a612`，生产逻辑与先前普通模式发布版本相同。本研究没有改 `src/`、数据、锁文件或运行规则
- 六份已提交公开夹具、首个独立方案、原结束线；正式 `createScenarioSimulationService(repository, false, 'standard')`，逐次清服务缓存，不复用切面；不可变定义缓存保留正常寿命。不运行战斗日志详细模式，不检查伤害值差异
- 计数独立于性能计时：Vite仅在诊断bundle转换源码，加聚合计数，不记录完整轨迹。各轴新进程运行冷首跑与第二次完整模拟。下表为第二次；除冷编译节点与编译目录创建量外，两次运行的动态计数一致
- 性能对照完全关闭源码转换，在六轴正序、反序各跑一个独立进程；每进程冷首跑1次、热身4次、测量16次。表中为两进程完整服务暖态中位数，单位ms；不是逐节点耗时，不是浏览器FPS。进程内重复不等于独立样本，未控制宿主调度/频率，未宣称尾延迟或因果相关
- 所有12个无插桩进程的252次完整运行，与计数进程完整Worker输出及有序回执SHA-256一致；输入不变、终帧一致、无恢复缓存命中。诊断保留对象用于聚合，**其耗时/内存不能当生产性能或分配采样**
- 计数以编译程序对象身份 + 节点ID去重；不同等级/上下文编译目录分别计算。动作节点不包括dataNodes表达式、条件树叶子或机器指令。宏/资源调用若出现仍保留共享目录身份，不凭展开路径重复算静态节点；本组暖态目录中callMacro/callResource均为0

### 电队：4个节点为什么会产生4.56万次访问

`src/data/operators/zhuang-fangyi.generated.ts` 的 `zhuangFangyiBuff5ActionGraph` 只有4个动作节点：查询主人生成的青霆剑实体（`abilityentity_chr_0030_zhuangfy_normal_skill_sword`）、条件判断、更新被动UI、写黑板。条件 `contextTargetCountCompare >= 0` 同时将数量写入 `swordsNum`，随后更新被动UI及 `EntityBB_SwordNum`。对应Buff `triggerIntervalSeconds: 0.03`、无限触发次数，实测触发3,801次。

每个节点：Execute 3,801次 + End 3,801次 + Reset 3,802次 = 11,404次；4个合计45,616次。每个binding只创建1次，后续命中11,403次。因此这是小图反复生命周期遍历，不能靠“缓存binding”解决，也不能因为普通回执省略UI记录就删掉实体查询和黑板更新。单个实例内节点访问直方图的最大值也是11,404；完整分布保留在原始证据。

## 控制缩放实验：什么时候节点数真会使成本增长

使用真实编译器和ActionGraphExecution，叶子为确定性空操作host；独立生产SSR进程，计数与计时分开，26种工况、正反两轮，每进程热身5次+测量20次。**这是合成解释器实验，不是修改真实战斗后的服务加速率。**

- 不可达源节点10→5,000：未缓存定义准备约0.057–0.066ms→20.665–20.713ms；实际可达10节点、10,000次Tick callback不变，Tick在所有规模0.468–0.622ms，没有随源节点数成比例增长
- 即使compileAll保留5,000个已编译节点，可达链仍为10、只绑定10。静态目录大并不自动导致每次遍历全部节点
- 可达节点100→1,000→5,000，每个100次Tick：约0.481–0.482→6.85–7.32→47.26–48.40ms；运行遍历规模确实增长
- 5,000节点×100Tick，四种状态均有500,000次next边Map.get：从未启动9.89–11.33ms；Reset已绑定但未启动35.38–37.68ms；已End37.59–38.82ms；正常启动47.26–48.40ms。前三种没有host Tick callback，但仍有图扫描。它证明遍历与binding状态有成本，**不证明真实战斗允许停止Tick或删状态**
- 同为500,000次callback，100节点×5,000Tick约24.75–24.83ms，而5,000节点×100Tick约47.26–48.40ms。即使动态访问总量相同，节点/实例分布和常数成本也不同，不能把次数当统一CPU单位

## 下一步：只提出可验证候选，不提前宣布优化

优先验证 **未绑定pending节点的Reset是否能延后实例化**，范围限定能证明无Reset副作用的节点/入口；保留已有实例Reset、分支选择、监听解绑、动态目标、作用域、同步重入和检查点格式/恢复语义。先做少量定向正确性证据，再以稠密与别汤赛决相反顺序完整服务筛选；有稳定收益才扩到六轴及完整切面验收。不能简单把 `entries(true,false)` 改成false，或删除全部未执行binding。

第二候选是证明静态叶子无Tick语义后减少空端口调用；仍须保留生命周期状态更新和canExecute实时检查。电队的高频Buff小图则适合单独微测生命周期调度成本，但不能修改0.03秒规则、删被动UI伴随黑板写入或擅自改成事件触发。如进一步探索事件驱动剑数，须先审计生成/销毁/结束/归属变化、恢复、同帧系统顺序以及原轮询观察时间点，证明两种观察时序相等。

六轴间的节点数与耗时关系只作描述：帧数、技能、Buff、实体、命中和输出均不同。这里没有分配字节或当前CPU抽样归因，也未推导任何“预计可提速百分比”；旧热点百分比不能直接搬到本轮。

无插桩控制与最终诊断工具的来源hash不同，不能混称同一工具快照：`graph-node-diagnostics.mjs`、`graph-node-diagnostics-runner.ts` 仅经过Prettier格式化；`graph-node-instrumentation.mjs`、`graph-node-probe.ts` 还加入了按生命周期分类的binding创建、实例节点访问分布、生命周期参与去重、基类空Tick与至少Execute一次的binding去重计数，属于诊断功能变化。控制bundle在这些增加前构建，Vite插件数组为空，生产源码没有计数调用；helper的reset在服务模拟和服务计时前，控制不调用snapshot。因此新增诊断口径不影响已测量的无插桩生产执行。两个阶段的实际来源hash都原样保留，所有控制输出/回执已与最终诊断结果交叉核对。
