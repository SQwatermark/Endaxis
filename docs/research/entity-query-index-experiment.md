# 通用实体查询索引与 Tick 裁剪实验

**结论：已试验按 owner/type 的派生索引，本轮不保留生产优化。** 稠密轴、电队的完整服务两轮方向不一致，不能由节点访问次数推断查找主导成本。候选源码已撤回，只有本文及可复现证据保留。独立的初次 Reset 延迟对象实验见[配套报告](lazy-initial-reset-experiment.md)。

## 候选与正确性边界

基线 `41396fd94850dd61ab93e6fa483b9f344312a612`，生产逻辑为 `16bd46e09adff8f581cbe5f28956eaf6bafcfe44`。候选仅改逻辑实体目录：维护 owner 的插入有序集合与各 type 的集合；单类型查询走窄桶，无类型/多类型查询保留 owner 顺序并执行原筛选。每次查询仍生成新结果数组和引用，不缓存最终值，不改查询频率，不按角色或技能 ID 特判。

索引在插入主目录后、spawned/子技能回调前建立；finished hook 和子运行时清理时实体仍可被查到；在主目录删除后、reset callback 前删除索引。kill 不删除，死亡但尚未回收实体仍可见。恢复按保存 Map 的迭代顺序重建派生索引，不新增序列化字段。

不能直接拼接多个类型桶：原始跨类型生成顺序会丢失。也不能按 instanceId 排序替代插入顺序：可注入的 ID 分配器不承诺单调。owner、type、sourceSkillCastId 为不可变实体身份，查询中的 sourceSkillCastId 仍先校验，再匹配。

53 个原生 Endaxis 定向测试通过（实体目录 25、实体操作 28）。新增测试覆盖：多主人、空/单/多/重复类型、来源 cast、未知 owner 的非法参数、非单调 ID、删除后重建桶、死亡延迟、生成/结束/Reset 回调可见性、恢复后顺序；80 轮混合生命周期操作后以原目录扫描为 oracle 比较 5,120 个查询。没有引入旧版 CombatSpec。

| 庄佩梨杰 |    7,656 |     21,438 |     21,052 |         19,030 |   19,030 |       10 |

电队平均每次查询仅扫描 2.80 个实体，且大多数就是返回对象。类型筛选后候选数是全部查询按原过滤规则计数，不等于候选索引实际访问数（多类型查询仍扫描 owner 桶）。即使理想地只访问返回实体，也仅省约 11.2% 的扫描条目，且不会消除返回引用分配、条件求值、黑板写入或生命周期枚举。4 节点小图的 45,616 次生命周期访问不能解释成 45,616 次昂贵查找。

## 为什么本轮没有静态删除空 Tick 节点

“提前知道某阶段无效果即可跳过”的原则成立，但这里必须证明整个协议无效果，不能只看 callback。用真实 `actionSequenceExecution.ts` 及其依赖在内存转译运行的三项断言全部通过：

1. 两个已开始节点，第一个 Tick callback 为空，但 `canExecute` 每次切换结果。原路径 gate 调用两次、后继节点收到 Tick；删第一个空节点后 gate 只调用一次，后继不再收到 Tick。自定义宿主允许这种实时读取，不能用静态 action.kind 擅自强化为纯函数。
2. 单个空 callback 首次 Tick 仍把 `started` 写成 `ticking`，序列化的中间状态改变。
3. 开始时只有第一个节点 active；它在 Tick 中同步 Reset→Execute 完整序列，成功激活原 pending 后继。原遍历继续调用后继 Tick，入口冻结的 active 快照漏掉它，两者最终 lifecycle 不同。回调使用公开生命周期算法，没有直接篡改状态。

因此不能按“叶子 tick 是基类空实现”删除整个枚举，也不能每帧拍一次 active 快照就代替原链。inline guard/宏包装本身即使为空，子体仍有意义；自定义 `bindOperation` 也可以返回带 Tick 的操作。

### 同帧的遍历顺序与集合不是同一个保证

同一入口的 `next` 链与内联子体有稳定的**相对顺序**；这不表示同一帧每个阶段都会访问相同节点集合，也不表示可以提前冻结分支：

- Execute 使用 `entries(true, true)`，允许按需建立 binding；条件结果、false 返回以及同步 closed 可提前停止，真正执行的分支由当时状态决定
- Tick/End 使用 `entries(false, false)`，只枚举既有 binding/内联子体；Tick 按当下生命周期和执行许可门控，End 将尚未开始的既有项也写成 ended
- Reset 使用 `entries(true, false)`，会创建此前不存在的 binding；条件/Switch 的 Reset 协议可展开未选分支以完成准备，不能套用上一阶段已选集合
- 同一帧内黑板、宿主许可、目标、分支选择和生命周期可以变化；同步回调可 Reset/Execute/End。因此优化计划必须保留原相对顺序并在访问时正确响应变化，不能用“同帧”推导“同一状态快照”

可统一排除的是在访问当下仍 pending/ended、结果为 false 或未许可的项。真正减少它们的访问需要**动态有序索引**，保留原先后顺序、实时后继激活、独立重入游标、Reset/End 更新及恢复重建。这个方向不因本次反例被否定，但比本轮静态能力小改动更广；在精确执行/中间态/恢复一致、不增加多层特判的约束下，本轮不强行落地，也没有把减少空 callback 当作减少节点访问宣称收益。
