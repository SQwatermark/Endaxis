# 动作程序只读检查：三项未保留实验

**结论：三项候选均未建立稳定的完整服务提速，全部撤回。** 本轮不保留生产代码或新增缓存，仅记录负面/不确定结果，避免后续重复把“少建对象”视作已经提速。

## 基线与筛选方法

基线是普通回执缺省规则的冻结树 `2da31e3e957db0d90844355e341551c5b12b8993`。实际发布的代码提交为 `16bd46e09adff8f581cbe5f28956eaf6bafcfe44`；两者 `src/`、`packages/`、`tools/`、`tests/` 和锁文件差异为空，仅研究文档/证据发布形式不同。实验使用独立基线与候选目录，不改发布中的共享工作区；机器摘要保留冻结快照的本地提交、生产来源指纹和候选 diff SHA-256，不把本地快照提交冒充远端提交。

范围限定为前期分配热点较明显的稠密轴 `6aba2a13c9fb961339acd766` 与曾在图适配器实验退化的别汤赛决轴 `6aaa98afecff634734db32cf`。使用已提交的同一公开夹具，不调整位置、结束线、伤害数值或游戏定义；不是六轴最终验收，也不借旧版伤害差异解释当前耗时。

每项候选进行两个相反顺序的独立进程对照：

1. 稠密基线 → 候选；别汤赛决候选 → 基线
2. 别汤赛决基线 → 候选；稠密候选 → 基线

每进程冷首跑一次、热身五次、正式二十次；三项合计 24 个进程、624 次模拟，其中正式测量 480 次。重型任务串行，无采样、无强制 GC。均使用 `verify-optional-execution-receipts-runner.ts` 的正式服务入口，显式 `receiptDetail: 'standard'`、`verify: false`，逐次清空结果缓存且禁用切面复用；不可变定义缓存保留正常寿命。首次完整结果保留及回合间 `structuredClone` 与该 runner 原实现一致，复制/哈希在服务计时外。

本地驱动对两个源码根分别做生产 SSR 构建，检查 bundle 没有混入另一根的 `src/`，并在结束时检查源码指纹不变。每轮输入/方案/数据修订、完整 Worker 结果及有序回执 SHA-256 全部一致。逐次计时、冷首跑、热身、p95、CPU、复制成本与来源在[机器摘要](action-program-inspection-experiments.json.gz)；原始 bundle、二进制和未保留补丁留在本机，不发布。

## 候选与结果

下表是完整服务暖态中位数，单位 ms；每个单元格为同一对照轮的基线 → 候选。

| 候选                               |    稠密第一轮 |    稠密反向轮 | 别汤赛决第一轮 | 别汤赛决反向轮 |
| ---------------------------------- | ------------: | ------------: | -------------: | -------------: |
| 顺序 visitor，省掉步骤数组         | 338.1 → 325.0 | 339.2 → 341.8 |  244.1 → 240.6 |  245.5 → 205.9 |
| 直接访问编译节点，再省控制对象复制 | 350.0 → 343.6 | 328.4 → 335.6 |  230.1 → 220.7 |  220.8 → 221.4 |
| 延后诊断路径字符串拼接             | 336.2 → 324.6 | 324.2 → 324.2 |  215.1 → 218.1 |  220.4 → 218.9 |

### 1. 省掉顺序数组

增加同步只读 visitor，宏和资源仍按原顺序展开，索引连续；控制分支仍使用原来的重新绑定对象。标准兼容预检与同步伤害修正条件验证改为消费 visitor，测试/检查用途的 `rootActionSteps` 仍返回数组。一次节点查询代替原循环两次查询，没有改变运行时图执行。

50 项定向测试通过，包含宏/资源顺序、控制子入口及 `callSite`、缺省/显式 scope、空序列、重入索引与异常传播。稠密第一轮下降约 3.9%，反向轮却高约 0.8%；别汤赛决两轮收益幅度相差很大。不能选择其中最快的一轮宣称稳定提速，撤回。

### 2. 直接读取编译节点

在第一项之外取消控制动作、分支数组与参数对象的复制；visitor 传原始编译节点及所属入口，检查器仅在递归时绑定子入口。保留宏/资源展开顺序与完整检查策略，不缓存 flags、截止帧、定义目录或“已通过”。`rootActionSteps` 保持原实现，作为独立对照。

50 项定向测试通过，包括节点身份、延后编译新入口、入口路径、重入和失败后再次遍历。稠密两轮约 -1.8% / +2.2%，别汤赛决约 -4.1% / +0.25%。没有稳定的总耗时收益，撤回。

### 3. 按需构造诊断路径

单独回到原始数组遍历，只在报告错误或递归检查时拼接步骤路径；支持的普通叶节点不预先拼接字符串。保持嵌套索引与错误顺序，未缓存结构或检查结果。

46 项既有定向测试通过。稠密第一轮下降约 3.5%，反向轮近乎相同；别汤赛决约 +1.4% / -0.7%。未证明改善，撤回。

## 如何解释，以及没有验收什么

- 这是无采样的相邻进程点估计；20 次进程内重复不是 20 个独立进程。p95 是排序样本，不是稳定尾延迟保证
- 观察到进程间变化，但没有控制宿主调度、频率或租户，也没有去优化/inline-cache 证据，因此不能认定差异来自宿主、GC 或 JIT 中的任何一个原因
- 分配热点不等于相同比例的可消除 CPU。既有普通模式 CPU 样本中，`rootActionSteps` self 约 1.19–1.28%，兼容检查含后代约 2.70–2.81%；后者不是都能靠消除物化省掉
- 三项均未通过性能筛选，不进入完整状态、逐帧 HUD、被动 UI、Buff 曲线、恢复分支及六轴验收；也没有为撤回的生产候选运行全量类型检查、全套测试或构建。不能把输出哈希相同写成完整切面验收通过
- 既有伊冯 `missing projectile reset handler 0` 问题本轮未触及，两条筛选轴没有运行恢复探针。本轮也不宣称浏览器 UI、旧版对照或内存占用改善
- 最终 `src/`、`packages/`、`tools/` 和测试均与基线一致；报告 JSON/Markdown 格式检查及 `git diff --check` 通过

## 下一项有证据支撑的方向

优先验证**单次伤害快照的批量属性读取**，而不是立即加持久缓存。既有普通模式稠密 CPU 的两个有限样本里，`readCombatAttribute` self 约 3.53% / 3.04%；源码仍为：

- `staticPlayerDamageSnapshots.ts:captureDamageScales` 逐个读取 31 个伤害区间属性
- `combatAttributeExecution.ts:readCombatAttribute` 每次对已定义属性扫描整个注册 modifiers 数组，先过滤属性与来源，再按注册顺序累加八槽
- 当前 `CombatAttributeSet.runtimeState` 暴露可变状态，恢复也重建数据图；不能仅按对象身份缓存最终值，或假定所有外部变化都会触发新增缓存的失效逻辑

可测假设是：仅在一次同步快照内批量读取所需属性，避免 31 次重复扫描无关 modifiers，同时保持每个属性内部的浮点累计顺序、来源过滤、原生 clamp、Armed/final 阶段、附加修正及完整来源明细。不跨命中复用最终值，不修改持久状态格式。

**实现前的证据缺口：** 上述样本来自[可选回执研究](optional-execution-receipts.md)的显式普通模式，早于最后的缺省/UI 范围修正；需在已发布普通模式重采稠密与电队/别汤赛决 CPU，并用计时外/独立探针统计属性读取调用点、modifiers 长度分布、有效与无关比较次数、读写比例，确认这些重复扫描在真实输入上值得换成批量聚合。空/短数组可能让新增 Map 或聚合器更贵，先做有界对照，不能由渐近复杂度直接决定保留。

图执行 `#binding` 的既有普通模式 self 约 3.81–4.83%，`#entries` 约 1.81–3.01%，也是候选，但当前已经缓存实例内 binding。尚未区分新实例创建、真实 cache miss 与查找开销；在拿到分解前，不重做已失败的 host/adapter 常驻复用。Buff tick 的约 12% inclusive 包含合法的下游执行，同样不能全当成查找开销。
