# Endaxis Next 架构整改路线图

本文把当前架构审查发现的问题，按产品建设顺序重新排列。它用于约束近期开发节奏，避免在编辑模型和应用边界尚未稳定时继续扩展模拟、投影或技能实例编辑。

## 建设优先级

1. 干员、武器、装备、敌人实例的选择和编辑。
2. 时间轴的编辑和调整。
3. 完整时间线模拟、事件记录、资源监控和战斗日志。
4. 投影和显示。

技能实例编辑暂缓。第一阶段只允许放置目录技能并调整位置，不建设倍率、步骤、命中、调度序列等内部内容的编辑界面。

## 当前判断

Next 的核心方向可以保留：项目文档、只读目录、编译产物、运行时和投影已经形成基本分层，核心也没有发现实际的文件循环依赖。但是当前边界仍停留在“概念上分层、实现上互相知道较多”的阶段；继续直接在 `NextTimelineEditor.vue` 和现有核心类型上堆功能，会明显增加后续迁移和理解成本。

当前最需要整改的不是战斗规则本身，而是编辑状态所有权、持久化边界、目录版本和应用装配入口。

## 第一阶段：实例选择和编辑

### 必须先完成

#### 1. 建立编辑会话

新增独立的编辑会话，统一持有：

- 当前项目和场景。
- 当前轨道、当前面板和当前选择。
- 显式命令提交入口。
- 撤销、重做和脏状态所需的事务边界。
- 文档身份分配器。

Vue 组件只负责调用会话命令和渲染视图模型。禁止继续让 `NextTimelineEditor.vue` 同时承担示例项目创建、文档修改、选择状态、弹窗协调和时间轴交互。

#### 2. 完整定义四类实例

| 实例 | 目录身份               | 用户配置                                   | 第一阶段要求                 |
| ---- | ---------------------- | ------------------------------------------ | ---------------------------- |
| 干员 | `operatorSlug`         | 等级、突破、潜能、信赖、技能等级、天赋状态 | 选择、替换、清除、编辑       |
| 武器 | `weaponSlug`           | 等级、突破、潜能、词条等级                 | 按干员武器类型筛选并编辑     |
| 装备 | `gearSlug`             | 槽位、精锻等级                             | 四槽独立选择和编辑           |
| 敌人 | `enemyId` 或自定义身份 | 等级、生命、防御、失衡、处决倍率、抗性     | 目录选择、自定义、覆盖默认值 |

四类实例使用同一种所有权规则：目录保存版本化默认事实，项目只保存目录引用、用户输入以及明确由用户接管的覆盖值。

#### 3. 补齐目录版本协议

`GameDataRepository` 必须暴露稳定的目录版本，并补齐敌人查询与枚举能力。打开项目时必须检查 `project.gameDataRevision` 与当前目录版本的关系，由应用层决定直接打开、迁移或报告不兼容，不能让编译器静默使用另一版目录。

#### 4. 集中旧版 UI 适配

第一阶段允许复用旧版的视觉表现、富文本、本地化资源和范围工具，但必须通过少量明确的 Next UI Adapter 访问。禁止选择器和编辑弹窗继续各自散落导入旧版 `@/data`、`@/utils` 和类型模块。

这项整改不要求重写旧组件视觉，只收拢依赖方向，为以后移除旧入口保留明确边界。

### 第一阶段暂不处理

- 技能命中、倍率、步骤和调度序列编辑。
- 完整战斗模拟。
- 资源曲线、伤害分析和合法性投影。
- 为性能引入复杂缓存。

### 第一阶段验收条件

1. 四类实例均可通过目录选择、替换、清除和编辑。
2. 所有修改通过显式命令进入项目文档，组件不直接深层修改文档。
3. 相同项目与目录版本能稳定恢复相同配置。
4. 项目 JSON 不包含名称、面板、模拟结果或 UI 临时状态。
5. 旧版依赖只出现在明确的 UI Adapter 中。
6. 编辑会话具备后续接入撤销、重做的稳定事务边界。

## 第二阶段：时间轴编辑

在第一阶段的编辑会话上实现：

- 技能库到时间轴的放置。
- 移动、复制、删除、多选、框选和轨道切换。
- 缩放、平移、吸附和键盘作用域。
- 显式事务历史，保证一次用户意图对应一次历史记录。
- 稳定端点身份和连接关系。

这一阶段要先解决 `SkillCastDocument` 的持久化边界。当前一次放置会复制完整编译步骤和调度序列，和“项目只保存稳定用户输入”的原则冲突。由于技能实例编辑暂缓，优先方案应是保存目录身份、位置和少量块级覆盖；完整动作程序加载时重新编译。

## 第三阶段：完整模拟和事实记录

### 先整改边界

- 把编译器输出与运行时输入协议提到中立的核心契约模块，消除运行时对编译器实现类型的反向依赖。
- 建立唯一的场景解析和运行时装配根，禁止每个调用者自行拼装资源、Buff、属性和事件系统。
- 明确同帧注册顺序和阶段顺序，并以集成测试固定行为。
- 选择唯一的应用编排方式；当前直接调用入口和泛型 `SimulationPipeline` 不应长期并存为两套主流程。

### 交付内容

- 从用户操作序列执行完整时间线。
- 输出仅追加的事实回执。
- 记录资源变化、伤害、失衡、状态、事件和技能生命周期。
- 提供结构化战斗日志，不在运行时生成本地化文本。

## 第四阶段：投影和显示

所有曲线、警告、状态条、伤害统计和分析结果必须从项目稳定输入与事实回执派生。投影层不得重新实现战斗规则，也不得反向修改项目或运行时。

缓存键由统一的版本身份组成，至少包含项目修订、游戏目录版本、机制版本和模拟参数；不能由调用者任意拼接字符串后自行保证正确性。

## 跨阶段工程整改

### 近期完成

- 收窄 `src/next/core/index.ts` 和 `src/next/index.ts` 的公开 API，避免把全部内部实现承诺为稳定接口。
- 拆分 `operatorDefinition.ts` 中目录 DSL、条件协议和战斗步骤协议，降低中心类型文件的改动扩散。
- 让运行时校验与 TypeScript 类型来自同一结构来源，或至少按领域拆分并建立同步测试；当前大型手写校验器容易漂移。
- 更新架构图和功能矩阵，确保文档不再描述已经过时的实现状态。

### 可以后置

- 生成文件体积和类型检查性能优化。
- 模拟流水线缓存和 Worker 化。
- 活动机制的完整目录覆盖。
- 技能实例内部编辑器。

## 执行纪律

- 每次整改只改变一个边界，并配套迁移或回归测试。
- 不把未提交的生成器、干员数据和旧版数据改动混入架构整改提交。
- 新功能必须先判断属于四个阶段中的哪一层；未到阶段的能力只保留接口，不提前实现。
- 代码清晰优先于抽象数量。只有当一个抽象明确减少状态真相、依赖方向或重复协议时才引入。
