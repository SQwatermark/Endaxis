# 伤害、资源与状态显示

伤害不是一个公式调用。一次命中需要读取当前状态、发布前后事件、计算数值、写入生命或失衡，
最后记录结果。各环节顺序会影响同一次命中，不能仅凭整轴总伤害接近判断正确。

## 伤害执行

[伤害动作执行器](../../src/core/combat/runtime/playerDamageOperationExecutor.ts) 组织动作执行，
[伤害模块](../../src/core/combat/damage) 处理公式和具体结算。
公式接收明确数值，不读取项目、语言、Buff容器或全局随机数。
运行环境负责从本场实体状态解析属性、修正、目标和随机输入。

普通伤害、处决、生命汲取等分支有不同规则，不能把它们强行换成同一攻击倍率。
公式要求的float32舍入、乘算次序、筛选范围和乘区必须保留。
伤害前事件可能修改待结算对象；输出侧与承受侧通知不能合并或重复执行。

伤害、实际扣血、失衡和附着是相关但不同的结果。不要看到一个伤害事件就额外结算一次伤害，
也不要从生命变化反推出完整命中语义。随机输入必须来自明确来源；缺少状态时不能猜种子，
测试用的固定样本耗尽后应报错。

## 状态只维护一份

同一场战斗中，同一实体的Buff查询、技能动作和伤害修正读取同一个Buff运行实例。
生命与失衡也由明确的账本维护，装配层和显示层不能各保存一份可变副本。

SP属于全队，终结技能量属于干员。检查、支付、返还和恢复分别记录，
不能把主控技力恢复限制套到所有资源上。费用帧、冷却和技能寿命见 [技能说明](skills.md)。

Buff、语义状态、元素附着和定时标记有不同用途。元素附着需要按当前实例、层数和反应顺序处理，
不只是添加一个颜色标签。状态工厂、包装Buff和最终状态也应按原生关系保留。
具体规则以版本化定义及研究证据为准，不在架构页复制旧版本的覆盖数量。

## 模拟入口与不支持的行为

[标准模拟入口](../../src/application/runStandardPlayerDamageScenarioSimulation.ts) 准备环境并检查能力，
[场景执行入口](../../src/application/runScenarioSimulation.ts) 组织编译后执行和结果。
便捷入口不能另建一套时钟、资源结算或显示计算。

[兼容性检查](../../src/core/combat/runtime/standardPlayerDamageCompatibility.ts) 应覆盖本次程序需要的能力。
未知行为明确报告，不能用空回调、默认倍率或静默跳过伪装支持。
条件分支、Buff引用、装备响应和实体子程序都需要检查其实际依赖；结构可解析不等于运行环境支持。

## 从记录生成显示

[结果投影](../../src/core/projection) 将同一组记录转换为曲线、诊断、Buff条和命中详情。
隐藏内部Buff只改变显示，不删除它的模拟效果。Buff正常结束与容器释放均可关闭状态条，
但不能因此发布相同的战斗通知。

重复执行的伤害步骤需要保留每次发生帧。定义中的步骤身份与某次运行中的命中身份分别处理；
当前连接保存步骤key，不把某一轮模拟实例写进存档。
附着刷新、叠层、转换和后续状态按实例及来源关系显示，不能仅凭名称或重叠区间拼接。

Buff 动作造成的伤害自动记录执行它的 Buff ID、所属实体和实例编号。
例如洛茜的爪印斫痕持续伤害，命中点属于目标身上的爪印斫痕持续条，不重复挂在洛茜技能块上。
攻击属性仍取自洛茜，回执保留原施法来源；不需要在干员生成配置里逐项指定归属。
Buff 显示名称由界面按 ID 查找翻译键，名称配置不参与伤害计算。
干员专属名称放在该干员的 `buffDisplayNameKeys` 中，由生成器读取 `operators.json` 的对应干员配置。
通用显示函数只读取这些数据，不维护干员特例表。

实际伤害与期望值须标清。存在状态性随机分支时，逐笔期望值之和不一定是整轴数学期望。
原生战斗随机状态未知时，编辑器每次模拟从头使用同一条均匀样本序列，使暴击事件在短序列中也按概率分布，
同时保证相同轴重复计算的结果一致。它是稳定的编辑器近似，不是原生随机数；录像对照仍应传入录到的完整随机状态。
技能块、持续效果和变速区间的时间规则见 [时间与显示](time-and-display.md)。
