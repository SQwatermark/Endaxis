# 技能操作与执行边界

技能库组织玩家输入，战斗运行时执行具体技能。两者通过技能段的目标技能 ID 关联。

## 概念

| 概念                                          | 含义                                                                                                       |
| --------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 技能库（skill library）                       | 干员可用的技能按键操作集合，由技能组组成，不包含切换干员、闪避和跳跃。                                     |
| 技能组（skill group）                         | 一个或一组技能段，对应一次或一组连续按键操作。普通与替换形态各自配置独立组。                               |
| 技能段／技能块（skill segment / skill block） | 一次按键操作的配置，引用该操作试图释放的技能 ID。                                                          |
| 技能段实例                                    | 轴上实际放置的一次操作，保存时间和配置来源，按模拟结果展示技能宽度与 hit。存档类型为 `SkillCastDocument`。 |
| 技能（skill）                                 | 所属干员等宿主内的实际执行程序。                                                                           |

## 输入与执行

模拟判断该时刻的输入会选择哪个技能；若与技能段的目标不一致，报告输入不匹配，仍强制执行配置目标。

技能组的 `operationType` 决定操作展示，具体技能的 `skillType` 描述执行类别。原生技能槽负责输入路由和换槽；等级、费用、冷却和养成修正按具体技能解析。调整展示分组、名称或排序不改变固定输入的执行结果。

## 展示与诊断

技能库、拖放预览、轴上技能块和导出图片按所属组展示操作类型与名称。组的 `nameKey` 引用名称模板，结合段号生成标签。

输入不匹配诊断使用技能库的内存反向索引，从候选技能 ID 查找对应操作段及名称。多个入口保留全部候选，没有入口时使用通用提示。该索引只解释结果，不参与执行或项目存储。

## 执行模块如何分工

```text
本帧输入 → 玩家输入协调（参数/种子/诊断）
          → AbilitySystemRuntime（路由、当前技能、延迟请求）
          → SkillRuntime（施放状态、费用、冷却、时间轴）
          → TimelineActionProcessor（区间调度）
          → ActionGraphExecution（控制流、动作寿命）
          → 资源/Buff/伤害等操作执行器（领域后果）
```

这些层共享显式端口，不各自保存另一套“当前技能”。玩家输入协调不持有未来排程；能力系统保存当前/处理中技能身份和延迟请求；技能保存一次施放进度；动作和时间轴保存自己的执行数据。编译程序、动作节点及步骤槽位目录按身份共享，可变黑板、选择、计数和注册编号进入战斗图。

## 动作图与时间轴

`ActionGraphExecution` 从编译图和宿主端口绑定叶子、分支、重复、目标循环、作用域与监听动作。宏参数代入的是操作数，运行时在消费点读取黑板，不自动变成调用时的值快照。`CombatActionSequenceRuntime` 提供黑板、目标上下文、程序槽位和操作末端；每个技能/Buff 宿主拥有独立实例，不能共享 once 或执行进度。

序列在调用动作之前写入 started 和执行许可，同步回调因此能观察和结束正在进入的动作。Tick 仅推进已经开始、执行成功且仍允许执行的项；End 对已获执行许可的开始项收尾，未开始项只封闭。返回 false 是动作结果，不是异常；抛错由外层会话失败封闭，不承诺自动 End 所有已执行动作。

条件动作和 Switch 各自保存选择与 Reset 规则，不能因都“二选一”而合并。重复动作保存计时、扫描次数和目标间隔；目标循环保存明确目标身份。直接黑板的 detachedSnapshot 仍共享实体板，不能用它代替整场分支复制。

时间轴按起点排序只为寻找到期项，实际同帧执行恢复原始配置顺序。新执行的区间通常到下一次访问才 Tick/End，包括零长度区间。JumpTo 跳过早于目标的待开始项，结束到期活动项；同步 CastEnd 则立即封闭调度入口，包含当前进入中的序列。这些差别属于可观察顺序，不能简化成统一的“跳到结束”。反向跳转明确不支持。

恢复绑定要求动作数据、调用点、图节点及 operationBindings 对应原程序；时间轴不能在 starting 尚未清空的中间调用栈上绑定。公开的低层绑定器只恢复所属片段，完整帧保存和候选提交仍由战斗会话负责。

## 技能启动、推进与结束

`CombatSkillPrograms` 以干员/技能/可选 castId 登记固定定义，分支复制登记表但继续共享固定程序和伤害快照槽位。同身份换成另一程序对象会失败；动态施放先核对固定定义、类型和 Tick 计划，再同时加入寻址表及推进列表。

普通即时启动先登记新的 CurrentSkill，再结束旧技能，随后执行新技能的 BeforeCastStart；这样的顺序让“下一技能消费”Buff 不被旧技能结束事件误清。技能重置黑板与时间轴，发布开始，应用准备值，然后立即执行零增量 Tick。扣费在对应帧的时间轴之前，自然结束检查在时间轴之后；同帧启动不应再多推进一整帧。

SwitchToBuffCast 有独立旁路，可以执行成功却不进入候选技能的普通 Casting 状态，也不保证出现 SkillStarted。输入回执 accepted 和排程 executed 仅表示实际执行入口结果；原生路由、标签和中断告警另行记录。被拒绝的连续组成员阻断后缀，告警本身不等同于拒绝。

延迟施放请求每宿主只有一个槽，同帧后写覆盖前写；消费前先清槽，消费时新产生的请求留到下一帧。它已经是战斗内后果，应进入切面；尚未提交的用户技能安排仍留在应用排程器。

能力系统先推进 Buff、共享冷却与活动技能，再处理可操作边界、延迟施放和回收。共享冷却按定义登记，不按放置块重复推进；换槽登记和结束回调使用稳定编号，旧回调不能撤销新的替换。具体冷却时钟与换槽预检见[战斗模拟](combat.md#时间与技能宽度)。

## 扩展与验证边界

新增动作需要明确 Execute/Tick/End/Reset、宿主可执行性、同步重入、步骤状态和恢复绑定；仅让执行器认识 kind 不算接通。新增技能入口要明确是否走玩家路由、是否延迟、是否继承施法与费用、是否真正进入 Casting，不能都转成一个布尔“合法”状态。

原生回归集中在 actions/timeline/skills、AbilitySystemRuntime，以及输入协调和宿主恢复测试。应检查相同帧内启动/结束、跳转/中断、嵌套响应、动态施放及分支恢复。多敌人空间选敌和没有闭合的原生能力仍需独立语义证据；现有零空间目标投影不能直接推广。
