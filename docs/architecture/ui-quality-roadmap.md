# UI 设计与实现质量中期计划

## 目标与依据

提升整体设计质量和实现质量，同时复刻旧版合理的使用体验。不是通用表单重写，
不是以拆文件、测试数量或源码相似度作为完成指标。

旧版行为参照 `D:/Projects/Endaxis-upstream-main`；先读源码解释规则，再在相同
数据、视口和状态下验证效果。游戏模拟事实仍来自游戏证据，不由旧版展示反推。
用户明确调整过的体验优先；新版模型必然差异和旧版明显缺陷需要单独记录。
深色主题优先，浅色主题留专项，不把浅色未完成伪装成全主题验收。

## 当前架构判断

- 已有不可变文档命令、编辑会话、显示模型、手势租约和逻辑输入区域，不推倒重来。
- TimelineEditor 仍集中协调大量选择、弹窗、持久化配置、手势和模拟反馈；按功能
  边界逐步迁出，而不是仅把连续代码搬到 composable。
- 输入区域已取代根 hasModalPanel 枚举；区域内命令优先级与原生文本/浮层 DOM
  保护仍保留。剩余验收需确认区域、手势和原生控件一致，不再增加根模态枚举。
- 之前的独立组件保存测试不等于完整项目保存验收；源码结构测试不等于行为测试。

## 设计约束

1. 自由编辑与严格模拟并行。告警不是编辑权限；不得隐式替换技能或抹去用户意图。
2. 选择、查看、编辑不同；不得因为选择而突然开新面板。
3. 实例/模板、草稿/已保存数据的范围必须明确；定义编辑器不照搬旧版技能表单。
4. 菜单和快捷键共享操作语义、事务与可用条件；不各自改写文档。
5. 视觉层级、命中层级、键盘归属分别设计并保持一致，不能只提高 z-index。
6. 布局变化不得改变游戏效果持续时间、输入时刻或模拟中断规则。
7. 编辑即时反馈；模拟待计算、计算中、过期、失败和告警需要可辨识，不能用旧结果
   冒充当前结果。具体状态实现先查现有代码，不预设必须引入某框架或 worker。
8. 同类控件共享尺寸、语义和反馈；不同任务保留不同表达，不追求所有编辑器一致外形。
