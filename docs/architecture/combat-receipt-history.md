# 回执历史、查询与截面

状态：2026-09-14 核心历史与截面路径已迁移，发布 API/查询与存盘适配尚待收束。依据实际消费者设计，不把战斗改造成依靠日志重放的引擎。

当前落地：`CombatReceiptHistory` 私有尾部及不可变段、`CombatReceiptView` 固定视图和惰性段目录，
写入冻结 entry/data；删除 `CombatReceiptState` 及可变 `runtimeState.entries` 出口。状态图不再含 receipts，
会话单独保存历史视图，恢复验证历史仍是保存的同一前缀且没有重放。`readState` 只返回瞬时状态，
`readHistory` 返回固定视图；`readReceipts` 使用本分支签发的 opaque cursor，返回冻结事实引用。
连续组与 compact 规划复用增量技能输入事实索引。发布结果暂以一次 `history.toArray()` 适配现有数组投影，
不再逐条复制/冻结；诊断、伤害分析和战斗日志已直接查询视图，其余时间轴投影共用一个数组适配点。
Worker 边界只传纯回执并在主线程重建视图。单结果 JSON Lines 导出已支持流式遍历；磁盘导入和
恢复战斗归档仍未实现。

这是本机串行复测，不能据此宣称已完成堆峰值/分支释放验证或全量验收。

## 1. 三种不同的数据

| 数据           | 回答的问题                                            | 变化规则                         | 截面处理                                     |
| -------------- | ----------------------------------------------------- | -------------------------------- | -------------------------------------------- |
| 瞬时战斗状态   | 现在还有多少资源、哪些动作/订阅/实体仍活动            | 后续帧会修改                     | 复制，恢复对象关系                           |
| 回执历史       | 在本分支里已经发生了什么、顺序如何                    | 只追加，不改旧事实               | 保存不可变前缀引用及边界，分叉共享           |
| 查询索引与投影 | 某技能何时可接续、某次 hit 的证据、曲线和日志如何展示 | 随新增事实增量更新，或从历史重建 | 不混入战斗状态；必要的小型消费者状态单独保存 |

“已发生”属于分支，不能等同于用户已经确认。候选分支内部发生的事实虽然不再改写，仍只是该候选的结果。
接受一个输入不意味着接受观察分支后面全部历史；主会话照常只推进已确认输入。不拼接两个候选的事实。

回执不是状态的备份：不能靠重放伤害、资源回执来恢复技能动作、Buff 引用、随机状态或订阅。
读回执也不能重新触发原生/语义事件。原有战斗事件系统继续负责行为，回执负责记录行为的事实。

## 2. 当前用途与问题

| 消费者                           | 真正需要的读取                         | 迁移后的接口                                         |
| -------------------------------- | -------------------------------------- | ---------------------------------------------------- |
| 旧轴修复 `checkpointRetiming.ts` | 当前分支新增的技能、输入和膨胀事实     | 游标增量读，按事件类型筛选                           |
| 连续组 `SkillInputGroupTiming`   | 特定 cast 的可接续边界                 | 技能输入事实索引，增量更新                           |
| 临时 compact 规划                | 前一 cast 的输入结果、中断、边界       | 复用同一个技能输入索引                               |
| 技能块显示和路由诊断             | 按 cast 汇集开始、接续、中断、来源事实 | 对固定历史视图做投影或建索引                         |
| 伤害/资源曲线、HUD、战斗日志     | 全序遍历、帧区间、帧处状态             | 固定历史视图；投影缓存绑定该视图                     |
| hit 详情、诊断跳转               | 由 receipt sequence 回到原始事实       | `view.get(sequence)`，不用反复 `find` 或各建一份 Map |
| 发布结果及缓存                   | 不会随模拟继续而变化的一份结果         | 不可变历史视图，按需共享/缓存投影                    |
| 导出/存盘                        | 稳定顺序、可流式遍历的纯数据           | 历史视图的序列化适配器                               |

迁移前的问题证据（以下接口已开始被上述实现替换）：

- `combatReceipt.ts` 的载荷是 primitive 字段表，写入已复制 data，但没有冻结记录，且公开了可变 `runtimeState.entries`。
- `CombatStateGraph.shared.receipts` 把整份历史带入 `structuredClone`；保存和分叉都重复制。
- `CombatRuntimeSession.readReceipts` 每次把筛选结果再 clone。
- `runScenarioSimulation.ts` 最终发布时再次逐条复制并冻结；此前的历史实际上仍可被写坏。
- `SkillInputGroupTiming` 持有会增长的数组并用数字游标消费，不能悄悄把 `entries` getter 换成每次生成新数组。
- `combatRuntimeAssembly.ts` 的 compact 模式还会全表 `find`；HUD、诊断又分别建索引。

这些问题不能只靠给数组加 readonly 或为每个消费者增加一个缓存解决。

## 3. 写入即成为不可变事实

保留一个最小写口 `CombatReceiptSink.record(entry): void`。游戏逻辑不接触历史内部结构。

写入时复制并冻结记录以及 data。当前 data 只有 primitive 值，明确冻结这两层即可，不引入通用深拷贝器。
sequence 由写口分配，不能由调用方覆盖。不向外暴露活动尾部数组、可变 state 或可写 Map。
导入历史也必须经过相同的不变性和编号校验，不能把外部数组当作受信任内部结构。

开始、命中、结束、中断分别追加事实。不得补写开始回执的结束时间，也不得为了显示把一条 hit 改成累计伤害。
若需要关联，使用已有 castId、hitId、实体/来源身份和 sequence；展示字段仍在投影层。
不改变现有可读事件名称、标签、对象类型，不顺带重新编码全套事件或修改技能定义。

## 4. 存储：共享已封存段，私有追加尾部

一个 writer 持有已封存的历史段链和一个私有尾部缓冲。段中记录与段的结构均不可变，记录保持全序。
尾部达到大小上限时封存；保存截面或发布稳定结果时也封存当前尾部。

截面从整图改成组合：

```ts
interface SavedCombatRuntime {
  state: CombatStateGraph; // 不含回执数组，只含真正的战斗状态
  programs: CombatProgramBindings; // 现有固定程序/分支登记关系
  history: CombatReceiptSnapshot; // 不可变段头 + 可见记录数
}
```

保存只需封存自己的尾部并保存历史引用；从截面创建 A/B 时，两者引用同一段头，各自拥有新尾部。
父会话继续运行也使用自己的新尾部，不能改变旧截面的可见记录数。尾部只包含已冻结的 entry 引用，
封存最多复制一个有上限的引用数组，不复制整段历史记录。

不维护指向全部子分支的全局注册表。丢弃试跑、截面或发布结果后，其独有后缀随 GC 回收；
只要还有读者，共享前缀就继续有效。游标也只保留自己需要的锚点，消费后替换旧锚点。
不能先 `structuredClone` 全图再删 receipts，那已经付出了全部复制成本。

先用封存段链即可，不引入数据库、通用持久化集合库或自定义内存管理。
从游标所在前缀到新段头只遍历新增段；需要正序时只反转该段引用列表，不反转/复制历史 entry。
固定视图的随机访问可惰性建立段目录并按 sequence 二分定位。首次目录构建 O(段数)，
保存/分叉 O(尾部上限)，增量读取 O(新增段和新记录)，导出 O(记录数)。不宣称所有查询均 O(1)。
段大小是私有实现参数，实际测量后决定，不成为游戏契约。

## 5. 两种读口，不强迫消费者理解分段

接口草案（名称在落地时统一；不是同时保留多套数组/历史协议）：

```ts
interface CombatReceiptView {
  readonly length: number;
  get(sequence: number): CombatReceiptEntry | undefined;
  entries(range?: { fromSequence?: number; toSequence?: number }): Iterable<CombatReceiptEntry>;
  toArray(): readonly CombatReceiptEntry[]; // 仅数组消费者/导出适配，固定视图内缓存
}

interface CombatReceiptReader {
  readSince(
    cursor: CombatReceiptCursor,
    filter?: CombatReceiptFilter,
  ): {
    entries: readonly CombatReceiptEntry[];
    cursor: CombatReceiptCursor;
  };
  snapshot(): CombatReceiptView;
}
```

- **增量读**服务正在运行的排程和观察器。返回一个新的、只含匹配 entry 引用的小数组；entry 已不可变，不再 clone。
  游标推进至全部已扫描记录之后，即使筛选结果为空也必须前进，否则反复扫描不相关事件。
- **固定视图**服务发布结果、曲线、日志、详情和导出。它只看发布时的历史，后续模拟不会改变结果。
- 每帧 `readSince` 不调用 `snapshot()`，不为了读一次而封存一个小段。返回批次不引用可变尾部数组。
- 帧过滤不替代顺序：同一帧有初始化、输入、技能更新等多条事实，sequence 才是全序。
  不得仅拿帧号充当增量游标。没有回执的帧仍在推进，观察截止帧由会话给出，不从最后一条回执推断。
- 截面仍记录 `initialInputPending` 等输入边界；两个相同帧号/相同历史长度的截面，不能因此被认为状态等价。

第一轮只提供真实需要的范围读取、事件类型筛选和 sequence 定位，不设计通用查询语言。
按 cast、hit、来源或帧的高频查询由相应索引完成；索引由共同投影函数建立，不复制事件解释逻辑。

## 6. 分支身份与引用

sequence 是一条分支历史内的序号，不是整个进程的唯一 ID。共享前缀的编号相同，A/B 后缀都可从 N 开始，
但两边第 N 条是不同事实。跨结果的引用必须携带所属结果/历史视图；`receiptSequences` 可以继续保持数字数组，
因为诊断本来就属于一个固定结果，不能把它们带到别的结果上查。

活动 reader 的 cursor 是带 writer 身份和代次的 opaque 句柄。恢复使旧 cursor 失效，fork 产生新 reader，
不允许用父分支/另一候选的游标读新分支。外部不能通过伪造数字进度绕过这些检查。
reader 可从该分支起点、当前末尾或它自己认可的截面位置创建 cursor；不暴露可任意拼接的段指针。
固定历史视图不因活动会话恢复而失效，已经打开的命中详情可以继续看它所属的旧结果。

## 7. 索引和瞬时状态的边界

技能输入索引统一维护 cast 的输入结果、开始、显示边界、终止及诊断引用；膨胀索引维护已发生区间和当前未闭合项。
这供连续组与旧轴修复使用，不增加另一套技能路由/资源判定。不把所有事件机械地建立所有字段索引。

HUD/曲线继续复用现有事实投影。先让它们接受固定视图的遍历，或在发布边界使用一次缓存的 toArray；
不能在热循环调用 toArray，也不能每个投影各自重新物化整表。
同一发布结果需要的查询索引由应用层共享，生命周期跟随结果，不缓存到全局静态表。

小型消费进度可重建或和所属排程器一起保存。第一步保证不串分支；若恢复时重扫前缀成为热点，
保存一份小型 reducer 状态及历史位置，恢复后只消费后缀。不为了避免重扫而共享可变 Map。
真正影响下一帧战斗的资源余额、冷却和订阅仍在状态图内，不依赖“查询索引刚好还在”。

Buff 进度曲线也是输出历史，但当前采样器会压缩/修改尾点。它不能直接套“所有点都已不可变”的假设。
后续若迁移，保留可变采样尾部在 recorder 状态，只有不会再压缩的前段可封存共享。本次不顺带改变采样语义。

## 8. 内存历史与磁盘格式分开

现有项目存档的权威数据仍是构筑和人工输入；不默认把模拟日志塞进每份项目。
用户需要导出战斗记录或保存可恢复运行时，才序列化相应数据。

- **普通结果导出**：版本化 metadata + 按 sequence 正序的记录流。可使用头记录加逐行记录的 JSONL，
  支持分批写出/读取，无需先建立完整大数组。保留现有 event、source/target、frame/time 和 data 字段。
  不直接序列化类实例、Map 内部结构或 JS 段指针。不在未验证前删掉 time 等看似可推导字段。
- **多截面/分支归档**：如确有此需求，在归档适配层将共享段只写一次，manifest 记录各历史的段引用及可见边界；
  单结果导出不为此承担复杂格式。不能把内存对象 ID 当成可跨进程 ID。
- **恢复战斗归档**：除历史外，必须包括瞬时状态、输入边界以及匹配的状态协议/游戏数据/程序版本。
  日志本身不能恢复战斗。当前没有据此承诺跨版本恢复，缺失匹配定义时明确拒绝。
- 导入校验 sequence、记录格式和引用边界，不静默重排。同帧事件保留顺序。数值若不能由 JSON 无损表达，
  必须明示编码或拒绝，不能让 NaN/Infinity 被静默写成 null。

先完成内存及单结果遍历协议；多分支磁盘归档只是边界设计，不列为当前必须开发的新功能。

## 9. 迁移顺序和验证

1. **写口不可变**：冻结 append 结果，关闭可变数组/state 出口；确认没有实际消费者需要改写旧记录。
2. **引入历史及读口**：为 SkillInputGroupTiming、compact 查询和旧轴观察建立公共索引/增量读取；
   发布结果用固定 view，现有数组投影仅在单一边界适配一次。
3. **移出状态图**：保存/恢复显式携带 history；装配创建新的 writer，绑定到自己的不可变前缀。
   `readState()` 只返回状态；需要状态和历史一起查看时提供显式 inspection 结果，不隐式重新复制全部历史。
4. **发布和序列化**：去掉发布时逐条 freeze/clone，结果直接持有不可变 view；由导出适配器输出数据。
5. **按同一三轴样本复测**：分别测图复制、恢复、模拟、历史查询；记录分支保留/丢弃后的内存趋势，
   不只看总耗时或序列化字节数。

验证必须证明：调用方修改写入参数不会改变历史；读者无法改写记录；父分支继续追加不改变旧 view；
A/B 共享前缀而各自后缀隔离；恢复旧 cursor 明确失效；同帧初始化/输入顺序正确；空筛选推进 cursor；
多段边界和发布时未满尾段不漏/不重复；按序查询、命中详情、曲线/诊断结果与旧实现相同；
snapshot/fork 不调用历史记录的 structuredClone；丢弃分支后没有全局表持有后缀。

试探分支还要验证释放行为。当前显式 GC 审计保留 24 个已经推进的候选外壳：释放前相对基线
多持有约 8.32 MiB，调用 `dispose()` 后只剩 0.184–0.187 MiB。该结果证明外壳不会继续强引用
重型候选分支；长轴峰值内存和反复转换后的进程趋势仍按 T5 单独测量。

迁移完成的标志是消费者已经使用上述边界、真实三轴结果保持一致、复制路径不再携带历史，
而不是只写出一个可分叉日志类或通过其单元测试。
