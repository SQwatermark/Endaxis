# 庄方宜在 Endaxis Next 中的建模方式

## 目的

庄方宜用于验证新版模型能否同时处理技能替换、跨技能持久状态、按状态层数缩放伤害、元素反应消费和一次性费用减免。

## 技能替换

普通与强化技能在游戏数据中是不同 SkillData，因此新版不把强化态建模成 `damageMultiplier`，也不把它做成仅影响文本的
`presentationVariant`。六个技能组分别拥有稳定身份：

- 普通/强化普攻；
- 普通/强化战技；
- 普通/强化连携。

`ultimateEnhancement` 只决定这些技能的 `availability`。这让存档能够准确回答“用户拖入的是哪一个技能”，也让合法性检查不必通过名称猜测技能形态。

## 战技上下文

青霄剑是跨施放持久状态；本次消耗的感电等级只在当前战技的落雷阶段有意义。二者必须分开：

- `sunderblade`：最多 9 层、持续 36 秒，决定本次有多少把剑参与落雷；
- `consumedElectrificationLevel`：最多 4 层，决定每次落雷的附加倍率，在末雷后清理。

伤害本身仍是普通 `dealDamage`，仅通过 `attackScalePerStatusStack` 引用后者。这样不会为感电 0 至 4 级复制五套完整伤害序列。

解包数据还显示，普通战技创建的飞剑攻击不是布尔标记，而是一条施加在庄方宜自身的限时 Buff：它持续 3 秒，按随青霄剑数量计算出的间隔触发，并携带伤害倍率、失衡和终结技能量等黑板参数。再次释放普通战技时，第 6 帧会先按 Buff ID 检查并结束上一轮实例，第 13 帧再创建新实例。因此：

- 不能把它投影成敌方 Buff、一次性 flag 或普通 `statusActive`；
- 通用运行时需要按 `caster/enemy` 解析 Buff 容器，并分别支持 ID 与 Tag 查询；
- 当前已闭环“施法者 ID Buff 层数检查与全部结束”，但 Buff 目录导入、创建和周期触发仍未闭环，普通战技暂不生成正式 DSL。

## 动作顺序

强化战技末雷使用同一个 `ActionSequenceDefinition` 表达：

1. `applyElementalInfliction`；
2. `dealDamage`；
3. 回能；
4. 清理本次感电等级快照。

这条顺序来自 SkillData，而不是 `beforeDamage` 之类的旁路标记。编译器只需按数组顺序执行。

## 一次性免费战技

终结技同时施加 25 秒强化状态和 `freeEnhancedBattle`。后者通过 `resourceCostMultiplier` 影响施放开始时的技力检查，并在强化战技的第一个逻辑节点消费。
因此第二次强化战技会自然恢复 100 技力消耗，不需要在技能定义中保存“这是终结技后的第几次战技”。

## 尚未解决的通用问题

- 连携施加反应时如何保存被消耗的附着层数，供后续回能公式读取；
- 天赋按每次青霄剑 hit 递增的电磁增幅事件；
- 潜能对状态时长、技能伤害加成和抗性无视的统一升级修正；
- 独立持续时间的多层青霄剑在运行时如何逐层过期；
- 飞剑攻击 Buff 的目录定义、创建参数传递与周期触发；
- 普通普攻第二、第五段的完整命中拆分。

这些能力应进入通用战斗模型，不应在庄方宜文件中加入不可复用的解释器。
