# 武器、装备与套装

配装分为游戏定义、用户选择和单场战斗状态。武器词条、装备词条与套装共用贡献结构，
动作、条件、Buff和事件也复用公共机制，不另造一套装备战斗语言。

## 定义和用户选择

[公共装备类型](../../packages/game-data-contract/src/equipment.ts) 保存身份、成长、词条与效果。
`slug` 标识定义对象；`assetSlug` 只定位展示资源，共用图标不能成为合并两个对象身份的理由。
装备词条的 `display` 决定怎样展示，`modifiers` 才是实际效果，不能从展示文本反推战斗数值。

[项目格式](../../src/core/project/schema.ts) 保存定义引用和用户选择：武器等级、突破、潜能、
最终词条等级，以及装备精锻等级。引用可指向内置或项目级模板。
这些实例不重复保存基础攻击、防御和编译结果；项目级模板是独立的定义数据，不能与配装实例混为一谈。

武器词条按用户选择的最终 `traitLevels` 解析，不再次把潜能叠加到词条等级上。
装备精锻的 `0` 表示初始档，解析时对应词条定义的第一级。两个配件槽共用 `accessory` 定义类型，
槽位位置由项目保存。套装归属写在装备定义上，三件生效是统一规则，不在每件装备复制套装效果。

武器成长节点之外的数值必须使用已确认的成长规则，不能自行线性插值。
定义字段及合法值以公共类型和校验器为准，本文不再复制完整接口。

## 常驻修正和战斗行为

`EquipmentContributionDefinition` 可以同时包含以下内容：

| 字段                     | 负责什么                               |
| ------------------------ | -------------------------------------- |
| `modifiers`              | 常驻属性、面板和分类修正               |
| `eventHandlers`          | 收到指定事件后检查条件并执行动作       |
| `buffDefinitions`        | 该贡献引用的Buff定义                   |
| `blackboard`             | 按贡献等级解析的初始黑板               |
| `enableSequence`         | 启用前执行的动作，此时自身事件响应关闭 |
| `initializationSequence` | 启用后在帧0执行的初始化动作            |

常驻修正复用 [构筑修正类型](../../packages/game-data-contract/src/buildModifiers.ts)。
这里的百分比修正使用小数，例如5%写作0.05；不要把这一约定扩大到所有动作字段。
按伤害或技能类型筛选的加成保留筛选条件，不能折算成无条件面板值。
事件触发的临时效果也不能预先当作常驻效果加入面板。

## 编译和来源

场景入口已经存在：[构筑解析](../../src/core/compiler/resolveScenarioBuilds.ts) 处理用户构筑，
[场景编译](../../src/core/compiler/compileScenarioRuntimeAssembly.ts) 汇总模拟输入。
新增装备支持应接入这些入口，不按旧方案再建一套流水线。

[装备编译器](../../src/core/compiler/compileEquipment.ts) 解析等级值、主副属性、动作和Buff引用，
输出一组带来源的贡献。来源区分武器词条、装备词条和套装，供归因、诊断与清理使用，
不使用翻译名称或本机路径作为身份。

编译不执行伤害、不注册监听，也不修改战斗中的Buff容器。
构筑阶段确定套装激活结果，面板与运行时复用解析后的贡献，不各算一份套装数量。

## 运行与清理

[EquipmentEventRuntime](../../src/core/combat/abilities/equipmentEventRuntime.ts) 已有正式装配入口。
处理器可以选择语义事件 `event` 或原生能力事件 `abilityEvent`，两者互斥；
优先级与注册顺序按定义保留，不能把两类通知当作同一个效果执行两遍。

同一贡献的初始化与事件响应共享黑板，各动作序列保留自己的执行状态。
启用前自身事件响应关闭，启用完成后才接受事件。注册或初始化失败时需要清理已经创建的内容，
战斗释放时统一回收监听与所持有的资源。

装备被动有自己的生命周期。它创建的附着Buff不能随意挂在触发事件的主动技能上，
否则主动技能结束时会提前清除装备效果。执行上下文保留装备来源，不伪装成一次玩家施法。
共用的事件与清理要求见 [战斗执行与状态](runtime.md)。

## 条件与数值不能近似替换

构筑时能确定的常驻修正，与依赖当前生命、目标状态或Buff层数的修正，应分别处理。
动态条件要在规定的运行阶段读取当前状态，不能用开战时的真假代替整场结果。
具体条件可能带有有序动作和黑板写入，不能按旧方案一概视为只读布尔查询；
当前Buff表达见 [公共Buff类型](../../packages/game-data-contract/src/buffs.ts)。

修正必须保留原生含义。例如 `skillCooldownMultiplier` 保存冷却时长倍率，不能随意改成缩减百分比；
`staticHealingIncrease` 区分输出治疗与受到治疗；`damageScale` 保留倍率目标和公式槽位。
治疗、减伤、失衡和伤害增幅不能因为都表示为数字，就互相替换成面板攻击或普通伤害加成。

某个旧装备有形态或一次性效果，不足以证明需要替换干员技能。
先确认原生行为属于条件、Buff消费、贡献选择还是技能结构变化，再选择对应表达。
旧数据和旧实现可用于找样本，不能直接作为新生成数据的规则来源。

## 怎样验证一项装备支持

验证应覆盖从定义、构筑、编译到战斗记录的完整路径：

- 静态修正在面板和战斗中读取同一数值，来源可追踪，套装只计入一次。
- 条件在生命或目标状态变化后读取新值，筛选范围没有扩大。
- 触发Buff的内部冷却、叠层、重复触发和结束顺序符合证据。
- 初始化、事件响应和主动技能共存时，黑板及来源没有串用，清理不会提前结束独立效果。
