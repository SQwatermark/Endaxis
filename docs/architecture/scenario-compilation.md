# 场景编译

场景编译把作者的构筑、技能安排和机制选择，连同已经准备好的游戏定义，变成一场战斗的程序与装配参数。它不读取原始游戏资源、不做网络或文件装载、不推进战斗，也不负责界面发布和异步请求取消。

## 输入、输出与责任

```text
ScenarioDocument + 已装载定义查询 + 显式运行环境
  → 机制与全局效果、构筑解析
  → 面板、技能/装备/养成程序、资源规则
  → 输入锚点与连续组、主控/闪避/外部事实
  → CombatRuntimeAssemblyOptions
  → 战斗装配与受控推进
```

正式入口是 [compileScenarioRuntimeAssembly](../../src/core/compiler/compileScenarioRuntimeAssembly.ts)。返回值同时包含固定程序和注入的运行端口，因此不是任意跨线程传输、持久化或反复装配都安全的纯 JSON 包。这里的“编译”表示不执行游戏推进，不代表对定义缓存完全无副作用；图首次发布和冻结见[游戏数据](game-data.md#图定义什么时候成为只读)。

| 子模块                                      | 负责的决定                                   | 不负责的事                               |
| ------------------------------------------- | -------------------------------------------- | ---------------------------------------- |
| `resolveScenarioBuilds`                     | 按轨道解析身份、武器类型、装备槽位和激活套装 | 不改作者配置，不制造缺席角色             |
| `resolveOperatorPanel`                      | 按养成/配装解析本次静态面板                  | 不把战斗 Buff 或动态余额写回面板         |
| 技能、装备、养成编译器                      | 等级值、定义图、被动/初始化/事件程序和来源   | 不创建技能施放进度、Buff 实例或事件订阅  |
| `compileScenarioTimeline`                   | 施放身份、输入顺序、连续组锚点与成员         | 不预演后续技能何时能成功执行             |
| `compileScenarioResources` 与规则解析       | 初始资源、全技能定义中的资源上限/费用规则    | 不根据只放置了哪几个技能伪造角色完整能力 |
| `compileMechanics` / `compileGlobalEffects` | 机制贡献、定义/适配器版本和初始化 Buff       | 不让数据适配器直接取得活动战斗对象       |
| 装配参数组合                                | 固定事实优先，补入环境端口并检查目标身份     | 不把缺失端口都填成无效果实现             |

定义 slug、轨道 ID、技能定义 ID 与施放 ID 分别属于查找、战斗对象、固定程序和一次调用。编译后的 operatorId 来自轨道身份，不能用角色名称代替；注入的实体级运行绑定也不能覆盖编译器确定的身份和技能程序。

## 正常路径与失败边界

构筑解析要求查询结果身份与请求一致，拒绝空轨道上的装备/技能、重复轨道 ID、错误武器类型和槽位。套装按已经解析的实际装备聚合。装备、全局机制与角色 Buff 合并时遇到身份冲突明确失败，不按覆盖顺序决定规则。

场景的准备区只表示可编辑范围。固定排程从最早实际输入决定开始帧，不因存在空白准备区就提前回复资源或推进 Buff。切人、闪避和外部事件编译保持稳定身份及同帧声明顺序；极限闪避的 Dash 和成功事实分开，不能在 Dash 尚未提交时先宣告成功。

连续组编译产生锚点和成员关系，实际接续依赖运行时的成功/结束边界。静态编译不会把组内每个成员都当成已经发生的 SkillStarted，也不会把拒绝的输入伪装成成功。运行时如何接管输入见[战斗模拟](combat.md)。

只提交逐帧输入的会话使用 `liveInputInitialFrame`：初始化帧限制在准备区起点到零帧，装配时不携带未来技能块、消耗品、切人、闪避和外部事件排程，并推迟首帧输入。固定技能定义仍需要编译；自定义施放程序可以由外部输入计划单独准备，但编译不等于已经提交输入或消费随机种子。

## 图准备、程序共享与执行分离

[图校验](../../src/core/action-graph/actionGraphValidation.ts) 检查所属图内的控制出口、缺失节点和非法回边；独立子资源另外校验。宏调用与内部节点绑定不是普通跨图控制边，宏递归也单独拒绝。

[图编译](../../src/core/compiler/compileActionGraph.ts) 先绑定数据表达式、主图/宏身份并验证结构，再按入口补齐已编译节点。多个入口可共享同一个固定程序，但每个入口保留 callSite。编译器内部 nodes/operationBindings 是目录，不是战斗动作进度；不能将其误当作切面数据克隆。

表达式在编译时绑定，在消费动作的上下文中求值。同一读取定义不意味着共享一次求值结果；随机和写黑板等副作用必须保留原执行次数。完整资源归属和宏规则见[动作图](action-graphs.md)。

## 机制能力：类型声明与正式装配要分开看

`MechanicAdapterRegistry` 按 family 登记适配器，重复 family 拒绝。机制选择先校验参数和定义，启用项必须有对应适配器；输出携带选择身份与双方版本。贡献层还检查非有限数、循环/回调等非法数据形态，以及当前未确定的同优先级事件顺序。

机制类型和 [installMechanicContributions](../../src/core/mechanics/mechanicRuntime.ts) 工具包含事件贡献，但**正式场景装配目前只接收战斗初始化序列和敌人静态属性倍率**，对事件贡献明确报错。通用安装工具通过核心公共出口暴露并有单元测试，不代表页面已接入这条运行链。

全局效果和自定义数值统一编译成普通 Buff 与 GlobalBuff 初始化序列；敌人最大生命等静态机制在生命账本创建之前应用，不能在运行时再乘一次。新增机制种类必须同时核对正式装配、来源、订阅清理和切面恢复，不能仅添加一个 Adapter 或让类型检查通过。

## 扩展与验证

新增字段先确定它属于定义、作者安排、编译产物还是可变状态。若只在编译阶段使用，不要继续透传到执行上下文；若会影响战斗后果，则必须在状态/恢复和回执边界找到所有者。

关键原生测试集中在 `core/compiler` 的构筑、面板、时间轴、完整装配、图编译与全局效果测试，以及 `core/mechanics`。应同时比较固定排程与逐帧输入、定义级与自定义施放、准备帧与首帧，以及缺定义/身份不匹配/未支持机制的失败；编译通过不能代替真实战斗规则验收。
