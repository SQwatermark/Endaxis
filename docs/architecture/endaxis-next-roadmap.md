# Endaxis Next 现状审计与迁移路线图

## 1. 文档目的

本文以当前 `main` 分支为基准，回答三个问题：

1. 现有 Endaxis 实际提供了哪些功能；
2. 哪些架构问题正在妨碍正确性、维护和后续自动排轴；
3. 如何按优先级将这些功能迁移到 `src/next`，并在切换入口前证明新版可用。

新版不是对旧目录的逐文件翻译。迁移对象是经过验证的用户行为和计算结果；旧版的状态形状、跨层依赖和派生字段不属于兼容目标。

各项能力的实时迁移状态见 [Endaxis Next 功能迁移矩阵](./endaxis-next-feature-matrix.md)。

## 2. 当前系统概览

### 2.1 实际数据流

```text
src/data 静态目录与干员脚本
  -> collect/patch/resolve 动态拼装
  -> timelineStore 构造技能库、实例和轨道动作
  -> compileEndaxisScenario/compileTimeline 编译逻辑时间
  -> simulation 事件引擎与战斗状态
  -> projection 日志、曲线、状态条、连携窗口和警告
  -> Pinia computed
  -> TimelineEditor 与各 UI 组件

timelineStore/armory stores
  <-> 撤销历史、场景切换、自动保存、导入导出和分享码
```

这条链路已经具备较完整的产品能力，但边界并不等同于目录名称。中央 store 仍在各层之间直接搬运、补丁化和重算数据。

### 2.2 规模信号

以下数字只用于说明职责集中程度，不作为代码质量的单独判据：

| 文件                           | 当前行数 | 主要职责                                               |
| ------------------------------ | -------: | ------------------------------------------------------ |
| `src/stores/timelineStore.ts`  |     6226 | 项目、场景、编辑器、配装、历史、编译输入、模拟投影协调 |
| `src/views/TimelineEditor.vue` |     3513 | 工作区布局、菜单、快捷键、导入导出和大量交互编排       |
| `src/data/collect.ts`          |     1828 | 配装效果收集、技能展开、补丁、触发器和等级解析         |
| `src/data/types.ts`            |     1182 | 游戏数据、效果、技能、补丁等多领域类型                 |
| `src/simulation/simulator.ts`  |      569 | 模拟入口与事件处理协调                                 |

旧代码中还存在大量开放形状和跨边界兼容逻辑：约 97 处 `[key: string]: unknown`、486 处 `any`、42 处 JSON 深拷贝，以及 30 处非 i18n 模块直接调用 `i18n.global`。这些数字会随上游变化，问题本质是缺乏明确的数据所有权。

## 3. 当前功能清单

### 3.1 项目与场景

- 多方案创建、重命名、复制、删除与切换；
- 浏览器自动保存、JSON 导入导出、压缩分享码；
- 撤销与重做；
- 战斗准备区、战斗时长和模拟区间；
- 周期边界、切人事件和从上一方案继承战斗状态；
- 长图、小图和分享卡片导出。

### 3.2 队伍与配装

- 四条干员轨道，允许空轨道；
- 干员等级、突破、潜能、技能等级、天赋状态、信赖和基础面板覆盖；
- 武器等级、突破、潜能及三个词条等级；
- 四个装备槽、精锻等级和三件套效果；
- 根据干员、武器和装备计算面板，并展示来源明细；
- 双形态干员和技能描述富文本展示。

### 3.3 时间轴编辑

- 从技能库放置单技能或普攻连段；
- 拖动、对齐、锁定、禁用、复制、粘贴和删除动作；
- 单选、多选、框选以及动作连接；
- 技能属性、命中和效果编辑；
- 自定义持续条、颜色和连接端点；
- 缩放、滚动、轨道高度、准备区折叠和图层显隐；
- 键盘快捷键、轨道切换和鼠标中键平移。

### 3.4 战斗配置与模拟

- 敌人预设、自定义面板、抗性、失衡和处决倍率；
- 技力、终结技能量、冷却和连携窗口；
- 伤害、暴击、失衡、处决、元素附着与反应；
- 干员、敌人和队伍状态效果；
- 天赋、潜能、武器、装备、协议和全局修正触发器；
- 条件、消耗、持续、层数、嵌套命中和状态读取；
- 逻辑时间到实际时间的编译，包括时间停止和持续时间修正；
- 战斗日志、伤害分析和跨方案状态继承。

### 3.5 可视化与诊断

- 技力、失衡和各干员终结技能量曲线；
- 敌我状态条、元素附着、连携窗口和动作按键提示；
- 技力、终结技能量、连携窗口、技能前置条件等合法性警告；
- 模拟日志、伤害详情和效果来源追踪；
- 桌面编辑器、移动端查看器、主题和多语言。

## 4. 当前架构缺陷

### P0：会阻断可靠演进的问题

#### 4.1 持久化文档、编辑状态和运行时快照混在一起

`ScenarioSnapshot` 和 `TimelineAction` 既是编辑器对象，又携带技能展开结果、面板、触发器、警告前置条件和模拟辅助字段。保存时只能依靠手工删字段、比较 baseline 或加载后刷新来判断谁是权威来源。

影响：

- 游戏数据更新后，旧存档中的派生值可能覆盖新目录数据；
- 新增字段很容易被无意写入存档；
- 恢复历史和读取存档都可能触发身份重建或结果漂移；
- 无法稳定定义“用户改过什么”。

新版必须只持久化用户输入、稳定身份和明确可编辑默认值。编译结果、面板、日志、曲线和警告全部派生。

#### 4.2 缺少唯一的领域模型和术语

旧版同时存在 `TimelineAction`、编译器 `Action`、`ResolvedAction`、技能 sheet、segment、hit 和 effect 等相互重叠的对象，字段通过展开和对象扩散跨层传播。大量 `any`、索引签名和 raw string 使类型系统无法证明对象处于哪个阶段。

影响：

- 同名字段在不同阶段语义不同；
- `treatAsSkillType` 一类兼容字段会误伤事件监听逻辑；
- 新机制常以布尔标记和特例叠加，而不是扩展稳定模型；
- 配置错误往往只能在运行时或 UI 中发现。

新版采用明确的阶段类型：`ProjectDocument -> AuthoredScenario -> CompiledScenario -> SimulationReceipt -> Projection`，阶段之间只允许显式转换。

#### 4.3 中央 store 和主视图承担过多职责

`timelineStore.ts` 与 `TimelineEditor.vue` 已成为事实上的应用容器。业务规则、状态变更、持久化、像素换算、弹窗和快捷键作用域难以独立测试。

影响：

- 修改一个交互可能触发历史、模拟或持久化副作用；
- composable 虽被抽出，仍通过庞大的依赖对象反向耦合中央 store；
- 无法在无 Vue 环境中复用编辑和模拟能力；
- UI 组件难以形成清晰的 focus/shortcut scope。

新版核心不得依赖 Vue、Pinia、浏览器 API 或 i18n。Pinia 只负责连接应用服务和渲染状态。

#### 4.4 目录定义经过可变补丁链才成为可执行技能

旧版 `collect.ts` 同时收集配装效果、展开技能、补 ID、应用 patch、解析触发器并生成 UI 所需形状。行为顺序部分依赖补丁调用顺序和约定字段。

影响：

- 很难从一个干员文件直接理解最终行为；
- 自动生成配置时无法判断哪些值来自数据、人工修订或运行时补丁；
- 同一 hit 内 buff、伤害和附着的顺序难以自然表达；
- 新角色容易复制旧角色的隐式约定。

新版目录使用有序 `ActionSequence` 和类型化 DSL；编译器只解析定义，不再修补定义本身。人工修订及反编译证据放在独立证据文件中。

#### 4.5 存档缺乏稳定、可验证的版本边界

旧格式以 `version: 1.0.0` 和松散对象为主，导入逻辑包含就地兼容和默认值回填，无法完整拒绝悬空引用和未知枚举。自动保存、导出、分享与历史也没有共同的强类型边界。

新版必须满足：

- 所有入口先解析、迁移、验证，再进入应用状态；
- schema 版本与游戏数据版本分离；
- 迁移为纯函数，不读取 store；
- 未知版本不得猜测加载；
- 自动保存、项目导出和分享使用同一文档结构。

### P1：应在功能迁移前解决的问题

#### 4.6 历史系统依赖完整 JSON 快照和手工提交时机

当前撤销历史保存完整序列化快照，并依赖 watcher 与 `commitState()` 的调用纪律。派生字段或不稳定 ID 进入快照时，相邻历史可能看似不同却恢复成相同状态。

新版应采用命令事务：一次用户意图产生一个前后明确的文档变更；撤销、重做、自动保存和模拟失效都订阅同一提交事件。历史只管理项目文档，不管理 hover、选择和模拟结果。

#### 4.7 身份、显示文本和本地化未彻底分离

旧版数据收集、store、技能库和持久化层仍会访问 `i18n.global`，部分对象携带已翻译名称。语言切换可能改变非 UI 数据，旧存档也可能只剩显示名而缺少可重新解析的身份。

新版核心只传递 slug、skill key、step key 和结构化日志参数。名称、说明、数值格式和错误文案只在 projection/UI 层本地化。

#### 4.8 配装存在多份表示和同步字段

干员、武器、装备分别存在实例 store，同时轨道又保存武器 ID、词条等级、装备 ID、精锻等级、`appliedDeltas` 和已计算 `operatorStatus`。

新版以 build document 为唯一用户输入；轨道只引用 build ID。面板计算接收目录定义和 build，返回不可持久化的 receipt，并能说明每项来源。

#### 4.9 敌人配置的所有权不清晰

敌人预设、`systemConstants`、`customEnemyParams`、全局修正和协议会在编译前合并，同一属性可能有多个默认来源。预设值是否可编辑、是否写入存档、目录更新后是否刷新并不统一。

新版敌人采用与配装相同的 `source + editable + edited` 语义，合并策略由单独 resolver 负责并输出来源明细。

#### 4.10 时间单位和身份生成不统一

旧版以浮点秒为主，在拖拽、吸附、编译和显示之间多次换算；ID 还存在随机短串和加载时补齐。

新版项目文档统一使用 30 FPS 整数帧；运行时可使用高精度时间，但必须从逻辑帧显式编译。持久化实体 ID 在创建时生成且终身稳定，纯派生对象使用确定性地址。

#### 4.11 错误处理缺少结构化结果

旧版部分导入、编译和模拟失败只返回 `false`、抛异常或写 `console.error`。UI 无法稳定定位到场景、轨道、技能、序列和步骤。

新版各边界返回带路径、错误码和上下文的结果；可恢复问题形成诊断，破坏不变量的问题阻止编译或加载。

### P2：可随 UI 迁移逐步处理的问题

#### 4.12 编辑器交互和快捷键缺少统一作用域

全局键盘、弹窗、菜单、时间轴和输入框分别阻止事件，打开过弹窗后作用域状态容易残留。新版应由单一 `InteractionScopeService` 管理焦点栈、命令启用条件和快捷键映射。

#### 4.13 计算与投影依赖 Vue computed 全量重跑

当前活跃方案变化会重新编译、完整模拟并生成所有投影。数据规模增大后难以定位缓存边界。新版先保证纯函数正确，再以项目 revision、目录 revision 和阶段输入建立可观测缓存；不能让缓存参与业务语义。

#### 4.14 UI、偏好和项目设置边界不一致

部分轨道高度与准备区折叠写入方案，部分工具栏、图层、面板尺寸写入 localStorage。新版需明确：影响分享结果或方案表达的设置进项目；仅影响当前设备显示的设置进用户偏好；瞬时交互不持久化。

#### 4.15 桌面与移动端存在行为漂移风险

移动端目前是独立查看入口。新版两端应消费同一 projection 和命令能力表；移动端可以只读，但不能重新实现战斗解释。

#### 4.16 测试中存在结构断言和跨层大型 fixture

部分测试依赖源码结构或庞大动态对象，能够阻止重构却不能证明用户行为。新版测试优先验证公开契约、序列执行顺序、迁移 fixture、模拟 receipt 和 UI 用户流程；结构约束只用于真正的依赖边界。

## 5. 新版目标架构

```text
Game data files (shared, read-only)
  -> adapters
  -> CatalogRepository

Project JSON
  -> parser / version migrator / validator
  -> ProjectDocument (唯一持久化真相)
  -> editor commands + transaction history
  -> resolver (目录默认值 + 用户编辑)
  -> compiler (逻辑技能 -> 有序运行计划)
  -> simulator (离散事件与战斗状态)
  -> receipt (稳定、结构化的事实记录)
  -> projections (时间轴、曲线、日志、警告、分析)
  -> Vue application / i18n / rendering
```

### 5.1 强制依赖规则

1. `core` 不导入 Vue、Pinia、Element Plus、浏览器 API 和 i18n；
2. 只有 adapter 可以读取旧 `src/data` 的形状；
3. compiler 不修改目录定义或项目文档；
4. simulator 不读取 UI 对象，也不生成展示文案；
5. projection 只消费 receipt 和只读目录；
6. UI 只能通过 command 修改项目文档；
7. 持久化只接受通过验证的 `ProjectDocument`；
8. 自动排轴未来也只能调用同一 command/compiler/simulator，不另建规则引擎。

## 6. 实施优先级

### 阶段 0：冻结契约与建立回归样本（最高优先级）

目标：先定义什么叫“迁移正确”，避免新版追着旧 UI 猜行为。

交付物：

- 旧版功能矩阵与对应入口；
- 真实项目导出 fixture，包括普通队伍、双形态、复杂 trigger、跨方案继承和自定义命中；
- 已验证面板快照和代表性战斗 receipt；
- 旧版明确保留、修正、暂缓的行为清单；
- 新旧对比工具的输出格式。

验收：每个 P0/P1 功能至少有一个可重复的输入和预期结果，争议机制被标为“待研究”而不是写入实现。

### 阶段 1：补全项目模型和目录边界

目标：让 `src/next` 能完整表达现有用户输入，但不携带派生状态。

任务：

- 为周期边界、切人、跨方案继承、全局修正和编辑器设置建立明确模型；
- 完成武器、装备、套装、敌人和系统规则定义；
- 明确自定义 action/hit/effect 的可编辑范围；
- 统一稳定 ID、目录 key、用户实体 ID 和派生地址；
- 固化 catalog defaults 与 `edited` 的刷新策略；
- 建立跨文档引用和语义校验。

验收：所有新版文档均可无 Vue 地创建、解析、验证、序列化并精确 round-trip；任何悬空引用和未知枚举都有结构化路径错误。

### 阶段 2：旧存档迁移器

目标：尽可能兼容当前导出文件，同时只写新版格式。

任务：

- 收集并脱敏真实旧存档 fixture；
- 恢复技能身份，区分用户编辑与旧派生值；
- 将浮点秒归一到逻辑帧；
- 将 before/after damage 等旧结构转换成有序 sequence；
- 对无法无损迁移的字段给出明确 warning；
- 建立 `legacy -> V2 -> V2` 幂等测试。

验收：fixture 迁移不崩溃，不静默丢用户编辑；迁移报告可定位到方案、轨道和动作。

### 阶段 3：配装解析与面板计算

目标：先贯通最稳定、最容易用游戏 UI 验证的计算链。

任务：

- adapter 将旧目录转换成新版 operator/weapon/gear/enemy definitions；
- build resolver 计算等级、突破、潜能、天赋、词条、精锻和套装；
- panel calculator 输出数值及逐项来源 receipt；
- 覆盖普通、双形态和属性比较型干员；
- 建立截图快照差异工具。

验收：已有确认样本完全一致；旧版与新版差异必须能追溯到具体来源，不允许只比较最终总数。

### 阶段 4：编辑命令与历史

目标：在没有时间轴 UI 的情况下完成可靠编辑内核。

任务：

- 场景与 build 的增删改；
- 放置技能组、移动、锁定、禁用、删除、复制和批量操作；
- hit/effect 编辑和连接；
- 一个用户意图对应一个 transaction；
- undo/redo、dirty revision 和 autosave 通知；
- 命令前置条件与结构化失败结果。

验收：随机命令序列执行后可逐步完全撤销并重做；历史中不出现 projection/runtime 字段；目录更新不改变用户明确编辑的值。

### 阶段 5：编译器最小闭环

目标：将一个方案稳定编译为确定性的运行计划。

顺序：

1. 技能组展开与逻辑帧；
2. ordered sequence 与 conditional；
3. 冷却、费用和 availability；
4. trigger/event handler；
5. 状态持续、层数和消耗；
6. 时间停止、持续延长和跨方案初态。

验收：同一文档和目录 revision 产生字节级稳定的编译摘要；编译过程不修改输入；佩丽卡、诀和庄方宜均有端到端 fixture。

### 阶段 6：模拟器主动战斗闭环

目标：优先覆盖排轴器需要的玩家主动攻击流程。

顺序：

1. 技力、终结技能量和冷却；
2. 有序 hit 内 buff/附着/伤害执行；
3. 面板代入、伤害和暴击；
4. 失衡、破防、处决；
5. 元素附着和反应；
6. 天赋、潜能、武器、装备和全局触发器；
7. 连携窗口队列和多段连携；
8. 终结技强化、技能替换和形态状态；
9. 切人和跨方案继承。

怪物主动 AI、多敌人目标选择和前台动画不属于首轮闭环。

验收：模拟输出结构化 receipt，包含每个状态变更的时间、来源、前值和后值；合法性诊断只读取同一份执行事实，不维护第二套资源账本。

### 阶段 7：投影与分析

目标：从 receipt 纯函数生成全部展示数据。

任务：

- 动作实际时间和命中端点；
- 技力、失衡、终结技能量曲线；
- 状态条、附着、连携窗口和触发效果；
- 合法性诊断；
- 战斗日志、伤害明细和来源归因；
- 大图导出所需的完整布局数据。

验收：任何 projection 均可独立重算和丢弃；切换语言不重新编译或模拟；警告和曲线在同一事件时刻、同一资源值上保持一致。

### 阶段 8：并行 UI

目标：建立内部入口验证完整工作流，不影响当前 `/timeline`。

迁移顺序：

1. 项目/方案和四轨道骨架；
2. 干员、武器、装备和面板；
3. 技能库与放置、拖动、选择；
4. 属性与 hit/effect 编辑；
5. 资源曲线、状态条、连接和警告；
6. 分析、日志、导入导出和图片导出；
7. 快捷键作用域、移动端只读视图和无障碍。

验收：Playwright 覆盖核心工作流；UI 不直接改文档对象；所有快捷键经过统一作用域；桌面与移动端共享 projection。

### 阶段 9：对比、切换与清理

目标：在证据足够时一次切换入口。

切换条件：

- 所有 P0/P1 功能达到功能矩阵要求；
- 真实旧存档迁移通过；
- 面板和代表性战斗样本通过；
- 连续撤销/重做、导入导出和分享通过；
- 性能不低于旧版的可接受基线；
- 已知差异均有文档和用户可见说明。

切换后只保留有期限的旧存档迁移代码，不保留旧运行时作为长期 fallback。

### 阻断下一阶段的缺口

- `GameDataRepository` 中武器和装备仍只有 slug 占位，机制目录也尚无真实 adapter；
- project schema 已完成周期边界、切人、跨方案继承和全局配置建模，但尚无继承状态投影器；

## 8. 决策记录原则

- 反编译确认的机制写入实现与证据文档；
- 游戏内可直接验证的数值同时保留快照样本；
- 仅从旧版 Endaxis 继承的行为标注为 legacy reference，不视为游戏事实；
- 尚未闭环的推测进入 TODO/研究清单，不进入可执行默认值；
- 每完成一个阶段即提交独立 Git commit，并更新本文件的完成状态。
