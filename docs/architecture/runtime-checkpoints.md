# 战斗运行时切面

本文说明战斗模拟如何保存一个完整帧时刻的数据、从该时刻建立分支、试算后回退。这里描述当前设计，
不记录迁移过程。任务状态和测量结果见[切面任务清单](../handoff/runtime-checkpoint-plan.md)。

## 用途

切面用于需要反复试算同一历史前缀的功能，例如：

- 旧轴转换逐个尝试技能位置；
- 编辑器判断一个候选技能能否接在现有技能后；
- 比较不同技能块种子、主控切换或人工标记；
- 调试同一战斗时刻之后的不同分支。

切面保存已经发生的战斗事实。编辑器尚未提交的技能、连续组后续计划和其他未来输入留在战斗外部。
已提交输入产生的延迟伤害、Buff、投射物、回调和时间膨胀属于战斗事实，必须保存。

## 核心规则

1. **数据和逻辑分开。** 切面只保存数据，不保存函数、闭包、类实例或事件处理器。
2. **只有步进可以执行游戏规则。** 保存、复制、恢复和读取不会施放技能、触发事件、扣资源或消费随机数。
3. **完整帧是公开边界。** 输入和各系统阶段执行完毕后才能保存或读取稳定结果。
4. **切面形成一棵树。** 一个保存点可以产生多个分支；分支可以继续保存和分叉；不合并分支。
5. **回退是替换。** 恢复先构造完整候选装配，全部成功后一次替换当前分支。
6. **身份必须稳定。** 技能施放、Buff、投射物、能力实体、订阅和动作槽位都按保存的身份恢复，不能重新编号。
7. **失败必须暴露。** 缺少程序、宿主或引用时恢复失败，不能从头重算或吞错继续。

## 数据、程序和外部输入

战斗相关内容分为三类：

| 类别     | 内容                                                             | 保存位置                       |
| -------- | ---------------------------------------------------------------- | ------------------------------ |
| 战斗数据 | 时钟、资源、技能进度、Buff、随机流、实体、投射物、事件订阅和编号 | `CombatStateGraph`             |
| 固定程序 | 编译后的技能动作、Buff 定义、投射物回调、时间膨胀曲线和动作槽位  | 程序目录，分支间只读共享       |
| 外部输入 | 尚未提交的技能块、连续组计划、切人标记、人工事件和单块随机种子   | `CombatInputSchedule` 等调用方 |

程序可以读取或修改当前分支的数据，但只能在步进时执行。恢复阶段只按稳定身份把程序重新绑定到数据。
程序目录需要与切面匹配；分支可以在自己的目录中登记新技能块身份，不能污染父分支。

## 数据树层次

战斗数据集中定义在[切面数据模块](../../src/core/combat/state/README.md)，数据根位于
[combatState.ts](../../src/core/combat/state/combatState.ts)。当前层次如下：

```text
CombatStateGraph
├─ shared
│  ├─ clock / resources / timeDilation
│  ├─ comboWindows / ultimatePresentation / globalCooldowns
│  └─ identities
├─ inputs
│  ├─ initialInputPending / control
│  ├─ castParameters
│  └─ submitted skill and external-event state
├─ environment
│  ├─ random / vitals / reactions / knockDown
│  └─ buffProgress / poiseBreakBuffs / postSkillRequestListeners
├─ events
│  ├─ native
│  └─ semantic
├─ operators[operatorId]
│  ├─ blackboard / ability / skills / cooldowns
│  ├─ buffs / statuses / timedMarkers
│  └─ passives / equipment / initializations / upgradeEvents / comboConditions
├─ enemy
│  └─ buffs / statuses / timedMarkers
└─ instances
   ├─ abilityEntities
   ├─ projectiles
   └─ globalBuffs
```

这里画的是所有权关系，实际数据图可以有共享节点和循环引用。跨层引用保存稳定编号或明确的数据引用，
恢复准备阶段统一解析并保留身份；不为消除数据环复制节点。运行对象、缓存和回调不进入切面。

切面数据按共享基础节点、环境、动作、能力、动态实例和战斗根分成六个文件。运行时推进、恢复绑定和业务规则仍放在
各自模块中；状态模块不提供汇总导出文件，调用方直接导入所需层次。

## 完整帧顺序

新战斗和恢复战斗共用
[combatFramePipeline.ts](../../src/core/combat/runtime/combatFramePipeline.ts)。逐帧输入在固定阶段提交：

1. 处理上一帧结束后形成的主控状态和本帧切人；
2. 更新连携窗口等输入前系统；
3. 提交本帧技能输入；
4. 推进技能、Buff、投射物、时间和其他战斗系统；
5. 提交本帧外部人工事件；
6. 完成本帧回执并进入下一个稳定边界。

初始化完成后的首批人工输入可以停在同一帧提交，由 `initialInputPending` 明确记录。提交前不能推进，
提交后不能再次提交；恢复到该切面后可以改用另一批首帧输入。

普通整轴模拟可以使用编译好的固定输入计划。需要分支试算时，`CombatRuntimeSession` 进入逐帧输入模式；
此后省略输入只表示空帧，不会重新启用固定计划。

## 保存、恢复、分支和释放

公开入口定义在
[combatRuntimeSession.ts](../../src/core/combat/runtime/combatRuntimeSession.ts)：

- `save()`：复制当前 `CombatStateGraph`，保存技能登记表分支和固定回执视图；
- `fork(checkpoint)`：从保存点构造独立会话，父会话保持不变；
- `restore(checkpoint)`：构造并校验候选装配，成功后替换当前装配并增加 generation；
- `discardCheckpoint(checkpoint)`：显式断开仍被调用方持有的保存点；
- `advanceInputFrame(input)`：提交下一完整帧的输入并推进；
- `readState()`、`readHistory()`、`readReceipts()`：读取隔离副本或固定视图。

会话在推进、保存和恢复时禁止重入。步进抛错后会话进入 faulted；调用方只能恢复到有效保存点或销毁
该会话。恢复失败不会替换原装配。

检查点句柄只能交回创建它的会话或输入排程器。句柄使用 `WeakMap` 关联实际数据，避免全局目录永久
持有已丢弃分支。长期持有的句柄应显式释放，不能依赖某次垃圾回收时机。

## 恢复装配

恢复入口在
[combatRuntimeRestoration.ts](../../src/core/combat/runtime/restoration/combatRuntimeRestoration.ts) 及相邻恢复模块。
流程分为四步：

1. **预检**：核对程序版本、实体目录、Buff 容器、技能身份、回调程序和所有跨对象引用；
2. **建立外壳**：绑定时钟、资源、环境、干员核心、敌人和动态实例的数据；
3. **重建关系**：按保存编号连接技能、Buff、事件订阅、能力实体、投射物、子 Buff 和回调宿主；
4. **提交装配**：所有步骤成功后才返回可推进的 `CombatRuntimeAssembly`。

恢复不会调用普通初始化流程。普通初始化可能施加 Buff、注册监听或执行动作，先初始化再覆盖数据会产生
重复副作用。

清理旧宿主或失败候选时按依赖逆序执行。某个清理步骤失败仍继续清理其他宿主，最后再抛出错误，避免
一处异常留下整批监听和闭包引用。

## 身份与引用

以下内容不能靠数组位置或对象地址恢复：

- `castId` 与对应固定技能定义；
- 技能、能力实体和投射物的实例编号；
- Buff 实例编号、父子关系和来源施法；
- 事件订阅编号及同阶段顺序；
- 动作黑板作用域和伤害快照槽位；
- 全局 Buff 的子目标顺序；
- 主控干员和上一完整帧的控制状态。

跨对象引用先保存身份，恢复预检一次解析。不能在各模块里分别猜测来源，也不能用当前数组顺序代替原生
创建顺序。派生缓存必须在恢复后从已保存数据重建，而且不能影响事件顺序或编号分配。

## 随机状态

随机模式和期望模式使用同一份
[environmentState.ts](../../src/core/combat/state/environmentState.ts) 中的随机流数据结构：

- 全局模式和全局种子属于整场固定配置；
- 已提交技能块的种子选择进入 `submittedCastSeeds`；
- 实际消费过的选择进入 `usedCastSeeds`；
- 各伪随机流和期望均匀序列保存自己的整数进度。

随机源不接收整轴技能种子表。单块种子只在该技能输入实际提交时登记，登记本身不消费样本。恢复后可以
给尚未提交的候选选择另一种子；已经提交或消费的选择不能原地改写。

## 回执历史

回执历史不放进 `CombatStateGraph` 的 `structuredClone` 路径。详细设计见
[回执历史](combat-receipt-history.md)：

- 已确定前缀以不可变分段共享；
- 当前分支只追加自己的尾段；
- 保存点持有固定 `CombatReceiptView`；
- 增量 reader 只读取游标之后的新回执；
- 恢复保留同一历史前缀，不重放旧事件；
- JSON Lines 导出按 sequence 流式写出，不先物化另一份完整数组。

UI 中仍有需要数组的投影适配点。这些适配点应逐步改为视图或增量查询；不能在每个消费者中重新建立
完整回执索引。

## 连续组与外部输入

[combatInputSchedule.ts](../../src/application/simulation/combatInputSchedule.ts) 管理候选分支的外部计划。它保存：

- 已确认且尚未执行的输入；
- 连续组游标和活动/停止状态；
- 与具体 `castId` 一起提交的局部自定义技能程序；
- 战斗保存点对应的输入边界。

战斗切面不保存尚未提交的计划。输入排程器保存和分叉时同时处理自己的游标与战斗检查点。保存点之前
已执行的输入不可修改；已经启动或停止的连续组属于历史；未启动组及边界后的固定输入可以整体替换。

## 旧轴转换

旧轴转换在每个候选最早可能改变结果的帧之前保存。试算分支提交“保存点后已确认但尚未执行的输入”
以及当前候选；尚未转换的旧轴技能不存在于战斗或排程器中。

候选分支只用于观察实际开始、显示结束、连携边界和终结技时间膨胀。候选确认后，主会话推进已确认
前缀并建立下一个保存点。观察分支可能越过下一待定输入，因此不能直接接管为主会话。

最终生成的新轴仍完整运行一次，用来验证产物与转换报告。最终重跑是验收，不能掩盖候选试算错误。

## 内存与性能边界

当前实现对战斗数据做完整 `structuredClone`，固定程序和回执前缀共享。复制成本与当时仍存活的状态量
有关，不宣称常数复杂度。

优化顺序是：

1. 避免从战斗开始重复推进共同历史；
2. 及时释放候选会话、输入排程器和回执游标；
3. 将历史回执移出状态图复制路径；
4. 测量状态图各层、固定程序、投影结果和模块加载的实际占用；
5. 只对证实的热点考虑分块或写时复制。

当前真实长轴和完整转换循环未观察到持续堆增长，但进程 RSS 峰值仍高。具体数字及限制见
[耗时与内存分析](../research/combat/checkpoint-retiming-cost-analysis-2026-09-14.md)。后续内存优化必须先做
组成分析，不能只根据 RSS 或单次 GC 前后的总数猜测对象来源。

## 验收要求

每次修改切面边界至少验证：

1. 父分支、恢复分支和从头运行的完整状态、结果及有序回执一致；
2. 保存点前后覆盖技能开始/结束、Buff 触发、投射物命中、时间膨胀和事件回调；
3. 兄弟分支可使用不同输入和随机种子，互不污染；
4. 缺少程序或引用时恢复失败，原分支仍可继续或回退；
5. 首帧输入、同帧多个输入和连续组中途保存保持原顺序；
6. 丢弃候选和保存点后没有重型状态被全局目录继续持有；
7. 真实旧轴转换产物、报告和预期性能保持一致。

检查命令和当前结果统一记录在[切面任务清单](../handoff/runtime-checkpoint-plan.md)。
