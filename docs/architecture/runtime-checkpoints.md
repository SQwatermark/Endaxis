# 战斗运行时切面

后续实施顺序、任务边界和验收清单统一见[任务安排与验收](../handoff/runtime-checkpoint-plan.md)。
本文说明设计和实现依据，不再新增逐轮待办。

本文包含早期审查和实施依据，旧阶段的“尚未接入”说明不能覆盖当前交接。当前正式会话已有保存、
恢复、分叉与逐帧输入，旧轴转换已接入；回执不可变历史移出瞬时状态，具体见
[回执历史、查询与截面](combat-receipt-history.md)。全量验收及剩余过渡清理仍未完成。
缺陷证据和本次修改见[切面方案审查](../research/combat/runtime-checkpoint-audit.md)。

## 要解决什么问题

保存某个战斗帧结束时的状态，之后可以反复回到这里，尝试不同输入，不重新执行此前的战斗。
旧轴转换、编辑预览和随机分支试验共用这一能力。切面不是项目存档，也不是一份模拟结果。

基本关系是：**固定程序 + 当前状态 + 本帧输入 → 下一帧状态 + 本帧回执**。

| 部分     | 内容                                             | 保存方式                                 |
| -------- | ------------------------------------------------ | ---------------------------------------- |
| 固定程序 | 游戏定义、构筑参数、技能程序、动作处理函数       | 当前会话内只读共享                       |
| 当前状态 | 时钟、存活对象、资源、监听、待执行动作、随机流等 | 完整保存，与试探中的修改隔离             |
| 外部输入 | 本帧技能块、主控切换、手动事件、技能块种子等     | 到执行帧才交给运行时；未来计划不进入切面 |
| 回执     | 已经发生的伤害、状态变化和其他结果               | 保存分支自己的历史；只读前缀可以共享     |

“不知道未来”按**来源**划分，不能把所有未来才执行的东西都删掉：

- 尚未提交的下一次技能块属于外部计划，不保存。
- 已经释放的投射物、正在施法的后半段动作、Buff 的下次跳伤，都是过去造成的状态，必须保存。
- 原生机制已经产生的待施放请求也必须保存；它不同于编辑器之后准备放下的技能。
- 连续组尚未提交的后续成员留在外部排程器。排程器已观察到的块结束、前驱关系等另有自己的
  可恢复状态，不能依赖被其他试探原地改写的回执数组。

## 切面之间只有分支和回退

切面的派生关系是一棵树：每个新节点只有一个来源，不支持合并，也没有多父节点。
恢复旧切面后尝试其他输入，会产生另一条分支；已有分支仍可再次恢复。恢复本身不执行业务，
也不删除其他切面。不实现差异合并、冲突处理或内容相同节点的自动合并。

这是一条语义约束，不要求运行时永久保存整棵历史树。调用方只保留需要回退的切面，
无人持有的切面可以被回收；不能为了记录父子关系让全部试探历史一直占用内存。

历史关系是树，单个切面内部的数据仍可以共享引用。例如多个技能共用一份冷却，
保存和恢复后也必须共用同一份冷却，不能拆成多个独立副本。

## 状态集中保存，行为仍按模块组织

采用一个完整的 `CombatState` 数据根对象，由会话统一持有。技能、Buff、事件、伤害等模块
继续各管各的规则，通过当前状态工作；不需要把所有业务写进一个大类，也不必为此引入 ECS 框架。

所有影响后续模拟的可变内容，都必须能从这个数据根对象遍历到。动态对象通过 ID 相互引用，
不能把某个 Buff 实例、SkillRuntime 实例或其方法闭包当成可恢复的数据。

具体约束：

1. 状态里保存动作位置、宿主 ID、程序 ID、事件上下文和启用标记；处理函数放在只读程序里。
2. 监听器保存为数据条目，包含触发条件、顺序号及动作引用；注销修改条目，不依赖闭包里的
   `disposed`。动作的 `finished`、执行一次的标记也同样处理。
3. 随机流保存当前整数状态、流身份和期望模式的计数器；恢复后继续取样的结果必须相同。
   只保存原始种子、或者保存随机函数本身都不够。
4. 模块可以在一次同步调用内暂存当前状态引用，不能把它跨帧留在成员、闭包或回调里。
   下一次调用应重新从会话取当前数据，避免恢复后还在修改旧分支。
5. 只读程序不能捕获会话的可变对象。自定义数据仍走统一编译；有任意私有状态的外部回调，
   必须先把状态归入明确的数据结构，不能承诺自动保存任意 JavaScript 对象图。

数据与逻辑只在受控步进中相遇，开局初始化也不例外。构造初始数据不执行业务回调；初始化动作
应在明确的执行阶段运行，结束后才取得 `beforeFirstInput` 切面。观察层读取独立数据副本，
不能拿着运行时对象直接调用动作。JavaScript 没有借用检查器，内部算法仍必须遵守不保留数据
引用的规范；不靠给全部读写加 Proxy 来补救隐藏的所有权问题。

先实现完整状态复制，作为正确性基线。保存和恢复都复制当前可变数据，保留 `Map`、`Set`、
数组的语义和遍历顺序；共享的仅是明确只读的程序及历史块。不使用 JSON 序列化复制运行时。
状态内部也不能靠 `Object.freeze(new Map())` 获得隔离，它阻止不了 `set()`。

## 整场数据的归属与尚未完成的接入

正式装配已有 `CombatSharedState`，连接时钟、资源、时间膨胀、连携、演出、全局冷却、
普攻继承和编号分配器的实际数据。它只是共享层，不含完整实体、动作和事件目录。
`CombatStateGraph` 在共享层之外接入能力实体、投射物和全局 Buff 的数据目录；这些目录
随正式创建和清理更新；来源宿主数据已收齐，标准环境与完整装配的统一对象重建尚未接通。
能力实体目录已包含正式子技能的局部进度、黑板、目标、作用域、时间轴序列进度与攻击快照，
并保留子技能黑板对实体黑板的共享引用。目录本身可以无副作用地绑定保存的实体、黑板和定时
标记；子技能、子 Buff 和 reset 回调在关系阶段接回。每个子技能状态保存会话内固定程序编号和
技能身份，程序目录持有具体已编译动作与伤害快照槽位映射。恢复按编号取得原程序并继续时间轴，
不调用 Start，也不重复加入状态数组。该目录属于同一切面树的只读程序绑定，不随分支数据复制。
普通技能宿主已接入 `operators` 下各干员的 `skills`，仅在实际创建宿主时登记。
每个干员节点同时包含实体黑板和能力系统状态，当前技能、延迟施放请求及技能槽选择不再遗漏
在技能目录之外；技能黑板与该干员节点引用同一实体黑板。
干员和敌人节点还包含通用语义状态及定时标记。语义状态保存层数、剩余帧和首次来源，
未配置该系统时明确为 null；它不代表所有 Buff、附着和控制系统都已接入。
提供容器数据端口的 Buff 目标已接入干员/敌人的 `buffs` 字段，保留容器与技能的实体黑板
共享关系。这里的 null 表示端口尚未提供数据，不表示该目标没有 Buff；完整恢复入口不能忽略
这一缺口。Buff 动作与监听绑定仍未全部接入。
能力实体自身的 Buff 容器也挂在对应实体节点；单独记录容器是否已创建，以区分按需创建前的
空状态和“已创建但外部端口没有暴露数据”的缺口。实体、子技能和容器仍共享同一实体黑板。
Buff 实例的 `actionHost` 已包含生命周期作用域、目标组、攻击快照、启用/触发序列进度、
普通事件响应的订阅与序列状态、定时动作的局部帧和调度进度，以及定义级技能槽替换状态。
恢复时直接接回这些数据，不重置响应、不申请新订阅编号、不重放已过帧，也不重新应用槽位。
SkillAffix 的来源施放编号、引用数、待转交请求和注销标记已进入 `actionHost.affixes`，
请求去重、转交和引用释放使用数据函数。完整注销后移除活动记录，避免反复启用积累无用数据；
它还保存五类 Ability 事件订阅、预施放请求、每份对象引用及对应回收/重置回调的稳定登记编号。
恢复先按编号重绑事件和请求，再在所有 Buff 实例重建后进入关系阶段，解析当前分支的实体或
Buff，并把回调绑定到原登记编号。回收通知同步移除对象引用；生命周期事件只补充实例编号，
不改变事件的来源/目标解析。函数和注销端口始终属于当前分支的程序绑定，不写入切面数据。
目前这套协议已有 Buff 子系统证明，但标准环境尚未提供跨干员、敌人和能力实体的统一解析端口，
所以仍不能从完整 `CombatStateGraph` 恢复整场战斗。
相同固定定义、相同已执行前缀，但未来块 ID 和初始黑板不同的装配测试，得到相同的已接入
数据图；提交未来块后才出现对应宿主。此检查不覆盖仍在图外的可变数据，也不覆盖缺少固定
定义、仍预建宿主的旧装配路径。

下面是目标层次，不是已经接通的 `CombatState` 接口。不能把现有对象上的若干
`runtimeState` 拼起来，就宣称已经能保存整场战斗。

| 数据归属                     | 必须包含什么                                          | 当前缺口                                                                                                                       |
| ---------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 全场时间与编号               | 战斗帧、时间膨胀、实体和施放编号                      | 已有数据结构，仍需统一程序绑定和整场根接入                                                                                     |
| 全场资源与结果               | 技力、生命、失衡、随机流、回执历史                    | 数据已部分接入模块；回执仍是可变数组，尚未实现只读历史块                                                                       |
| 实体目录                     | 干员、敌人、能力实体及各自的黑板、状态、标记          | 能力实体数据已有目录；子技能、生命周期绑定和其他实体尚未统一                                                                   |
| 技能与动作实例               | 施放进度、动作树、目标上下文、共享冷却、附着 Buff     | `SkillRuntimeState` 已连接施放、黑板、共享冷却、作用域、攻击快照和时间轴序列进度；具体动作状态未收齐，装配仍预建未来技能块宿主 |
| Buff 与监听目录              | Buff 实例、叠层、子实例、属性修改、监听顺序和注销关系 | 部分关系已改为 ID；仍有对象绑定和闭包持有可变状态                                                                              |
| 全场交互机制                 | 连携候选、暂停、QTE、终结技演出状态                   | 连携、演出标记和全局冷却已各自集中；仍需连接整场根，不能由 UI 反推                                                             |
| 外部排程器（不在战斗切面内） | 未提交的技能块、主控切换、种子计划、转换试探计划      | 输入阶段已分开，装配与未来计划仍未彻底分离                                                                                     |

目录负责拥有数据，跨目录关系用 ID 查找；确实共用的数据只有一份。例如共享冷却不能在
每个技能下各存一份。程序绑定不属于上述可变数据，恢复后必须按当前数据重新解析，
不能让旧对象或旧句柄继续修改被放弃的分支。

完成标准是：正式装配的全部可变状态均有归属，统一恢复后能重复运行同一分支，并通过不同
输入分支、真实轴结果、异常回退和内存检查。之后才接入旧轴转换的前缀复用。

### 动作树与事件订阅

护盾对象已支持绑定保存的 `BuffShieldState`，不重新读取属性计算最大值、吸收参数，也不
补满余额。Buff 容器的基础恢复入口会直接绑定复制后的属性、实体黑板、实例、叠层组、修正器、
护盾和父子关系，不执行 Add、Start 或 Enable。测试覆盖两层 Buff、计时推进、部分吸收和父子结束，
恢复分支耗尽护盾不会结束原分支实例。启用/触发序列、普通事件响应、局部定时动作、定义级技能
槽替换及 SkillAffix 也可按保存状态重绑；测试确认事件编号、`once` 进度、定时动作游标、槽位
应用状态和对象回收登记不变。旧式自定义持续动作没有显式恢复协议时仍明确拒绝。

同步次数循环、结束时间轴和到达可操作边界步骤已标明自身无跨帧数据，并支持重新绑定。
循环体每次同步执行完毕，循环次数不需要额外存进切面。测试确认恢复后不会重放已执行步骤，
显式重置后再次执行则使用新分支端口。投射物寿命与回调步骤仍需先迁移其外部宿主绑定，
目前仍拒绝恢复，不能把“步骤对象没有字段”当成整个派生行为已经可恢复。

投射物寿命目录已能接收保存的数据，按实例编号重绑推进、结束与回收端口，按原订阅编号
重绑 reset 处理程序。恢复不会重新发射、分配编号或执行回调，必须提供已恢复的编号分配器，
并拒绝在能力推进阶段中间恢复。测试覆盖飞行中、已结束和待回收三个阶段，以及旧注销对
新分支无影响。回调技能宿主的状态和完整装配接线仍待接入，不能只恢复寿命目录就继续整场模拟。

回调技能宿主已提供 `CallbackSkillHostState`，一起保存技能数据与能力系统数据；工厂可用
保存的数据重建宿主，不重建局部黑板、不重新施放、不分配施放编号。恢复仍需提供当前
分支的动作执行器、Buff 查找和固定伤害快照程序。测试从技能中途恢复，验证后续逐帧
状态、回执与命中次数一致。

投射物目录现已通过 `callback` 保存发射时的独立黑板、来源施法和回调技能身份。命中前
`host` 为 null，命中时挂入实际宿主的技能与能力数据。测试确认飞行中的切面不会随原分支
命中而出现宿主。固定回调程序的定位和完整恢复工厂仍待接通，当前不能只凭技能名恢复所有回调。

回调程序不能以 `skillId` 或动作 `key` 作为恢复索引：`compileSkill.ts` 会按技能等级解析
回调的黑板、费用和子动作，同名技能可能对应不同的已编译程序；动作 `key` 本身也允许缺省。
正式投射物目录现已持有 `ProjectileCallbackPrograms`，按已编译程序对象登记编号，
发射时把编号写入 `callback.programId`，切面不复制程序。
多个分支共享目录及程序，不能在恢复时按新遍历顺序重新编号，也不能按内容相同合并动作。
目录不保存操作执行器、实体宿主或回调函数；这些绑定必须由恢复分支重新创建。
寿命目录恢复时会检查编号存在且技能身份一致。调用方须传入原战斗共享的固定目录，
不能换一份目录重新分配相同编号。`callback.skillId` 仅供核对身份，不能用它直接查找程序。
回调宿主恢复工厂仍需接通到投射物阶段推进，这部分尚未完成。

正常发射动作已改用 `ProjectileCallbackRuntime` 统一命中、推进和回收逻辑。该绑定层
收到未命中数据时不会创建技能；收到已有宿主数据时立即重新绑定，但不调用 start。
恢复工厂必须返回引用同一份保存数据的宿主，否则报错。测试通过这一绑定层推进恢复后的
真实回调技能，逐帧状态与回执一致。整场恢复时仍需按程序目录和来源重建工厂及动作执行器。

固定回调程序目录也持有对应的伤害快照动作编号映射。正式回调工厂让同一程序的宿主共享
这份映射，攻击数值仍在每个宿主的数据中独立保存。恢复时不能换另一份映射，否则保存的
数字槽位可能指向错误动作；工厂对此进行身份检查。测试覆盖编号映射共享、数值容器独立，
以及带目录的回调宿主恢复后逐帧结果一致。

`restoreProjectileCallback` 已负责按保存数据重建黑板、来源施法和投射物实体身份，并从固定
目录解析回调程序与伤害快照映射。调用方只提供当前分支的动作执行器、投射物端口和 Buff 查找。
测试覆盖未命中时不提前创建宿主，以及已命中后逐帧推进一致。整场装配仍需调用此入口，
并恢复对应来源的执行器；目前尚未开放完整战斗保存/恢复。

投射物联合恢复测试已将寿命目录、回调恢复入口与阶段推进接在一起。分别在第 1、3、5 帧
保存，覆盖命中前后；恢复后推进到最终回收，每帧核对整个投射物目录及回执相同。
`bindProjectileCallbackLifecycle` 负责将回调绑定接到能力推进和寿命推进端口，恢复时不重发射。
该测试使用真实回调技能宿主，但没有整场的伤害、Buff 和来源执行器，不能替代整场回归。

动作序列的 `steps` 按执行步骤下标连接内部数据。条件和 Switch 包含选择结果及各分支
子序列；重复动作、目标循环和时间轴跳转连接各自的计时与执行状态。尚未提供数据的
步骤留 `null`，因此这棵树仍不能作为完整恢复入口。
黑板作用域包含执行时创建的子序列及其实际黑板；重置时清空当前子序列。
监听动作包含已安装的响应序列，结束或安装失败时清空。每项响应记录事件目录引用、
事件名、阶段和注册编号；队伍订阅及同时监听原生事件和手工标记的响应保留全部引用。
复制后这些引用仍指向同一份已复制的目录。事件中心可以按原编号绑定处理函数，
不重新注册，也不改变原有顺序；跨目录、失效引用和重复绑定都会报错。
整场宿主如何生成这些处理函数还未接完，不能把事件中心的局部重绑当成整场恢复。

`createSequence` 可接收已复制的序列数据，重新构建执行绑定而不调用 Execute 或 Reset。
已接通条件分支、Switch、重复动作、目标循环、黑板作用域和跳转；操作步骤只连接调用端口，
其执行器自身的数据仍须由宿主恢复。尚未支持的步骤会拒绝绑定，序列长度不匹配也会报错。
局部测试已验证分支不重新求值、循环不重放首次触发、目标不重新选择、子黑板不重新初始化。
监听动作已能把响应序列和保存的订阅重新绑定：不重置响应、不申请新编号，也不在绑定时执行动作。
原生事件由环境提供绑定端口，负责查找对应目录和补回事件目标上下文；手工事件在语义事件中心内绑定。
这些端口还未接入整场恢复装配，也没有整场原子替换入口，不能用于正式转换器恢复。

动作宿主可以绑定已复制的作用域数据，后续新序列继续遵守已有 once 标记并复用缓存黑板。
`createTimeline` 也能绑定调度进度和序列树，恢复时不会重放区间开始或重置动作。
保存的序列数组按开始帧排序，恢复时通过程序来源下标对应配置，不能假定配置本来就有序。
测试覆盖了活动区间继续执行、后续区间正常启动，以及这些过程与未中断执行逐帧一致。

技能宿主也已提供绑定入口：恢复施放进度、初始和当前黑板、目标、共享冷却、作用域、
攻击快照和时间轴。初始黑板单独保存，不能用施放过程中已修改的值替代。
附着 Buff 由当前分支按引用解析，缺失时拒绝恢复；共享冷却也必须指向恢复后的同一份数据。
局部用例验证了继续执行的状态与回执逐帧一致、结束时使用新分支 Buff 绑定，以及再次施放恢复初值。
这个入口要求调用方先恢复操作执行器和事件环境，不会替代整场装配，也尚未接入旧轴转换。

普通干员技能现在由 `CombatSkillPrograms` 保存固定程序绑定。键由干员、技能和施放块身份组成；
同一键在一棵切面树中只能绑定同一个编译程序对象。每项绑定同时持有伤害快照的动作槽位映射，
正式新战斗已经从该目录取得映射。恢复分支必须沿用原目录，不能重新遍历动作生成另一套槽位。
整图预检会把候选中的每个技能状态配到当前定义和该固定绑定，并将结果作为下一对象创建阶段的
输入。候选状态有定义但原目录没有对应绑定时直接失败，不能临时登记一套看似相同的新程序。

`bindRestoredCombatOperatorSkills` 把预检项、恢复后的共享冷却、当前分支操作执行器和 Buff 引用解析
组合成普通技能宿主。它把保存的动作宿主状态显式交给执行链，并要求执行链公开的状态就是同一对象；
随后复用固定伤害槽位和保存的技能数据构造 `SkillRuntime`。绑定过程不调用 TryStart、不申请施放编号，
也不推进时间轴。联合测试从技能中途继续，逐帧核对技能、能力系统和回执与未中断分支一致。

恢复后的技能由 `bindRestoredCombatOperatorAbilitySystem` 装入保存的能力系统状态。技能数组只包含
已经存在于切面的施放宿主；冷却推进计划则来自完整共享冷却目录，因此从未施放过的技能仍会推进。
槽位组、输入路由、模式定义和实体动作运行时继续使用当前固定干员程序，当前技能、处理中技能、
槽位替换、模式层及延迟请求直接读取保存状态。构造时不会再次启用默认模式。冷却就绪观察者只在
保存账本实际跨过就绪边界时调用。

能力系统已能绑定保存的选择、技能槽和模式状态，不再覆盖为构造默认值；恢复时会核对
技能定义之间的类型一致性、槽位定义和模式定义，当前技能缺少绑定会报错。运行中改过的
原生技能类型按切面保留，不要求等于初始类型。技能与能力系统共同恢复的
用例已验证继续推进后的两层状态和回执逐帧一致。模式切换记录原模式及登记编号，
结束时删除登记，可按原编号重建结束句柄，重复结束无效。

形态切换动作已直接在动作树中保存登记编号，执行器不再用 WeakMap 保存该动作的回调句柄。
执行和结束步骤时临时挂接这份数据，调用完成后还原上下文；恢复只重新绑定，不重放切换。
测试覆盖恢复后结束动作只还原新分支，旧分支仍保持原形态。普攻映射动作也已保存登记编号，
恢复不会改变映射顺序，结束时只删除自己的登记，不删除后来添加的映射。
两类动作共用登记编号的数据结构，实际撤销规则仍分别执行。
技能槽替换的登记编号、还原技能和冷却继承选项已放入能力系统数据，不再由装配层闭包保存。
安装新替换前先撤销同槽旧替换；结束时先删除登记，再还原技能并读取当前冷却进度。
动作树现已保存技能槽替换的登记编号，执行器不再持有结束句柄。恢复动作不重新替换技能，
结束时向当前分支传递槽位和原登记编号；无限期替换仍不会随动作结束而撤销。
动作层测试已覆盖恢复后的结束入口隔离。替换与撤销算法已移入 `abilitySystemExecution.ts`，
正式装配层通过执行端口提供槽位操作、冷却继承和回执。联合测试复制能力数据与真实冷却账本，
确认恢复后撤销读取该分支当前的进度，旧编号不能撤销新替换，原分支不受影响。
这仍是替换子系统的联合测试，不代表完整战斗装配已经支持恢复。

每个干员的数据中另有 `cooldowns` 目录，按技能身份保存全部已装配的共享冷却账本。
没有施放实例的技能也必须保存冷却；不能只从 `skills` 中收集，否则会漏掉这类技能。
技能实例和该目录引用同一份数据，整体复制后仍保持共享，避免恢复后同技能各算一份冷却。
测试已覆盖没有实例的账本，以及定义技能、施放实例、冷却目录三者的引用关系。

冷却的固定周期解析和恢复绑定现集中在 `combatSkillCooldownRestoration.ts`。面板中的冷却乘区只在
固定配置阶段计算，切面保存当前计时与预占状态；恢复对象直接绑定该状态。连携技能的动态冷却倍率
仍在实际预占时从当前分支 Buff 目标读取，不保存旧对象回调。恢复会核对冷却目录完整性和计时器
形状，配置为无冷却的技能不能带计时器，配置为有冷却的技能也不能缺少计时器。

默认场景模拟的随机状态已接入 `environment.random`，保存实际消费的暴击流、概率流和期望
序列计数。两种模式都验证了复制后继续取样一致，原分支推进不会改变保存的数据。
如果使用自定义样本源且没有完整状态端口，这里为 null，不能据此开放恢复。
随机模式设置与种子配置仍由外部绑定提供；之后技能块的种子表不复制进这份随机数据。
整场恢复入口也尚未接通。

标准环境的 `environment` 数据已接入敌人与干员的生命、失衡账本，以及元素反应等级和到期时间。
这些字段引用实际执行的数据；后续创建的干员账本会加入同一目录。普通倒地的活动状态和计时器
也已接入，恢复时必须配合同一份实体 Buff 标签。Buff 进度记录已保存原始采样、时长分母
和活动实例索引，恢复后可继续采样；旧分支结束不会截断新分支的曲线。环境构造器可以直接绑定
上述数据、失衡 Buff 实例集合、预施法监听目录和原生事件目录，不重新初始化账本或登记监听。
随机数据存在时，样本源必须显式绑定同一份状态；普通倒地数据存在时，也必须提供同一固定规则。
各来源处理函数、Buff 容器和跨对象关系尚未全部接线，因此环境整体仍不能独立恢复战斗。

失衡增伤 Buff 的待清理列表已改为容器内实例编号。失衡恢复时从当前敌人容器解析，
不持有旧分支 Buff 对象，也不按 Buff 定义 ID 批量清理。已回收实例跳过；数据尚在但执行绑定
缺失会报错，不能静默漏掉清理。

整场数据图的 `events` 分别保存原生实体事件目录和手工语义事件订阅。
目录引用各事件中心实际使用的数据，随后新建的实体也会登记到同一个目录。
订阅阶段、优先级、注册编号和注销结果可随数据一起复制；回调函数仍在宿主中，
整场宿主的恢复接线尚未完成。环境没有提供原生目录时明确记录为 `null`，不能当作空目录。

## 保存时刻与输入顺序

### 当前技能目录不能直接保存

`CombatRuntimeAssembly` 已对具有无 `castId` 固定定义的放置块改为提交时创建；没有独立定义的
旧装配输入仍会预建宿主，这条路径尚待清理。即使某个宿主还处于 `ready`，它的存在和身份也已经
透露未来排轴。因此，下一步不能简单把当前技能对象表映射成状态表后接入切面。

必须先分开固定技能定义、已提交施放实例和外部排轴块：

- 固定定义按干员和技能查找，提供可施放性、技能槽和内部 Cast 所需的程序。
- 输入阶段提交具体技能块时，才创建或绑定这次施放的数据实例；不能提前把未来块的黑板、
  随机种子和编号准备进当前状态。
- 同技能的冷却仍在共享账本中推进，不能因宿主改成按需创建而停止未施放技能的冷却。
- 过去施放产生的投射物、Buff 和待施放请求仍归当前战斗，不能随输入块目录的拆除一起删掉。
- 转换器需要查询先前技能的显示结束时间，应从已经提交的施放事实读取，不能要求未来宿主存在。

验收时使用两份前缀相同、后续技能块不同的计划：执行到相同前缀后，战斗数据应相同。
仅比较最终伤害不足以证明没有读取未来。

能力系统已提供 `registerCastInstance`，可在输入阶段把新施放实例加入已有技能定义对应的
寻址表与推进列表；重复 ID、缺失定义或类型不匹配时，在写入前拒绝。共享冷却仍由原账本
每帧推进一次。正式装配已在提交有固定定义的技能块时使用该入口；外部计划仍以延迟装配器
保留在装配对象中，尚未完全移出会话。共享冷却就绪回执只记录干员和技能，不再任意选择一个
放置块的 `castId`。不能据此宣称未来输入隔离已全部完成。

只开放两个稳定边界：

- `beforeFirstInput`：初始化完成、首批外部输入尚未执行。
- `afterFrame(f)`：第 f 帧的所有阶段、同步事件和本帧清理都已完成。

从 `afterFrame(f)` 前进时，接收第 f+1 帧的完整有序输入批次。首帧有独立的初始边界，
不能把“尚未执行第 0 帧”和“第 0 帧已经执行完”混成一个数字 0。

同一帧的输入仍在现有规定的阶段执行，保留技能输入、主控切换、强制命中等的先后顺序。
批次只是外部交付形式，不能借改造之机把现有帧阶段合并或重排。

连续组还有一个特别要保留的边界：`CombatInputRuntime` 在输入阶段开始时检查前段是否结束，
此前本帧的 Buff、实体等阶段已经运行。不能在上一帧末尾预先决定下一段，否则会晚一帧。
外部排程器应在指定输入阶段得到只读查询机会，提供当时的就绪候选，并按输入结果推进自己的状态。
固定输入接管本轨道后停止旧组、本帧新启动的组不再推进第二段等规则都要保留。
阶段内仍不允许保存切面；排程器不是能任意修改战斗状态的插件，也不能借回调把未来计划藏进状态。
下方的 `step(inputs)` 仅演示固定输入；动态排程接口须先用连续组的阶段回归验证，再定最终签名。

帧正在执行、事件回调尚未退栈时，拒绝保存或恢复；不试图保存 JavaScript 调用栈。
执行抛错后会话进入故障状态，只允许恢复已有完整切面或销毁，不能继续推进半帧。
保存/恢复的重入锁不能替代这个执行阶段检查。

示意接口如下；这是语义说明，暂不作为正式 API 发布：

```ts
const base = session.save();
session.step(inputsForNextFrame);
const branchA = session.save();

session.restore(base);
session.step(otherInputsForNextFrame);
const branchB = session.save();

session.restore(branchA); // A、B 都是独立有效的切面。
session.restore(branchB);
```

## 恢复必须一次性替换

恢复分成准备和提交两个步骤：

1. 检查切面身份、所属会话及程序版本，在当前状态之外复制目标数据并重建必要索引。
   任一准备步骤失败，当前状态保持原样。
2. 准备全部完成后一次性换掉会话的当前数据根对象，并换代外部观察缓存。
   提交步骤不分配复杂对象、不执行游戏逻辑，也不调用可抛错的业务钩子。

不能依次调用各模块的 `restore`，指望反向注册顺序解决对象依赖。Buff、资源、监听、技能之间
存在相互引用；中途抛错会留下新旧混合状态。恢复时也不能调用 `finish`、`dispose` 或初始化
来清理旧对象，这些操作可能触发伤害、资源变化和新的监听。旧数据只失去引用，由正常内存回收处理。

切面本身只通过不可伪造的会话令牌访问内部数据，不公开可变载荷。保存得到的数据与工作副本隔离，
每次恢复再生成独立的工作副本；试探不能修改源切面。同一切面可以反复恢复，保存 A 后回到根切面
运行 B，也不能使 A 失效。首版只支持同一会话、同一固定程序；跨进程和跨版本存档不在范围内。
以后若需要并行分支，可共享固定程序、分别持有状态，不能共享可变运行时。

复用切面还要检查编辑位置。构筑、敌人配置、游戏定义、模拟模式或全局种子改变时，重建会话；
不能恢复旧切面后只换一张定义表。修改外部输入时，仅复用早于最早受影响阶段的切面。
技能块种子及该块的强制命中设置随本次输入进入实例上下文，派生行为继承已提交的上下文，
不能每次取样再去查询一张包含未来技能块的整轴配置表。

## 对象身份与缓存

内部 ID 分配计数器、对象创建顺序和监听注册顺序都属于状态，要随切面恢复，保证重跑一致。
外部持有的可操作句柄则带会话与运行代号：一次恢复后，旧句柄不能操作新分支，即使内部数字 ID
恰好相同。只读 UI 可以按业务 ID 重新查询。运行代号不进入伤害、随机种子或内部排序。

缓存按用途处理：

| 种类                                                 | 处理                                   |
| ---------------------------------------------------- | -------------------------------------- |
| 只依赖固定程序的查询表                               | 只读共享                               |
| 能由当前状态完整推导、且重建顺序不影响结果的索引     | 不进切面，在准备阶段重建或按代号失效   |
| 历史计数、注册顺序、增量扫描位置、影响后续判定的结果 | 属于状态，保存或改成明确等价的纯推导   |
| UI 投影、伤害汇总、导出结果                          | 留在观察层，按已发布分支和运行代号更新 |

例如连续组的结束边界扫描器、主控变化的上次观察值，看起来像缓存，实际上会影响后续事件，
不能漏掉。不能仅凭“可以重新算”就排除状态：必须证明重建不会改变浮点计算顺序、随机消费或事件顺序。

## 分支回执与内存

回执用于解释结果，但保存到第 f 帧不应每次复制从第 0 帧以来的全部日志。
使用不可变分块前缀加当前尾块：保存时封存尾部；恢复切换到对应分支的日志根，之后另开尾块。
封存成本与固定的尾块大小有关，读取完整数组只在选定结果需要展示或导出时进行。
不能用单个可变数组加长度截断代替分支日志，那只能返回祖先，无法恢复已经离开的兄弟分支。

回执载荷也要在记录时取得所有权，或复制为只读数据。只冻结外层回执、仍引用调用方的可变对象，
会让旧切面里的历史跟着后续修改变化。回执序号在分支内确定，观察层结合运行代号识别结果。

试探不向 UI 发布中间结果，不写外部文件或调用外部观察钩子；调用方选定分支后才发布。
游戏内部事件仍在试探中完整执行，它们是模拟的一部分。观察层输出和游戏事件不能混成一个入口。
切面和分支结果有明确释放时机，转换器只保留必要的基点及候选，不无限保存每一帧。

## 必须覆盖的状态

下表是迁移审查清单，不是按表增加一批 `capture/restore` 适配器。

| 范围             | 必须考虑的内容                                                        |
| ---------------- | --------------------------------------------------------------------- |
| 帧与阶段         | 全局帧、局部时钟、稳定边界、各时间域推进状态                          |

迁移还必须检查构造过程。当前装配会提前为将来的技能块创建 `SkillRuntime`，并接收完整控制和

挪到输入循环里就认为完成。

## 旧轴转换怎样使用

需要区分**已确认的战斗前缀**和**为了知道技能显示结束而向后运行的试探**。

例如 A 在 100 帧开始，试探运行到 220 帧才知道 A 的技能块结束；下一个其他轨道的 B 可能要放在
130 帧。不能直接把 220 帧的状态当成已确认前缀。应保留较早切面，带着已确定的 A 输入推进到
B 之前，再尝试 B；220 帧只是本次探测结果。B 的时间膨胀还可能改变 A 的最终显示结束。

转换器应保持以下规则：

1. 继续由旧轴全局顺序和用户规定的三项最大值决定候选；时刻取正式模拟和显示投影结果。
2. 外部保存已经选定的输入前缀；选定一个候选，不等于可以保留它探测到的最远状态。
3. 基点只推进到不会再补入输入的位置。需要在同一帧补入另一条轴的输入时，从该帧之前恢复，
   用完整、有序批次重跑这一帧。不能把同一帧当成只可追加而不影响已执行步骤。
4. 探测接续许可时先逐帧检查。允许接续的窗口可能打开后关闭，二分和指数跳步会漏掉短窗口。
   可以利用切面减少历史重放，不能用未经证明的单调性减少检查。
5. 每次试探都恢复运行状态与外部排程器状态；模拟回执与投影必须来自同一分支。
6. 临时缺少技能块结束意味着还需向后推进；完整合法输入运行后仍无法得到应有结果，则排查程序
   错误，不能伪造时长掩盖问题。

窗口搜索可再减少两种重复工作：维护一个不含本次候选输入的基准分支，随候选帧单向前进；
每次保存基准、加入候选及其主控输入、执行完整一帧。若该帧已经报告不可接续，就恢复基准，
让不含候选的分支再前进一帧，不必把失败候选运行到技能块结束。找到允许位置后才继续该试探，
取得显示结束等规划结果。失败诊断必须确认在该帧产生，不得用尚未发生的结果提前判断。
这是转换器决定放弃试探，正式模拟仍按现有规则执行输入并报告诊断，不新增阻止施放的门禁。

成本由这些部分组成：一次程序编译、已确认前缀的推进、各试探区间的推进、状态复制、索引重建
和输出整理。不能直接承诺整体 `O(N)`：如果同时存活状态随 N 增长，每次复制仍可能累计为
`O(N²)`；如果试探区间越来越长，也有同样问题。

分别测量编译次数、执行帧数、保存/恢复耗时、活跃状态大小、日志整理、峰值内存和释放后的留存量。
短轴、长轴、多 Buff、长投射物、长时间膨胀都要覆盖。首先消除重复编译和从零重跑；只有测量证明
状态复制是瓶颈，才针对具体容器引入分块写时复制。

## 为什么先不选其他实现

| 方式                       | 决定及原因                                                     |
| -------------------------- | -------------------------------------------------------------- |
| 显式状态全量复制           | 首版采用；最容易验证是否完整，也便于和从头模拟逐项对照         |
| 分块写时复制               | 以后按测量局部引入；必须覆盖全部写入口，不能假定浅拷贝自然安全 |
| 每次写入记录撤销操作       | 暂不采用；当前对象、闭包、嵌套事件太多，遗漏一次写入就破坏恢复 |
| 从初始输入重放             | 保留为正确性对照；它不能满足快速回退的性能目标                 |
| 通用 JavaScript 对象图克隆 | 不采用；类私有字段、闭包状态和外部引用没有可靠通用复制方式     |

## 实施顺序与验收

### 当前实现进度

已经拆出并接回现有模拟的算法如下。旧调用口负责连接尚未迁移的技能与 Buff 宿主，不再各自
保留另一份算法；它们目前仍不是完整的可恢复战斗实例。

- `buffTriggerState / buffTriggerExecution`：周期触发的余量、次数和同步停用检查。
- `abilityEventState / abilityEventExecution`：订阅编号、阶段、优先级与分发顺序；状态没有回调，
  注销也不再依赖闭包里的 `disposed`。
- `projectileLifecycleState / projectileLifecycleExecution`：寿命、来源、分阶段回收、准入集合和
  reset 订阅编号；结束及 reset 逻辑由当前执行端口按编号解析。
- `simulationRandomState` 与取样函数：随机流整数状态及期望模式计数；算法不再把状态封进函数。
  新取样函数只接收本次技能块的种子，旧整轴种子查找暂留在未迁移的调用口。

内部工具 `StateStepper` 管理一个明确完整的数据根，提供受控执行、独立读取和整体保存/恢复。
执行上下文离开本次调用后失效；步进中不能保存、恢复、读取或重入。输入、输出、观察数据和切面
均与工作副本隔离。执行出错后只能恢复或销毁，恢复准备失败不改变当前状态。
复制前拒绝函数、访问器、类实例和隐藏字段，避免 `structuredClone` 静默丢掉私有状态。

`statefulExecutionBranch.test.ts` 在一个小型完整状态上串联上述生产算法，验证 Buff 触发事件后
发射的投射物在关闭 Buff 的分支中仍会命中，并对比两种随机模式、兄弟分支和从头重放的完整数据。
这不是正式技能程序、完整 Buff 容器或整场装配已经迁移的证明。

迁移回归及真实轴逐回执对照结果见[审查记录](../research/combat/runtime-checkpoint-audit.md#首次状态迁移验证)。

目前还没有把技能实例、完整 Buff 持续动作、完整事件宿主、外部输入排程和分支回执共同装进
可恢复的整场状态。`StateStepper` 也不负责游戏帧阶段或分块日志；这些必须随装配层迁移完成。
不能把旧 `CombatRuntimeAssembly` 放进它的状态里，也不能只塞已迁移模块后向转换器开放保存入口。

动作序列的执行进度也已拆出：`actionSequenceState.ts` 保存每一步的生命周期、执行结果和
进入时的许可，`actionSequenceExecution.ts` 负责同步推进。现有 `ActionSequence` 调用同一个
内核。分支测试覆盖执行中的序列恢复、同步中断后不再执行后续步骤，以及结果取反状态恢复。
时间轴调度也已拆出：固定区间与来源顺序放在程序中，游标、活动项下标和同步跳转标记放在
`timelineActionState.ts`，执行算法放在 `timelineActionExecution.ts`。正式调度器使用同一内核。
组合测试将调度进度与动作序列一起保存，覆盖跨越跳转目标的活动项、被跳过的待执行项、
目标帧上的新动作及同步技能结束，并比较恢复分支与从头运行的完整数据。
这些区间是已启动技能的内部程序，不是用户尚未提交的未来技能块输入。
重复动作的计时、扫描次数、目标触发次数及首次 Tick 标记已放入 `repeatedActionState.ts`；
跳转动作的已执行标记和首次 Tick 标记已放入 `timelineJumpState.ts`。对应执行算法不持有
这些状态，现有步骤绑定调用同一算法。分支测试覆盖周期追赶、目标间隔边界及跳转同步重入。
条件动作和 Switch 的选择已改为 `branchActionState.ts` 中的分支下标。选择、Tick、End 和
Reset 使用 `branchActionExecution.ts`，保留两者不同的重置规则及 Switch 的 float32 标签匹配。
组合测试同时保存选择和真实分支序列进度，恢复后只推进原来选中的分支。
目标循环的活动子序列列表已改为 `targetLoopState.ts` 中的编号数组，创建、Tick、End 和
Reset 的顺序由 `targetLoopExecution.ts` 负责。组合测试同时保存目标、动态子序列进度和成员列表，
覆盖另一分支销毁子序列后恢复继续。现有绑定层仍持有子序列对象，其编号分配也还在绑定层；
这只完成成员调度迁移，不代表实际动态动作体已全部成为纯数据。
黑板值与实体板关系已放入 `actionBlackboardState.ts`，读取、动态赋值及创建子作用域使用
`actionBlackboardExecution.ts`。数据图保留实体板共享；读取只回退一层，direct 遮蔽和实体写入
仍是不同路径。测试覆盖整图恢复后的共享关系、兄弟分支隔离及独立实体作用域。
作用域缓存及 once 标记已放入 `actionScopeState.ts`，缓存键是黑板数据节点，随整图恢复保留
父板身份。`actionScopeExecution.ts` 保留执行期不缓存、宿主 Reset 清空，以及动作体返回后
才标记 once 的规则。正式对象绑定另用弱引用表连接黑板对象，不把对象放入可保存数据。
缓存现在由宿主明确持有并在 Reset 清空；整场装配迁移时还须验证宿主销毁与内存释放。
技能的施放进度、准备输入、来源施法和扣费标记已集中到 `skillExecutionState.ts`。正式宿主
调用 `skillExecution.ts` 处理开始记账、逐帧推进、扣费时点和结束清理顺序。组合测试把技能、
时间轴和动作进度一起保存，验证延迟扣费、提前结束分支恢复及自然结束顺序。
共享冷却已拆为 `skillCooldownState.ts` 与 `skillCooldownExecution.ts`，其单周期计时数据和
算法在 `periodicTimerState.ts`、`periodicTimerExecution.ts`。固定周期不随试探复制，动态倍率
只在实际可预占时读取。恢复测试覆盖共享引用、确认帧前返还与显式覆盖取消预占。
Buff 句柄已要求提供 `BuffReference`（所属目标和容器内实例编号）。技能附着列表保存引用数据，
结束前仍先捕获本次清理集合，结束过程中新增实例不会被清空。实际句柄暂存在绑定表中；
整场恢复时必须按恢复后的 Buff 容器重建绑定，不能复用旧分支对象。
Buff 的生命周期标记、时长、计时增长和增强次数已放入 `buffLifecycleState.ts`；寿命推进与
MarkFinish 顺序由 `buffLifecycleExecution.ts` 处理，正式 Buff 调用相同算法。组合测试同时
保存周期触发和生命周期，验证暂停、提前结束后恢复及同步结束重入。
叠层组的成员与计数已放入 `buffStackingState.ts`，成员只保存同一目标内的实例编号；优先级
启用和计数由 `buffStackingExecution.ts` 处理。执行优先级回调前先固定本次成员绑定，
随后读取实时结束状态，防止同步回收导致遍历丢失原成员。正式绑定表在回收时删除对应项。
增减层、层数上限、定时增长及达到上限时重置周期也已接入数据算法；组计数与实例增强次数
的恢复测试覆盖减层后再增长。BeforeEnhance 后才判断上限，增强事件仍先于属性刷新。
刷新、延长和有限时长直接写入的规则也已从对象方法移出。
属性集合已拆成 `combatAttributeState.ts` 和 `combatAttributeExecution.ts`，修正器使用普通数据
对象。注册列表保留对象身份和顺序；整图复制时，所属 Buff 的引用与注册列表必须指向同一份
复制后的修正器。测试覆盖等值独立项、重复注册、按所属引用移除及分支回退。

Buff 的属性修正归属已放入 `buffAttributeState.ts`，正式替换与移除流程调用独立算法。
组合测试同时复制归属和目标属性集合，覆盖增强后恢复、移除不影响其他来源，以及注册失败撤销。
这些数据仍由现有对象分别持有，尚需接入同一个战斗根状态。

Buff 的父子关系已保存为目标与实例编号，结束遍历由独立算法处理，仍会访问结束回调中新添的
子实例。释放仅清除关系，不伪造子实例结束。实际句柄目前留在适配层，尚需统一按分支解析。

`buffInstanceState.ts` 已统一持有生命周期、周期触发、属性归属与子实例引用；正式 Buff
从同一份实例状态访问这些数据。实例也持有自身黑板数据，与目标实体板保留共享引用；
初始化收集和覆盖顺序不变。护盾的初始参数、余额、次数和耗尽标记也由实例持有，吸收算法
先更新状态再执行结束回调。容器已能按实例编号重建这些对象绑定。

Buff 的启用/触发序列、普通事件响应和局部定时动作已支持重绑。SkillAffix 的事件、实体和
子 Buff 回收订阅，技能槽替换，以及普通 Buff 回收监听仍未整体迁移。

容器的实例编号、释放重入标记、实体标签计数和添加冷却已放入 `buffContainerState.ts`。
标签增减及冷却推进使用独立算法，保持多项冷却和引用计数规则。成员目录按发布顺序保存编号，
实时遍历仍能访问同步新增成员，回收移除编号及绑定。公开成员查询返回当前对象列表；需要
实时处理的内部流程直接遍历编号。活动修正注册表与成员绑定仍持有对象，尚未完成整体恢复。

容器数据图已纳入实体属性、共享黑板、实例数据目录和叠层组数据。创建与回收同步维护目录，
分配顺序与发布顺序仍分开保存。正式容器复制测试确认 Buff 属性修正和实体注册项保持同一
引用，Buff 黑板仍指向同一实体板。恢复入口也会重建活动修正、护盾、叠层和父子对象绑定；
尚未数据化的对象回调继续明确拒绝，不能据此开放整场恢复入口。

活动护盾列表已引用实例中的护盾数据，持续防护注册表也按实例数据关联。复制保留注册项和
实例数据的共享关系，结束和释放删除注册项；护盾排序与本次吸收遍历仍通过绑定层执行。
伤害、治疗和失衡修正等活动注册表仍待迁移。

三类修正器的条件与数值处理已移入独立执行算法，现有对象仅转交定义、本次上下文和取值端口。
修正器取值已改为 Buff 标识和黑板数据引用，执行时通过统一算法读取；不再保存捕获 Buff 的
取值闭包。伤害条件程序仍在对象绑定中，尚不能把这些修正器对象放入切面。

治疗与失衡修正器已改成普通数据，实例与活动注册表共享同一修正项，取值来源指向实例黑板。
容器直接调用执行算法，注册和移除仍保留顺序与对象身份。伤害修正器仍有条件程序绑定待迁移。

伤害修正的归属、取值来源和活动注册关系也已进入数据图；状态只包含伤害协议字段，不带
装配定义中的条件工厂。是否存在条件程序明确记录，但程序仍通过适配层解析，尚不可恢复运行。

实例数据明确保存所属目标、容器内编号、定义标识和来源；来源动作、定义归属、施法快照与
创建时优先级也已纳入状态。创建状态必须传入身份，不能靠旧对象补齐来源信息。

共享技力获取与自然恢复修正项已改为普通数据。Buff 的获取效率修正与全局注册表保持同一引用，
容器数据图接入这份共享注册状态。资源对象可以直接绑定完整保存账本，并核对场景固定的上限、
队伍身份和基础回能参数；恢复不会从展示快照重建或重复注册动态修正。

全局 Buff 的组目录、实例编号、黑板、寿命、技力修正及子实例引用已进入数据，结束算法先
注销修正再固定子实例并结束。所有目标容器恢复后，父目录按保存引用接回子 Buff 和固定定义，
同时核对活动修正仍与共享资源注册表引用同一对象。这个阶段不重新施加子 Buff 或修正。动作
持续期仍须随来源宿主恢复，完整装配尚未接入。

动作持续期记录使用程序槽到当前分支关系数据的映射，结束后清除对应槽。
`CombatOperationPrograms` 按编译节点对象身份分配固定槽位，并由同一切面树的恢复分支共享。
统一的 `CombatOperationHostState` 保存全局 Buff、时间膨胀、能力实体寿命、连携候选、终结技能量
回复限制、定时标记、生命下限和技能施放继承八类关系。生产技能把它放入
`SkillRuntimeState.operations`，能力实体子技能复用来源技能的宿主，因此同一动作的结束阶段只
清理当前分支。事件来源共用的 `AbilityEventHostState` 保存启用状态、订阅引用和子 Buff 引用。
普通干员与能力实体被动还保存共享黑板、启用及响应序列和动作宿主，并按稳定 key 放入整场数据
图。装备贡献保存共享黑板、宿主与响应序列；初始化程序保存启用/初始化序列和动作宿主；潜能
事件保存程序 key 与订阅。处理函数恢复时按保存订阅编号重绑，不重新注册。反应式操作链使用与
技能链相同的八类动作宿主。下一阶段只负责按依赖顺序重建这些对象绑定和跨容器关系，不能在
构造过程中重放初始化程序。

装配根中的时钟、模拟器、实体编号、投射物目录、敌人标记、全局冷却、施放编号和普攻继承目录
必须在构造器读取恢复输入后创建，不能使用字段初始化器抢先生成空状态。当前实现已经改为显式
构造阶段。共享层由 `CombatSharedRuntime` 一次性新建或绑定，所有运行对象直接引用同一份
`CombatSharedState` 子数据；恢复时还会核对时间膨胀程序目录和外部回执，不能用另一份对象冒充。
之后绑定标准环境，由环境提供原生事件目录及按保存引用重绑处理函数的端口，再建立语义事件层、
实体目录和来源宿主。这个顺序使恢复订阅时无需猜测发布实体，也不会重新申请订阅编号。

对象构造前先执行整图预检。预检只读候选数据，核对当前干员程序与保存目录完全对应，并检查资源
队员、技能冷却、技能黑板和 Buff 实体黑板仍指向复制图内各自唯一的数据。被动、装备、初始化及
潜能宿主的有无也必须与当前固定程序一致。预检不深拷贝、不执行任何规则；失败时尚未创建候选
对象，因此不需要回滚业务副作用。通过预检只证明候选拓扑可绑定，不能替代后续关系完整性检查。
能力实体还会检查目录键、实例编号、Buff 容器创建标记和容器数据是否一致；已有容器必须继续与
实体引用同一黑板。这些错误也在对象创建前报告。

标准伤害环境接收整场候选图中的敌人和干员 Buff 容器数据。它从保存的属性和实体黑板创建对象
外壳，并把原数据直接交给容器；不会再次应用面板初值。此阶段尚不重建 Buff 实例及生命周期动作，
这些关系要等全部来源宿主和定义目录就绪后统一绑定。通用状态容器则复用现有模板中的固定定义，
只替换为保存的状态 Map；绑定过程不施加状态，也不推进剩余时间。

Buff 实例恢复按 `definitionOwnerId + definitionId` 解析固定定义。同名 Buff 可以存在于不同干员的
定义目录，仅按 Buff ID 查找会接错程序。实例若在创建时保存了跨实体来源属性读取端口，还必须
保存该属性目标的实体身份；恢复时从当前分支实体目录重新解析读取函数。函数本身不进入数据图。
实例对象与生命周期动作先绑定，父子 Buff、全局 Buff 子投影和 SkillAffix 对象引用仍在后续关系
阶段统一接回。

`CombatBuffRestoration` 负责执行整场顺序。它先为每个目标绑定普通实例，并按保存的实体身份把
来源属性读取接到当前分支；随后绑定引用这些子实例的全局 Buff 父目录；最后遍历所有目标解析
父子 Buff 和 SkillAffix 对象引用。全局父子反向索引若出现一个子实例属于多个父层，会在绑定前
拒绝。任一阶段失败后候选标记为失败，不能在同一份半绑定数据上重试。

能力实体的 Buff 容器按需创建，因此恢复时要同时检查 `buffContainerCreated` 和 `buffs`。标记为
未创建时不得存在容器数据，标记为已创建时必须有完整容器数据。通过检查后，标准环境使用保存的
属性状态、实体黑板和容器状态创建目标外壳，不执行 Add、Start，也不再次施加出生标签。重建结果
先加入统一目标表，之后才由 `CombatBuffRestoration` 绑定实例和关系。

投射物采用数据和关系两阶段恢复。第一阶段只验证并绑定飞行、命中、回收和回调宿主数据；第二阶段
在能力实体、技能回调宿主及重置处理器全部存在后统一解析对象关系。第二阶段先在局部表中完成全部
解析再提交；任一引用失败时不留下部分绑定。存在活动实例而关系尚未完成时，禁止发射或推进。

生命与失衡账本已拆成数据和执行算法，两个恢复计时器、生命下限表及编号一并保存。动作宿主保存
生命下限规则编号，结束时通过当前分支的生命账本按编号移除，不再保存或复用旧分支清理回调。

技力与终结技能量账本已统一为 `combatResourceState.ts`。队伍列表和身份索引共享队员数据，
回能限制句柄及编号、基础许可、暂停时间和共享修正状态一并纳入。支付、恢复、队伍回能及
许可变更算法已移入 `combatResourceExecution.ts`，现有账本仅转交调用。动态倍率仍由步进时
传入的读取端口提供，完整战斗接线尚待迁移。
转场与开始回调、动态动作体和监听注册仍在对象绑定层；技能宿主尚未整体
成为纯数据，不能开放整场切面。已集中状态中的准备输入也只能来自当前已提交操作，不能
提前准备整条轴未来的技能块。

帧时钟已独立为数据。时间膨胀的全局、实体实例、忽略集合、编号和累计时间已集中到
`timeDilationState.ts`，曲线函数由同一切面树共享的 `TimeDilationPrograms` 按编号提供，推进
算法直接使用状态和程序目录。恢复会核对所有活动曲线编号，不发布开始事件。开始、停止与动作
持有关系仍须随具体技能或 Buff 宿主接入。

### 后续接入顺序

能力系统已集中当前技能身份、处理中的技能身份、延迟施放请求、技能槽形态、模式层、
原生技能类型覆盖、普攻映射登记及边界发布标记。对象接口通过身份解析当前技能。
延迟槽写入和取出已拆为数据算法；实际边界跟踪的待到达项和登记集合已接入同一数据根。
单干员核心恢复按“实体外壳、共享冷却、技能宿主、能力系统”的固定顺序完成这些对象绑定，
同时恢复共享黑板、状态和定时标记。它只接受已经通过整图预检的状态，不重新施放技能、执行
初始化或分配编号。被动、装备、养成初始化和潜能事件由紧随其后的来源宿主阶段接回。

常驻被动和装备事件各有独立来源恢复入口。它们直接绑定保存的局部黑板、动作进度、启用状态和
订阅身份，不重新执行启用程序。来源持有的子 Buff 在所有目标实例建成后先完整解析到当前分支，
确认没有缺失引用后才统一提交给宿主，解析端口对每个 Buff 身份只调用一次。

养成与装备初始化恢复只创建绑定保存数据的序列对象。直接养成初始化使用自身保存黑板；装备
初始化必须继续引用对应装备贡献的同一块黑板。两者都要求操作执行器绑定保存的动作宿主，并保留
初始化序列和可选启用序列的原进度。恢复不调用 `execute`、`tryExecute` 或装备 `enable`；装备来源
释放时仍通过恢复后的启用序列执行 End 清理。

潜能事件按保存的程序顺序和订阅身份重绑当前分支处理函数，不创建新订阅。单干员来源协调器保持
正式装配的“装备事件、潜能事件、初始化、常驻被动”顺序。四类来源全部建立后，它先在跨来源范围
检查子 Buff 所有权唯一性并完成一次性解析，再提交给各宿主；构造失败会清理已经建立的候选宿主。

整场候选基础阶段现从预检结果直接绑定共享账本和标准环境，并创建敌人、全部干员和已存在能力实体
的 Buff 目标外壳。共享时钟、资源、回执、编号、随机位置、生命账本、属性、实体黑板和 Buff 容器
都引用复制图中的原数据。随后整场 Buff 实例阶段在完整目标表上重建普通实例和全局父实例；来源
所有权、能力实体子技能及 Buff 对象关系仍在后续阶段提交，期间禁止推进战斗。

标准环境绑定战斗上下文后，恢复基础阶段用保存的语义事件状态和环境提供的原生订阅重绑端口创建
唯一语义事件中心。干员阶段先恢复全队核心，再按队伍顺序恢复各自来源宿主；它只使用候选环境创建
的 Buff 目标，不复用原分支 `operator.buffRuntime`。全部来源建成后，子 Buff 在全队范围检查唯一
所有者并一次性解析。能力实体关系阶段从所属干员的当前编译结果取得定义，从切面树共享目录取得
子技能程序，接回实体被动、进行中的子技能和直属子 Buff。恢复不执行被动启用序列，也不重放子
技能开始动作。实体目录先构造整批关系，全部成功后才写入实例；失败后可修正解析端口并重试。
当前阶段结束后仍不推进，最终 Buff 对象关系和整场提交顺序尚待接通。

投射物回调状态保存固定程序编号、定义干员、独立黑板、来源施法信息和可选回调宿主。定义干员不能
从 `source` 反推，因为来源可能是 Buff、普通能力实体或另一投射物。恢复先建立纯数据目录，再按该
身份创建当前分支操作链；尚未命中的回调不提前创建技能宿主，已经命中的宿主从保存帧继续。
SkillAffix 保存的对象登记通过统一路由接回：普通实体使用实体目录的 reset 编号，投射物使用投射物
目录的 reset 编号，Buff 使用所属目标的 recycle 编号。投射物允许这些处理函数先于宿主关系绑定，
最终关系提交时逐项核对，避免由依赖顺序迫使恢复阶段重新注册编号。

连携目标及黑板准备已不再返回开始回调，改为 `SkillCastStartPreparation` 数据，由技能
在初值恢复、开始回执之后应用一次。准备值随技能状态保存，Buff 旁路会丢弃它。施放前
通知也已改为保存事件数据和原始技能寻址方式；消费时才创建 Buff 附着入口，通知函数由
当前宿主提供，不保存为每次施放的待执行闭包。

技能目标上下文已接入技能状态，保存命名组及组内实体身份。设置目标组时复制数组和
身份对象，避免调用方修改输入而改写已选择的目标；恢复时仍须同时恢复对应实体目录。

能力实体目录已集中身份、来源、目标、寿命、待回收标记、死亡来源和共享黑板数据，
创建及释放同步维护目录。定时标记数据也已接入，时钟以编号引用，扫描时读取当前分支时间。
子技能、所有权子 Buff 和实体被动已经有明确的数据身份与恢复阶段。reset 登记保留编号，由实际
持有登记的操作宿主在重建执行链时接回处理函数。投射物和回调宿主尚未完成整场接线，因此能力
实体关系层仍不能单独作为完整战斗恢复入口。

输入排程仍在 `CombatInputRuntime` 中持有未来轴数据，不能把整个排程器放进战斗切面。
单次输入执行已拆为 `processCombatSkillInput`，只接收本次输入和实际帧；现有排程器调用
同一个入口。回执列表已独立为状态，追加时复制载荷。整场接入时还须将排程放在战斗之外，
在正确的输入阶段提交，并将回执与所有战斗状态一起保存和恢复。

逐帧驱动器已不再注册技能和外部事件排程器，改为登记两个输入阶段。每次推进由调用方
提供阶段入口：技能输入位于连携窗口更新后、技能推进前，外部事件位于技能推进后。
装配对象目前仍持有默认排程入口，属于过渡接线；显式传入本帧入口可以跳过默认排程，
但它还不是已完成的、与未来技能程序彻底分离的战斗会话。

先在实际执行链上迁移一个完整纵向样本：技能产生 Buff，Buff 注册监听，事件产生投射物，
投射物含随机行为并正常销毁。从同一切面多次尝试并恢复成功后，再迁移其余状态。
只给时钟和几个计数器加快照，无法验证真正困难的对象生命周期与引用关系。

迁移完成前不开放整场模拟快照。完成后，普通模拟也使用同一个状态驱动内核，不保留一套普通
实现、一套试探实现；原有测试和真实轴对照用于确认重构没有改变游戏语义。
最后再把旧轴转换接到这个能力上，随后评估编辑器等消费者。

正式入口至少通过以下验收：

1. 在每个稳定帧保存、前进、恢复、重跑，完整状态和回执逐项一致，不只比较总伤害。
2. 根切面下分别保存 A、B，反复恢复 A/B，并测试嵌套分支和释放未选分支。
3. 两份输入前缀相同、未来不同，在前缀末尾得到相同战斗状态；删除未来块不改变过去。
4. 切面后的投射物命中、Buff 跳伤、延期施放完整继续；尚未提交的未来技能不能自动出现。
5. 覆盖初始化、第 0 帧、空输入帧、同帧多输入、边界结束事件、膨胀和浮点推进顺序。
   连续组特别覆盖本帧输入阶段前刚到边界、固定输入停止旧组及同帧声明顺序。
6. 覆盖对象创建、销毁后恢复，监听开关，以及旧外部句柄对新分支操作时被拒绝。
7. 期望与随机两种模式均能恢复取样位置；恢复本身不消耗样本、不改变强制暴击设置。
8. 帧中保存/恢复被拒绝；执行失败后可恢复；恢复准备失败时原状态完全不变。
9. 修改原始回执载荷不能污染已保存历史；缓存失效正确；试探不产生 UI 或外部副作用。
10. 生成多种确定种子的输入序列，对比分支恢复与从头重放，失败时输出第一处状态差异。
11. 真实轴的完整回执与现版基线对照，另测保存/恢复成本及反复试探后的内存释放。

## 参考系统

以下用于借鉴工程方法，不作为游戏规则的依据，也不意味着必须引入对应框架。

- [GGPO 开发指南](https://github.com/pond3r/ggpo/blob/master/doc/DeveloperGuide.md)：要求可恢复的
  完整游戏状态、确定的逐帧推进，并建议通过回退后重跑比较来暴露隐藏状态。
- [Photon Quantum 系统约束](https://doc.photonengine.com/quantum/v3/manual/quantum-ecs/systems)
  和[状态定义](https://doc.photonengine.com/quantum/v3/manual/quantum-ecs/dsl)：行为系统保持无状态，
  可变游戏数据由帧统一持有。这支持状态集中、业务仍分模块的选择。
- [MuJoCo 模拟编程](https://mujoco.readthedocs.io/en/stable/programming/simulation.html)
  和[可复现性](https://mujoco.readthedocs.io/en/stable/computation/index.html#reproducibility)：
  共享模型与每次运行数据分离；可恢复状态也包括影响继续计算的内部量，不能只复制显示值。
- [Box2D 快照](https://github.com/erincatto/box2d/blob/main/docs/recording.md#snapshots-snapshot)：
  快照边界、内部状态、对象身份及宿主回调都有明确限制，不能把游戏外部接线当作自动恢复内容。
- [Rapier 序列化](https://rapier.rs/docs/user_guides/javascript/serialization/)：整个物理世界可保存并
  恢复，参考其完整世界边界；本项目首版不需要二进制存档格式。
- [FASTER 检查点与恢复](https://microsoft.github.io/FASTER/docs/fasterkv-recovery/)：有全量及增量机制，
  但其并发与磁盘恢复复杂度并非当前同步战斗模拟所需，不照搬数据库检查点框架。
