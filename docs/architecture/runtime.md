# 战斗执行与状态

这里说明稳定规则，功能完成度见 [当前交接](../handoff/current-context.md)。
具体游戏行为见 [研究入口](../research/README.md)，不能用旧流程图代替同版本证据。

## 谁负责什么

编译器准备程序和初始输入，运行环境提供本场实体状态，CombatRuntimeAssembly把它们连接起来。
装配代码不应成为第二个伤害计算器或条件解析器。

每个执行器只处理自己认识的动作和条件，其他内容交给后续执行器。
最终仍无人支持的内容必须报错。增加支持时同时检查编译、运行环境和预检，不能只让预检放行。

帧推进和同帧调用顺序会影响结果，不能依赖对象遍历顺序或按接线方便调整。
实际战斗帧、对象自己的时间、费用帧、允许接续时间和自然结束时间分别处理。
界面技能块宽度不能当作技能对象或投射物的销毁时间。
具体坐标和变速职责见 [时间、变速与显示](time-and-display.md)。

## 不同状态不要混用

| 状态            | 用途                                             |
| --------------- | ------------------------------------------------ |
| SkillRuntime    | 本次技能的施法身份、动作黑板、执行位置和结束清理 |
| CombatResources | 全队SP及干员终结技能量；检查、支付和变化分别记录 |
| Buff            | 实例、叠层、黑板、属性或伤害修改、监听和结束动作 |
| Status          | 用于条件查询和显示的明确战斗状态                 |
| Timed marker    | 能力系统中的定时标记，不自带完整Buff行为         |

不能因为界面上都显示为持续条就把这些状态合并。
同一状态只有明确的管理者；查询、伤害修正和界面记录必须读取同一份事实。

## 事件与清理

事件名称、数据、输入目标和来源按公共定义传递，不能在每个监听者处重新猜测。
原生事件与用于展示的语义记录不能重复执行同一效果。
同步事件可能嵌套，内层结束或抛错后须恢复外层来源、目标和黑板环境。

临时监听由技能或Buff持有并释放，事件中心不猜监听寿命。
一组注册中途失败时清理已经注册的部分，不影响其他宿主；这是工程上的清理保证。
投射物回收先结束技能，再通知reset，最后清理Source。
详细机制见 [事件、来源与生命周期](events.md)。

## 伤害和可复现性

伤害计算、承伤处理、生命写入和事件通知不能当作同一步。
新增处理器应核对所在阶段、来源和是否重复执行，不能仅让最终总伤害接近旧结果。
伤害标签与行为特征是不同维度；事件条件只能读取该事件实际提供的数据。

公式需要时明确使用float32。随机样本从指定来源取得，不直接使用全局随机数。
运行时不翻译、不创建界面对象、不写用户存档。显示层只读取记录，不再模拟一次资源或Buff。
