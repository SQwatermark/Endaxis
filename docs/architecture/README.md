# 架构说明

本文说明系统长期怎样工作。当前完成度和待办见 [当前交接](../handoff/current-context.md)。

## 数据怎样变成模拟结果

```text
游戏资源和反编译证据 → combat-spec行为规格
                            ↓
游戏数据转换器 → 公共定义 → 正式生成数据
                                ↓
用户项目 → 应用层 → 编译器 → 战斗运行时 → 结果记录 → 曲线、诊断和界面
```

| 目录                          | 负责什么                                     |
| ----------------------------- | -------------------------------------------- |
| `packages/game-data-contract` | 各层共用的数据定义和名称；公共类型在这里维护 |
| `tools/game-data-compiler`    | 根据原始数据和证据转换、生成、检查游戏定义   |
| `src/core/project`            | 用户项目的存档格式和校验                     |
| `src/core/game-data`          | 提供游戏定义的访问入口，不另写一套公共类型   |
| `src/core/compiler`           | 解析等级、引用和配装，生成一场战斗需要的程序 |
| `src/core/combat`             | 处理时间、技能、Buff、事件、伤害和资源       |
| `src/core/projection`         | 从战斗结果记录生成曲线和诊断，不重新结算资源 |
| `src/application`             | 组织编辑、撤销、模拟、取消和异步结果检查     |
| `src/ui`                      | 界面和交互，不按干员名称硬编码游戏规则       |
| `src/data`                    | 正式生成数据，必须通过转换器更新             |

底层不能读取Vue组件或Store。生成器不能读取旧生成文件来填补未知数据。

战斗目录进一步分工：`actions`处理同步动作，`timeline`负责技能帧调度，`runtime`组织执行和状态，
`damage`计算伤害，`buffs`、`status`、`infliction`分别管理相关状态，`events`分发通知，
`receipt`记录结果。新增曲线先找显示层，新增游戏规则先找对应执行模块，不把逻辑塞进装配文件。

## 模拟哪些内容

模型中只有一个没有主动行为的敌人，忽略距离和投射物飞行路径。
时间顺序、实例身份、黑板、来源、技能结束、Buff引用和资源结算必须准确。
SP属于全队，终结技能量属于干员。投射物不建立能量账户。

不知道的游戏规则应报错或明确标为未知。应用不模拟某个功能，不等于游戏没有这个功能。

## 技能与事件

技能、Buff、被动和装备响应共用事件名称、数据和同步通知机制。
各自的执行对象负责黑板和结束清理，不应重新实现一套事件系统。

动作属于谁（Owner）、来自谁（Source）、在哪个对象上执行、最后归因给哪个干员，是不同问题。
继承的施法信息（SkillCastInfo）也不能代替这些身份。

投射物结束回调使用独立的AbilitySystemRuntime和SkillRuntime。
回收时先结束当前技能，再通知reset监听器，最后清理Source；监听器执行时仍能读取来源。
投射物触发回调、回调技能结束和投射物回收不一定在同一时刻。
没有回调的投射物只支持已确认的寿命规则；不认识的形式要报错，不能虚构空技能。

发布伤害相关事件不等于造成一次伤害。伤害动作进入统一计算流程，再把结果记录给界面使用。
部分条件会按游戏规则写黑板，不能假定条件只返回真假。

## 编辑与类型

编辑器允许用户表达输入，模拟器负责报告不合法之处，不能偷偷换技能或删效果来通过校验。
异步放置与模拟必须检查取消和请求版本，避免旧结果覆盖新编辑；一次操作对应一次撤销。
技能组的放置策略来自生成配置，界面通用处理。

图编辑器由调用方提供与文档类型匹配的显示函数。内部字段包装通过明确的读写适配器处理，
不能把包装层写进用户项目。已有公共类型直接复用，不用强制断言掩盖接口问题。
