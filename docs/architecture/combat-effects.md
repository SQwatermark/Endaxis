# 实体、伤害与状态后果

本页说明已提交动作怎样变成之后仍存在的对象或一次结算。未来用户输入由应用排程器负责；已发射投射物、能力实体的子技能、Buff 周期和延迟请求已经是战斗事实，必须随战斗状态继续或恢复。

## 能力实体与投射物

`LogicalAbilityEntityRuntime` 管理定义实例、黑板、子技能、子 Buff、定时标记与死亡/回收；`ProjectileLifecycleRuntime` 管理投射物寿命、命中/到达/阻挡/结束回调和 reset。两类对象共用整场 `AbilityEntityInstanceIdAllocator`，分配器与目录一起进入图，不能各自从 1 编号。

Owner、Source、定义干员和继承施法分别回答“由谁管理”“因谁产生”“从哪套程序查规则”“归哪次施放”。能力实体上的多个技能共享该实体的能力系统身份，同时各自保留技能进度。子技能程序和回调程序编号属于固定目录，实例数据只保存身份和进度。

普通实体 kill 先标记死亡和待释放，不立即删除目录；即使释放延迟为零，也到下一次推进才回收。同帧查询仍可能找到死亡对象，调用者须按自己的条件检查 alive。finish 依次结束子技能、子 Buff 和标记，再进入装配的完成钩子；钩子发布实体结束和适用的 ownerHpZero，随后清理被动/容器并记录回执，最后从目录移除并执行 reset 通知。

投射物依次经历 active、finished、marked、reset。到达不同于单纯超时，命中过滤失败不同于成功命中；结束回调可以启动仍需推进的回调技能，不能把 finished 直接解释为所有后果已经消失。reset 前结束当前回调宿主，reset 通知仍能按对应阶段读取来源，最终删除实例及绑定。

寿命阶段在开始时取候选快照，回调新发射的对象不进入本轮；能力阶段另有准入集合。普通实体遍历还会重新确认实例是否已被前一个回调释放。这些规则决定同帧是否多推进一次，不能以集合遍历“优化”改变。

发射时复制回调所需的直接黑板和施法身份，飞行中尚未触发的回调不提前创建技能宿主。恢复先建对象目录，再按保存的定义干员/程序编号接回操作链与回调；已启动宿主续跑，未启动宿主保持未启动，不能通过重放发射/命中重建。

当前空间模型只接受已证明的零空间/单目标投影，范围查找不计算半径碰撞。持续投射物来源时间同步等未闭合能力仍由编译/预检拒绝；恢复目录存在不代表支持全部原生投射物。

## 伤害与治疗流水线

| 边界                            | 决定与输出                                                         |
| ------------------------------- | ------------------------------------------------------------------ |
| 装配/标准环境                   | 提供目标账本、当前属性、Buff 修正、随机与事件端口                  |
| `resolveCombatDamageOrigin`     | 按 skill/reactive/equipment 选择真实宿主字段，不借其他技能补身份   |
| `PlayerDamageOperationExecutor` | 准备事件、即时修正、属性快照、公式/暴击策略、生命/失衡后果         |
| 纯公式函数                      | 数值输入 → 公式结果，不访问 UI 或主动写战斗                        |
| `executeHealthDamage`           | 承伤/输出前事件 → 护盾 → 击杀边界 → 生命写入 → 回执与后事件        |
| `HealOperationExecutor`         | 已选择目标和来源 → 治疗修正/写账本 → 回执 → outputHeal/receiveHeal |

每次伤害有独立 PlayerDamageContext。准备事件和 beforeCalculation 修正先于正式计算；Hit 临时属性在 finally 中释放。Reset 时要求的攻击快照另存于可恢复数字槽位，固定步骤身份与当次数值不能混为同一个缓存。伤害详情在执行边界记录真正使用的值，投影不从最终伤害倒推公式或套新面板。

生命伤害先通知目标 beforeTakeDamage，再通知来源 beforeOutputDamage，之后执行护盾与生命写入。目标事件和来源事件的施法载荷不同；不能为方便展示把执行技能身份塞给所有目标事件。治疗用两份输出/接收载荷，满血的成功治疗也可能产生事件，不能仅按 actualHealing 是否为零判定动作未执行。

连续数值期望和离散概率路径不同，见[随机模式](randomness.md)。生命、失衡、护盾、免伤、暴击后效各自有明确执行时点；大执行器中这些顺序具有领域语义，不能以并行计算或泛化中间件抹平。

## 附着、反应、语义状态与定时标记

元素附着先从目标 Buff 容器取得当前实例和层数，纯决策函数返回附着、爆发、消费或复合状态操作，再由适配器对同一实例执行。异元素消费核对先前投影实例，不能重新选择同名 Buff。附着/爆发/复合状态的实际行为继续走普通 Buff 和动作系统。

元素反应容器还保存已接入的感电/腐蚀级别与到期时间；通用 CombatStatusContainer 保存显式定义的层数/持续规则；TimedMarkerContainer 保存允许同 ID 多实例的标记及创建时绑定的时间域。三者用途不同，不因为结果都画成持续条就合并。

通用状态动作负责主动变化回执，状态运行时只补自然到期，避免重复记录。带属性修正的通用状态需要专用运行支持，当前适配器明确拒绝，不默默忽略。

部分看似查询的方法带惰性清理：定时标记 has/latest 查询会 sweep 并可能通知到期；反应 isActive/snapshot 会移除过期条目。因此不能把任意运行时查询当作无副作用的显示接口。UI 应读取已发布投影或会话复制数据，完整保存/恢复入口本身不调用这些游戏清理查询。

## 扩展与验收

新增动态对象须闭合编号、来源、宿主清理、时间域、待发生后果及恢复绑定。新增数值效果须闭合属性读取时点、临时修正作用域、目标写入、事件顺序和回执；新增状态须明确它属于 Buff、反应、通用状态还是标记。

原生测试分布于 abilities、damage/heal/infliction/status、标准环境和 restoration。必须比较直接运行与恢复续算的实体身份、回调进度、事件及实际余额，而不只比较总伤害。当前文档描述 Endaxis 已实现的边界，不证明所有游戏公式、原生事件或空间行为完整。
