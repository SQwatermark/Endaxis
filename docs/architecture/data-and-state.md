# 数据与状态

这份说明补充 [架构总览](README.md)，重点解释哪些数据可以保存、谁负责转换。

## 先判断数据属于哪一类

| 数据               | 谁管理                 | 是否写进用户存档 |
| ------------------ | ---------------------- | ---------------- |
| 用户输入           | 编辑命令和项目会话     | 是               |
| 游戏定义           | 游戏数据仓库，只读共用 | 不复制整份定义   |
| 编译结果           | 编译器，根据输入重建   | 否               |
| 运行状态           | 单场模拟，允许变化     | 否               |
| 战斗记录和显示结果 | 运行时记录，显示层读取 | 否               |

目录中的skillKey、项目中的放置身份、单场Buff实例ID和界面的节点key用途不同，不能互相代替。
存档字段以 `src/core/project/schema.ts` 为准，不用旧文档里的字段清单代替当前schema。

## 存档和模拟结果分开

存档保存用户输入：队伍、等级、配装、敌人、技能放置、实际战斗帧、布局和明确编辑过的默认值。
默认值需要保存实际值及是否编辑过，避免重新打开项目时悄悄变化。

面板、编译后的动作、Buff实例、伤害记录、曲线和警告由输入重新计算，不写成项目事实。
选择、悬停和撤销栈属于编辑会话；语言和主题属于设备偏好。
游戏名称由稳定ID和语言包取得，不把翻译后的名称当作身份。

用户对象和需要显示、连接的命中有稳定身份。纯派生步骤不必为了完整外观分配随机ID。
命中连接保存伤害步骤的稳定key；运行时hitId由施放ID和步骤key派生，不把两者混为一个存档字段。
重新编译同一输入应得到稳定结果，不能让撤销因为重新分配身份而失效。

## 两个编译器做不同的事

`tools/game-data-compiler` 把版本化游戏资源转成正式游戏定义。
`src/core/compiler` 把这些定义与用户等级、配装、时间轴组合成一次模拟程序。

游戏数据转换器按以下顺序工作：

```text
原始资源 → source读取 → 公共动作和条件转换 → 模拟范围内的处理 → 领域组装 → 输出
```

- source保留原始类型和字段，不提前删除当前场景用不到的证据。
- 公共转换层解释共用的动作、条件、Buff、实体和引用，不按首个使用者另写装备版或干员版。
- 领域组装只处理干员、武器或装备自己的归属、成长和输出结构，不互相导入实现。
- 判断原始类型是否共用，依据同版本schema中的类型身份和引用关系，不能只看字段长得相同。
- 同一种原始类型可能有不同输出用途：共用读取结果，不强行合并领域组装。
- 省略不影响木桩模拟的行为时，要在明确的处理步骤记录原因，不能从原始读取结果中偷偷丢弃。

完整干员候选必须包含属性、技能、养成和全部必要引用，不能用空技能或空养成占位。
原生charId、元素、职业等来自版本化数据；产品slug等身份由配置明确提供，不从翻译名称推测。
公共枚举映射只维护一次。具体接口和依赖检查见 [转换器README](../../tools/game-data-compiler/README.md)。

整批重建在同一轮规划中生成干员并收集公共 Buff，避免为公共目录再规划一次全部干员。
处理分成两阶段：先逐人组装，保留最终定义、审计字符串和去重的公共原始定义；
再收齐同批所有可能读取这些值的定义，分析用途并逐人优化、渲染。原始动作图和完整计划不留到第二阶段，
已渲染的干员定义及时释放。公共定义先检查同 ID 是否完全相同，再补齐系统根并优化。
正式单干员生成和检查也使用同一批次的全部消费者，只输出或检查目标干员。
底层规划 API 没有完整批次用途时继续保守保留，不能用单人分析代替正式文件的一致性检查。
生成与验收各自重新执行一轮，
共同检查干员、审计、公共定义和名称文件，不能拿首轮缓存代替第二轮结果。
这两份产物使用一个重建阶段，任何规划、渲染、写入或验收失败都会阻止后续候选发布。

来源读取由每轮独立的 `OperatorPlanningSources` 管理。固定表原文缓存上限为 32 MiB，
技能、Buff 等逐人资源原文缓存上限为 16 MiB，按 UTF-8 字节计算并淘汰近期未使用的内容。
这是源文本预算，不是堆内存预算；解析后的对象、定义、审计和渲染文本另占内存。
超大文件照常读取但不缓存，JSON 按需解析并冻结，需要原文和 JSON 时由同次读取提供。
每人规划后清理逐人缓存，固定目录的解析结果仅在本轮复用；独立验收新建上下文，重新读取来源。
不能让全局缓存或上一轮结果掩盖来源变化，也不缓存依赖等级、场景或黑板的编译计划。

## 生成器的编译优化设计

这里设计的是 `tools/game-data-compiler` 的生成优化：减少正式定义里的无效分支、动作和黑板值。
它生成的数据要适用于不同等级、潜能、配装、队伍和时间轴，不能按某一次模拟的输入裁剪。
具体实施状态见 [当前交接](../handoff/current-context.md#未完成的开发工作)。

### 现有能力与缺口

现有代码已经有裁剪，新增优化应接着这些规则做：

- [actionSequenceProgram.ts](../../tools/game-data-compiler/src/compiler/actionSequenceProgram.ts)
  能删除禁用节点、部分恒定守卫和纯读取的空分支，也能合并投影后相同的两分支。
  外层是否消费返回值、`alwaysNext` 和条件是否有副作用都会影响判断。
- [skillPresentationTargets.ts](../../tools/game-data-compiler/src/compiler/skillPresentationTargets.ts)
  已分析只用于表现的黑板和目标组；部分分析通过完整字符串查找引用，判断比较保守。
  [presentationCalculationIsolation.ts](../../tools/game-data-compiler/src/compiler/presentationCalculationIsolation.ts)
  会阻止被省略的相机、角度等计算结果流入保留的战斗动作。
- [skillBlackboard.ts](../../tools/game-data-compiler/src/compiler/skillBlackboard.ts)
  合并原始默认值和各等级补丁，本身不判断哪些键已经没有用途。
- [planOperatorDefinition.ts](../../tools/game-data-compiler/scripts/planOperatorDefinition.ts)
  在组装完整干员后、渲染前执行整份定义的优化。
  这里已经收集被动技能对 Buff 身份的读取，防止把负责触发事件的空 Buff 删掉。

组装后的统一用途分析与优化入口已经接入，能简化字面量条件、裁剪部分技能算术链，
并删除技能和装备中无用的初值。实体继承和投射物结束回调已经按接收方用途分析，
跨定义读取目前保守汇总全库键；按目标进一步缩小范围、删除私有定义和原生动作坐标的完整追踪仍待扩展。
零资源动作还需检查事件和记录，不能因数值为零直接删除；也不能按干员名、Buff ID 或黑板键名添加裁剪名单。

### 什么叫没有价值

一个节点只有在删除后既不改变结果，也不影响后续执行时，才没有价值。
这里的结果包括伤害、治疗、资源、Buff 层数与寿命、目标选择、技能资格、时间变化、
事件顺序、随机抽样、归属、界面记录、诊断和用户保存的命中连接，不只是总伤害。

分析每种动作和条件时，至少回答以下问题：

| 要检查的事                                 | 用途                                               |
| ------------------------------------------ | -------------------------------------------------- |
| 读取、写入哪些黑板键                       | 找出仍有人使用的值，以及读取前就被覆盖的写入       |
| 是否读旧值再写新值                         | `assign` 与 `add`、`multiply` 不能用同一条删除规则 |
| 返回值由谁消费                             | 没有动作的条件也可能阻止后续序列或决定技能资格     |
| 是否发布事件、抽样、改变战斗状态或生成记录 | 这些影响不会因为输出黑板没人读取就消失             |
| 是否建立作用域、监听、延迟任务或结束清理   | 子序列为空不一定代表容器可以删除                   |
| 是否把值交给其他技能、Buff 或实体          | 当前序列没有读取，不代表其他执行对象不使用         |
| 求值是否可能报错                           | 不能删除一次读取后顺便掩盖缺失黑板值等错误         |

用现有动作、条件联合类型按 `kind` 明确检查字段，不再用任意字符串出现次数证明可删除。
新增类型如果没有分析规则，就保留并报告原因；不默认它是纯计算。
分析结果保存在生成器内部，不把用途标记、依赖图或裁剪配置加入公共数据契约和 `operators.json`。
已有字符串隔离检查先保留；只有新分析覆盖其语义并通过反例验证后，才替换重复扫描。

### 放在什么位置

当前处理顺序是：

```text
严格读取来源 → 现有公共投影及场景裁剪 → 领域组装与引用补齐
    → 保留既有步骤身份 → 分析用途并裁剪 → 复查引用与身份 → 渲染及候选验证
```

原始数据继续完整读取，不因为预计会删除一个分支，就跳过未知类型、非法字段或缺失来源检查。
来源规则已经证明不可达的分支，可以沿用现有“不要求建立其运行模型”的处理，并记录依据。
新增优化不能通过捕获编译错误、假设条件为假来制造不可达分支。

新增处理使用组装后的现有定义对象，不再建立一套动作格式，也不解析生成出来的 TS 文本。
主动技能、被动、Buff、实体子技能、武器和套装共用分析规则；各生成入口只负责提供完整输入。
当前批次用途覆盖全部干员、公共 Buff、共享实体定义、武器、装备、套装、机制 Buff 和初始化程序。
装备和机制调用各自现有的源数据编译入口，不导入正式生成库补消费者。默认仓库的共享实体定义为空。
系统敌方 Buff 由敌人独立容器持有，其受限动作没有实体黑板查询；敌人定义仅提供面板和失衡配置。
新增定义域或读取出口时必须复查这些边界，不能沿用旧的空集合来证明没有消费者。

第一阶段放在现有伤害步骤 key 分配之后。保留节点原有的 key，数组压缩后不重新编号。
[definitionStepKeys.ts](../../tools/game-data-compiler/src/compiler/definitionStepKeys.ts)
目前使用结构路径补充身份；提前裁剪会改变这些路径，使同一来源的优化前后无法直接核对命中。
渲染时的共享序列提取仍放在优化之后，并验证展开后的 key 与优化前逐项对应。
Buff、技能、实体 ID 以及公共导出名同样不因优化重命名。

### 第一步：简化可以证明的分支

先处理字面量条件，以及同步局部序列中由确定写入得到的常量。分支汇合时，只有所有可达路径
都得到同一值，才继续当作常量；事件、回调或未知写入可能改值时，撤销相应的常量结论。
第一批不做跨帧常量传播，也不按默认等级把可调整的黑板初值替换成常量。

- 条件无副作用、求值不会报错且结果确定时，只保留可达分支，同时保持原来的返回值和继续规则。
- 两侧行为、返回值、作用域及清理效果完全相同时，纯条件可以消去。
- `all`、`any`、`not` 按原来的短路顺序简化。例如“先写黑板再遇到恒假条件”不能整段替换为假。
- `switch` 的首个匹配项、默认分支、空选项和停止规则全部保留，不能排序或按标签去重。
- 不把 `alwaysNext`、独立黑板作用域、`once`、循环或延迟容器当成普通嵌套数组直接摊平。

比较、计算和取整必须使用已经核实的数值语义，包括 float32、比较容差、除零和整数边界。
[actionBlackboardOperationExecutor.ts](../../src/core/combat/runtime/actionBlackboardOperationExecutor.ts)
中的 `calculateActionValue` 与 `modifyActionValue` 就有不同的除法处理，不能用同一个 JavaScript
除法替代。需要复用时仅提取小型纯数值函数，不让生成器执行一场战斗来猜常量。
原生证据不足或数值行为不明确的运算先保留。

### 第二步：删除无用写入，再删黑板值

为每个值区分所属定义、作用域、键名和数值或字符串类型。同名键不一定是同一块存储；
技能黑板、Buff 实例黑板、实体黑板、条件黑板和父子序列的共享黑板分别处理。

从所有保留行为需要的输入反向查找：保留一次读取，就保留可能为它提供值的写入；
保留一次写入，就继续检查它的输入和控制其执行的条件。循环反复分析，直到保留集合不再变化。
同一技能所有时间线、已安装监听器、结束回调、Buff 触发和实体被动都是分析入口，
不能只看一条时间线，也不能只看某次模拟实际触发过的监听器。

删除无用值需要证明以下条件；当前实现只删除无人使用的算术链和初值，尚不删除覆盖写入：

1. 同步局部序列中，某次赋值在任何读取前必定被覆盖，且两次写入之间没有能读取它的事件或回调。
2. 纯计算的结果不再被读取，而且计算本身没有随机抽样、记录、诊断或其他副作用。
3. 删除上述写入后，只被这些计算使用的上游临时值也可以继续删除。
4. 没有剩余读取、外部访问或受保护用途的键，可以从相应默认值、等级列和局部初始化中删除。

例如 `临时值 = 2; 临时值 = 3; 使用临时值`，仅看读取顺序还不足以删除第一次赋值。
还要核对写入语义，并证明中间同步事件或回调读不到该值。
`临时值 += 0` 也不能仅凭算式删除：仍需检查读取、缺省值处理、舍入和写入是否有影响。

当前运行时的 `assignDynamic` 还会在新旧值相差不超过 `1e-5` 时保留旧值。
因此两次 `assign` 也不等于无条件覆盖：初值为 `3.000001` 时，先写 2 再写 3 得到 3，
只写 3 则仍是 `3.000001`。首批仅删除结果完全无人使用的算术链，不应用普通的覆盖写入删除规则。
此外，删空序列会改变其再次执行时的返回值；保留一个步骤时，必须同时恢复它依赖的初值和写入。

实体继承分析先收集全库外部读取，再检查接收实体的寿命、子技能和被动，以及 Buff 的生命周期、
属性、伤害、护盾等动态参数。首版不按 Buff 宿主或查询目标排除同名键，宁可多保留一些值。
实体缺失、递归成环或存在未知访问时，不声称已经查清用途。投射物结束回调保存父技能本层（direct）黑板的快照，
其所有延时入口的读写都要传回父技能；回调或子作用域已有同名初值，也不能证明父值无用。
这里裁剪的是技能传出的无用值，尚不删除 Buff 和实体自身的黑板或定义身份。

装备静态词条另有一个可以直接判断的情况：构筑属性已写入 `modifiers`，且没有启用、初始化或事件入口时，
运行时根本不会创建这项贡献的动作黑板。因此整块黑板可删，完整等级属性仍由 `modifiers` 提供。
这个判断适用于任何位置的武器词条和套装，不能写成“固定删除前两个词条”。
贡献中保存的 Buff 蓝图使用独立的实例黑板，不能跟着一起删除。即使初始化序列为空，它仍是运行入口。

有运行入口的装备贡献也逐键检查初值：先简化分支，再汇总启用、初始化、全部事件条件与程序的读写。
既不读取也不写入的键可删；写入目的键仍须保留旧值，避免改变 epsilon 比较结果。
整板复制或其他未知访问保留整板。这个步骤只删初值，保留入口、装备宿主、事件注册、写入动作，
也不把该贡献持有的 Buff 蓝图黑板当作同一块板。

以下访问必须纳入保留集合或明确阻止相关裁剪：

- 技能时长、费用、冷却、伤害修正、Buff 寿命、实体初值等动作树以外的字段读取。
- 天赋、潜能、等级补丁和装备修改指向的键。首批保留这些修改目标，不删除补丁来规避校验。
- 用户可覆盖的参数和编辑器公开使用的键。可调整值不能因为当前默认值固定而被常量化。
- 子技能安装、Buff 赋值、投射物回调与实体被动的跨对象传值。
- 运行时拼接的键名或尚未明确的访问，保留可能被访问的那块黑板；不要扩大为全项目禁用优化。
- `inheritParent` 等整体复制：先视为所有键可能传出。只有接收方的完整读取已知，才按键缩小范围。
  `shareParentBlackboard` 则必须按共享存储处理，不能误认为子序列拿到了一份副本。

各等级、未命中等级补丁时的默认值、动态声明以及技能重置时的初始化语义都要保留。
若某项优化只有选定等级、潜能或配装后才成立，应留给场景编译器，不能应用到通用生成数据。

### 第三步：复查动作与整份引用

分支和黑板裁剪后再次检查局部动作，直到没有新的可删除节点。
最后重新计算 Buff、技能和实体引用，清除没有任何保留入口能访问的私有定义。
按公共 ID 导出、可供其他对象引用或可由用户选择的定义是入口，不因当前干员未引用就删除。

跨对象删除必须同时考虑直接调用、ID 与标签查询、层数读取、监听事件、技能槽替换和动态引用。
后续可以将“读取哪些键、观察哪些身份、发布和监听哪些事件”保存为每个定义的小型摘要，
减少同时保留的已组装对象。当前两阶段实现仍保留待优化的最终定义，不保留整批原始转储和完整计划。
摘要不足或可被未分析对象访问时保留相关定义，不能通过本地引用计数推断全局无用。

尤其不能直接删除这些内容：

| 看起来没有作用             | 仍可能有的作用                                       |
| -------------------------- | ---------------------------------------------------- |
| 零倍率伤害、零资源变化     | 命中、停帧、事件通知或结果记录                       |
| 没有数值修正的 Buff        | 身份、标签、层数、刷新、结束事件、技能资格或 UI 显示 |
| 结果未使用的概率条件       | 推进后续战斗使用的随机流                             |
| 空监听器、空循环或空作用域 | 注册寿命、次数限制、返回值或清理时点                 |
| 数值没变的写入             | 初始化、浮点舍入、缺省值处理或其他读取者可见的状态   |

纯表现随机数已有独立的来源裁剪规则；它不等于所有随机动作都可删除。
不要用“伤害不变”扩大那条规则的适用范围。

### 实施顺序与验收

公共 `compiler` 目录中的用途分析和优化入口已接到干员、公共 Buff、武器和套装生成。
已有投影规则继续负责原生语义，渲染器继续只负责输出。
先补每种动作和条件的明确用途描述，不先搭通用插件框架或增加一批配置开关。

后续扩展仍按以下顺序独立验证：

1. **只分析**：生成候选清单和保留原因，产物不变。建立当前生成器的基线。
2. **局部分支**：处理字面量条件、纯空分支和等价分支，验证短路、返回值与步骤身份。
3. **局部数据**：处理同步序列中的无用写入、纯计算和无用初值，再扩展到跨时间线与作用域读取。
4. **跨定义引用**：覆盖装备、队友、实体被动和事件后，再裁剪无入口的私有定义。

验证期间提供内部“不应用、只报告、应用”三种模式，用同一份来源和输入比较新增优化前后。
这只控制新增优化，不撤销原有场景投影；模式不写进干员配置。每条裁剪记录包含来源文件与
原始动作路径、定义及作用域、规则、依赖的场景前提、删除内容的摘要和保留身份映射。
将它们放入现有候选审计输出，汇总被删除的分支、动作、黑板键、初值单元和定义数量。
被未知消费者阻止的候选也统计原因，不能把“未分析”计作优化收益。

必要验证包括：

- 规则正例与反例：带写入的条件、短路、返回值被消费、空 Switch 分支、随机流、浮点边界。
- 作用域与时间：同名键、父子复制或共享、跨帧读取、事件重入、延迟回调、结束和重置。
- 真实机制：洛茜 Buff DOT、卡蜜拉实体被动、弭弗零倍率命中、装备对 Buff 事件的响应，
  以及会改黑板的等级和潜能组合。样本用来发现漏判，不能替代删除规则本身的证明。
- 新优化开关两侧使用相同输入、随机样本和推进方式，逐项比较命中、资源、Buff 变化、
  事件及清理顺序、窗口、诊断、可见黑板和存档连接；不只比较 DPS，不以旧版输出为答案。
- 检查步骤 key 不变、引用闭合、再次优化不再变化、重复生成一致，并运行现有候选类型检查、
  全技能、组合轴和装备验证。正式数据仍通过既有候选发布流程更新，不手改生成文件。

`CombatStepReached` 和 `CombatConditionEvaluated` 是编译树的内部遍历记录，裁剪后允许减少。
双路比较仅排除这两类记录；其余战斗事件仍按原顺序逐项比较。曲线和诊断中的回执序号
要同步映射到保留事件，确认引用仍指向同一件事，不能直接删掉引用字段来让测试通过。
同一来源的新增优化保留伤害步骤 key，用它逐项核对裁剪前后结果。
这不要求原生投影修复维持错误的旧结构；正式发布前不为开发期间的旧命中编号增加兼容迁移。

性能同时记录生成耗时、输出体积、场景编译耗时、模拟耗时和峰值内存，使用固定样本预热后重复测量。
删除数量不等于速度提升；只有量测后才能报告收益。分析按对象串行进行，增量更新受影响的节点，
避免每轮反复复制或序列化整棵树。当前缓存只在一轮内复用原始来源与固定目录解析结果；
若将来复用编译结果，还必须区分来源版本、优化规则与场景前提，不能直接扩大原文缓存的职责。
达不到证明条件时停止该项裁剪并报告原因，不为了减少行数引入难以核对的抽象。

## 资源下载与来源

活动机制同样先转换为公共定义，再参与场景编译。活动参数、关卡信号和Buff的含义需要追到实际消费者，
不能把表中的数字直接当成伤害倍率。活动适配器保留来源，复用通用动作和状态；界面只修改选择与参数，
不直接写运行状态，也不在战斗核心按活动名称分支。

Endaxis的 `akedb-sources.json` 声明需要哪些资源。combat-spec提供行为依据，不决定下载范围。
下载器先查AKEDB，再按规则使用可选的VFS提供者。AKEDB有集合清单时，仅对清单中的缺失文件回退，
不混入VFS的额外成员；整个集合缺失时才使用VFS清单。

投射物和能力实体资源按SkillData/BuffData中的引用取得，不需要先完整解包游戏。
每个文件记录实际提供者、位置、长度和SHA-256。混合来源必须如实标记，不能称为纯AKEDB版本。
解码不完整必须失败，不能用预览截断内容生成正式定义。

## 目标查询不能在转换时猜完

模板ID集合只说明哪些类型可能出现；运行时仍需从真实实例中选目标。
查询需保留Owner、对象类型、标签、施法身份过滤及原生顺序，不能自行附加“当前施法”条件。
标签父子关系来自同版本目录；只有裸ID时只能精确比较，不能猜层级。

目标组写入保留完整SkillData来源路径，后续转换沿用同一路径，不另扫原始JSON或拼一套坐标。
下载规划可以报告尚未取得的引用；正式编译遇到相关查询时必须有足够的资源和规则。

排序、数量限制、Buff过滤和洗牌参数必须完整保留。确认了代码顺序后才生成可执行操作。
已支持的Owner距离排序保留升降序、显式数量及未限量时128上限；其他未确认的排序或筛选报错。
洗牌先执行，再根据运行时数量裁剪；不能把Unity随机来源替换成战斗使用的另一随机流。

## 顺序、显示与扩展

同帧动作按序列顺序执行，条件持有完整分支，不能拆成散落的前后伤害标记。
战斗帧使用30 FPS；变速改变对象每帧消耗的局部时间，不改写用户放置帧，详见 [时间、变速与显示](time-and-display.md)。
技能组组织单段或有序技能，展示变体与技能种类分开。
LevelValues中的单个数值适用于所有等级，数组表示逐等级数值；倍率按定义约定使用百分比。
语法helper只做通用构造，不藏干员专属规则或执行模拟。
运行时只使用准备好的数据，不读取旧生成TS、翻译或界面状态。
资源警告与曲线读取同一份战斗记录，不各算一套账。

本地化发生在显示处，主题使用统一样式变量。缓存、可视区域渲染和性能优化不能改变结果，
也不应引入难以追踪的全局状态。特殊机制只有在通用动作不能清楚表达时才使用明确扩展点。
旧项目经过专门导入和同等校验，新代码只写当前格式；旧实现只用于体验参考，不提供游戏规则。

## 一次编辑怎样得到结果

1. 页面通过 `src/data/gameDataRepository.ts` 查询和展示游戏定义。游戏文字按需加载，不影响战斗计算。
2. `src/application/openProject.ts` 识别并加载项目。旧格式先转换，再做结构和目录引用校验。
3. 编辑命令生成新输入，由 `src/application/editor/scenarioEditorSession.ts` 管理提交和撤销。
   选择、拖拽和弹窗状态不混入存档。
4. `src/core/compiler/compileScenarioRuntimeAssembly.ts` 汇总构筑、面板、时间轴、敌人和资源。
   编译结果不引用Vue对象，也不写回用户输入。
5. 支持范围检查在运行前报告未知步骤，避免执行一半后才发现不支持。
   相关规则见 `src/core/combat/runtime/standardPlayerDamageCompatibility.ts`。
6. `src/core/combat/runtime/combatRuntimeAssembly.ts` 创建本场状态并执行程序。
   应用层组织推进和结果冻结，专用环境不能再复制一套模拟循环。
7. 运行时记录发生的事实；`src/core/projection` 据此生成资源、状态、诊断和日志。
8. 界面整理这些结果并显示。新增显示优先使用已有记录，确实缺少事实时才补运行时记录。

每次模拟使用自己的可变状态。编译数据可复用，运行时对象不能跨场缓存。
同一实体的Buff查询与伤害修正必须读取同一份Buff状态。同一技能需要共享的冷却由明确的管理者维护，
不能让多个放置块各自结算一份，或重复推进时间。
缓存需要覆盖输入、游戏数据、编译规则和运行环境的变化；语言、主题不应改变战斗结果。
Worker只负责把执行放到后台，不另造一种核心行为。

## 界面操作

保留用户熟悉的轨道、技能库、拖放、复制粘贴和构筑编辑流程，不因内部重构随意改交互。
组件发出操作，命令修改项目，会话记录历史，随后重新计算显示和模拟结果。
复制粘贴为新项目对象分配新身份；框选、菜单、焦点和拖拽过程不保存为项目输入。

快捷键通过 `src/ui/keyboard/keyboardShortcutRouter.ts` 管理：活动作用域先处理，
弹窗阻止底层穿透，文本框保留正常编辑键，作用域销毁时注销。不要散落新增全局按键监听。
主题通过 `src/ui/theme/themeRegistry.ts` 管理，界面使用统一变量。
游戏文字与界面文字在显示处解析，语言和主题不进入战斗缓存。

不再依赖已经移除的旧Store、Simulator或旧文本适配层。
具体定义编辑和交互规则见 [项目模板与编辑器](editor.md)，放置与输入边界见 [技能说明](skills.md)。
