# Endaxis 事件系统：从游戏行为到程序结构

本文面向玩过《明日方舟：终末地》、掌握基本编程知识的读者。无需先读反汇编或熟悉项目代码。

核对日期：2026-09-10。本文描述**当前架构及明确的未完成项**，不按提交顺序叙述。
游戏行为依据来自游戏数据和 combat-spec 的反编译研究；本文中的教学例子不代表某件真实装备的效果。

## 1. 现在收束到哪一步了？

**主要运行链路已经统一，但事件系统还不能宣布全部收束。**

现在不是“技能、Buff、武器各有一套事件系统，然后互相转译”。主要原生事件已经共用事件身份、
类型化载荷、同步分发器、动作目标绑定和响应上下文。不同宿主主要负责自己的黑板与生命周期。

剩余问题并非都只是整理代码：部分结束路径还可能漏发或重复发消费通知，少数条件读取仍未贴合
原生语义。修好这些之后，才能把架构统一视为行为上也收束了。

投射物尤其需要区分三层寿命：**触发结束回调、回调技能及其中的动作区间、投射物对象回收**。
目前 duration-finish 路径已使用独立生命周期实例，回收等待来自全部启用回调的原始技能时长；
结束并不立即回收。该路径的163发射通知已经接入，SkillAffix与能力实体共用实际对象的
reset引用；它不监听“投射物结束”来提前释放引用。但回调内部仍是旧的即时动作投影，
其他投射物形状尚未全部接入，因此不能把这个路径贯通误读为整条投射物事件链已经完成。

| 方面                                           | 当前状态             | 不应误读为                           |
| ---------------------------------------------- | -------------------- | ------------------------------------ |
| 公共事件身份、载荷、主要发布订阅链             | 已贯通               | 游戏全部事件都已支持                 |
| Buff、配装、干员被动、技能临时监听的公共响应链 | 主要路径已接入       | 所有宿主允许订阅完全相同的事件集合   |
| 响应期间的事件、目标和来源切换                 | 已统一，支持嵌套恢复 | 事件来源等于当前动作宿主             |
| 注册、启用、销毁和共享黑板                     | 主要宿主已按职责拆分 | 宿主之间生命周期完全相同             |
| Buff 结束／减层来源                            | ID／Tag 路径已接通   | 当前实例结束、点燃等全部调用点已完成 |
| 兼容事件、优先级映射、特殊上下文               | 仍有待办             | 可以凭名字合并或直接删除             |

## 2. 用一个例子区分四件事

假设有一个效果：“持有者造成电磁伤害后，给自己添加一个增益”。它可以拆成：

1. **事件**：刚刚发生了什么？这里是“造成伤害”。
2. **载荷（payload）**：这次发生的具体情况，例如伤害类型、受击目标以及该事件实际携带的来源信息。
3. **条件**：这次是否符合要求？例如伤害类型是否为电磁。
4. **动作**：符合后做什么？例如添加 Buff。

“电磁伤害”通常是事件数据中的条件，而不是给每件装备另造一个“本装备的电磁伤害事件”。
同理，监听器来自天赋还是武器，不应改变“造成伤害”本身的含义。

还要区分**发布事件**和**执行效果**：发布“法术爆发”通知本身，不等于自动扣一次敌人生命。
实际伤害必须由对应游戏数据中的伤害动作进入伤害管线。否则事件监听和伤害动作都结算一次，就会重复伤害。

代码中的三个常见词：

- `trigger`：什么时候开始响应。兼容触发器可能还包含旧的筛选条件。
- `condition`：读取当前状态或本次事件，判断是否满足要求；部分原生条件还会将匹配结果写入黑板。
- `step`：执行程序中的一步。既可以是伤害、添加 Buff，也可以是包含子步骤的条件分支。

因此，“条件”不应简单理解成绝无副作用的布尔函数；是否写黑板由原生条件的证据决定。

## 3. 整体上有两条管线

### 3.1 游戏数据变成可执行定义

```text
游戏导出数据                         反编译证据
     │                                  │
     │                          combat-spec 行为规格与测试
     ▼                                  │ 校验语义
game-data-compiler：解析 → 公共事件投影 → 条件/动作序列转换
     │
     ▼
game-data-contract 约束的干员、武器、装备、Buff 等定义
     │ 选取等级、潜能、配装等
     ▼
运行时编译程序 → 安装到一场战斗中
```

这里有两种不同的“编译”：游戏数据编译器把原始格式转换成 Endaxis 定义；运行时编译再根据
本次构筑，得到模拟实际使用的程序。生成器不是模拟器，公共契约也不负责执行伤害。

公共响应的大致结构是：

```ts
{
  (event, // 监听哪一种公共事件
    priority, // 数据响应的执行优先级
    sequence); // 响应时执行的动作序列，可包含条件
}
```

这是结构示意，不是可直接粘贴的完整技能定义。实际类型为 `AbilityEventResponse`。
原始名称投影和事件程序遍历有公共实现；宿主转换器仍负责等级、安装位置和当前支持范围。

### 3.2 一场战斗如何执行事件

```text
技能 / Buff / 其他已建模动作
     │
     ▼
伤害、治疗、附着、资源等领域模块
     │ 在正确时点发布有类型的事件
     ▼
对应实体的分发器
     │
     ├─ 固定回调
     ├─ 数据动作响应（按优先级）
     ├─ 技能监听阶段
     └─ 连携监听阶段
              │
              ▼
     绑定本次事件与动作目标
              │
              ▼
     共同条件 / 动作序列执行器
              │
              └─ 产生新效果，必要时同步发布下一事件
```

这不是网络消息队列，也不是下一帧才处理的通知中心。事件通常在当前调用中同步完成：
外层动作要等监听器执行完，才能继续后面的逻辑。

“技能临时监听”这个名字也不意味着它必须放在图中的“技能监听阶段”。已恢复的原生
EventListenerAction 注册的是数据动作，当前转换走数据动作阶段。

## 4. 同一个事件，究竟要统一什么？

### 4.1 一份身份，一份对应的载荷类型

`addedBuff` 表示已有定义的事件身份；具体是哪个 Buff、作用于谁，是载荷里的数据。
`AbilityEventPayloadMap` 约束事件与载荷的对应关系，不能把伤害载荷塞给添加 Buff 事件。

公共契约保存可序列化的定义。运行时载荷可能带有实际 Buff 引用、可变伤害对象或操作回调，
因此放在运行时层，而不是塞进项目存档协议。

同一次发布的主要消费路径拿到**同一个事件对象及载荷引用**。不为武器复制一份，再为连携
改写另一份。尤其在伤害前处理阶段，监听器可能要修改尚未结算的伤害对象；复制载荷会让修改失效。

但“同一个对象”仅针对同一次发布。`beforeOutputDamage` 与 `outputDamage` 是不同时点的事件，
不能因都涉及伤害就合并。输出侧和承受侧的通知也不天然相同。

### 4.2 一套分发规则，不是所有实体混用一个无归属广播

每个实体有自己的事件分发入口。监听谁与事件载荷中涉及谁，是两个问题。
例如施加方的 `outputBuff` 和接收方的 `addedBuff` 可以描述同一次施加的不同侧面，
却分别在不同实体上发布。不能只对比事件名称而忽略注册位置。

当前分发器的数据动作按整数优先级从高到低执行；同优先级按注册顺序执行。
这是当前已恢复规则，不代表原生所有优先级枚举都已映射。生成器仍拒绝未经支持的非默认配置。

### 4.3 一套条件和动作解释，不是一套宿主生命周期

假设天赋与武器都判断“本次 Buff ID 是否匹配”，应调用同一事件 Buff 读取与条件实现。
但是武器卸下时何时注销、临时技能监听何时结束，必须由各自宿主负责。

**统一的是行为含义和执行基础设施；保留的是有真实含义的生命周期差异。**

### 4.4 “结束”不是一个通用的销毁操作

同样是画面上的状态消失，游戏里可能经过不同路径。不能为了统一接口，让所有路径都发布
“Buff 正常结束”事件，否则监听这个事件的技能或装备会被额外触发。

| 路径                              | 当前确认的职责                        | 不能顺带做的事                       |
| --------------------------------- | ------------------------------------- | ------------------------------------ |
| 单次施法结束（CastEnd）           | 结束本次时间轴，清理本次施法附属 Buff | 无条件清空整个 Ability 拥有的子 Buff |
| Ability 禁用（Disable）           | 注销响应，清理被动与 Ability 子 Buff  | 把它视为每次 CastEnd 都会发生        |
| Buff 正常结束（Finish）           | 按结束原因执行相应动作与通知          | 把原施加者自动当成本次结束来源       |
| 宿主释放自身 Buff 容器（Release） | 释放修正、持续动作和监听，关闭表现    | 补发普通结束／减层事件               |

例如能力实体销毁后，其身上的状态条需要消失，但这不意味着触发一次“消费 Buff”。
Endaxis 使用 `BuffReleased` 表现回执关闭状态；它不是新增的可配置 AbilityEvent。
“Ability 拥有的子 Buff”和“附着在这个实体身上的 Buff”也不是同一份列表，不能混清。
上述区别已有反编译依据；实体各组件的完整销毁顺序仍在验收中。

## 5. 最容易混淆的：谁是谁？

以下以“A 给 B 施加一个 Buff，后来 C 的技能结束这个 Buff”为例。它只是身份示意。

| 身份               | 示例                             | 含义                            |
| ------------------ | -------------------------------- | ------------------------------- |
| Buff owner         | B                                | Buff 挂在哪个实体身上           |
| Buff source        | A                                | 最初是谁施加了它                |
| 结束来源实体       | C                                | 此次结束／消费由谁引起          |
| 结束事件的施法来源 | C 的此次技能                     | 具体哪次施法，不只是一个实体 ID |
| 监听宿主           | 可能是 B 的 Buff 或 C 的装备能力 | 谁持有响应程序、黑板和注册句柄  |

这些身份不能互相补位。找不到事件施法来源时，不能拿 Buff 最初施加技能顶上。

动作环境与事件上下文也不同：

- **动作环境**：这段动作属于谁，它自己的黑板、Buff/技能实例和施法来源是什么。
- **事件上下文**：现在为什么执行这段动作，本次事件携带了哪些数据。

监听器执行时保留两者，不把事件来源覆盖成宿主身份。不同原生动作和条件读取哪一种，
由对应证据决定，不能制定“所有动作都用事件来源”的省事规则。

### Input、Trigger 与 sourceId/targetId

原生响应还会设置动作读取的 Input 与 Trigger。Endaxis 用公共事件绑定表解释它们。
例如 `outputBuff` 和 `addedBuff` 对载荷两端的绑定相反，因为它们发布在不同一侧。

所以 `payload.sourceId` 不应被无条件当作“此次分发所在实体”。无目标事件也不能为了
填通用接口而补一个 `targetId = 自己` 或 `targetId = 木桩`。

### 未知来源和明确无来源

能力实体的出生/结束事件现从控制器出生时保存的完整施法信息读取来源；结束它的动作
不会替换该来源。出生通知先于子技能启动。两边均已接通真实生产端，而非只有载荷类型；
原生地址与尚未扩展的死亡/释放调度边界见 combat-spec 的 `ability-entity-event-origin.md`。

当前代码区分：

- `undefined`：没有提供，或者这条路径尚未恢复该信息。
- `null`：明确没有来源施法。
- 来源对象：明确是哪一次施法。

三者都不能触发“去借用外层事件来源”。需要来源才能判断的条件，遇到未知值可以报错；
明确无来源则按该条件的已恢复规则处理。这比悄悄猜一个来源更能暴露模拟缺口。

## 6. 为什么需要临时上下文和持久黑板？

一次响应可能在执行中触发另一个事件。例如外层伤害响应添加 Buff，添加 Buff 又触发内层响应。

```text
进入事件 A → 保存外层上下文
  执行动作 → 同步进入事件 B → 用 B 的事件、目标、来源
                         ← B 结束，恢复 A
继续执行 A
A 结束 → 恢复进入 A 之前的上下文
```

`withAbilityEventResponseContext` 负责这个作用域，使用 `finally` 保证异常时也恢复。
恢复的是事件、事件来源和目标绑定，不是把宿主的所有战斗状态回滚。

**黑板**可以理解为动作程序的变量表。一次事件结束，不意味着把能力积累的计数清零。
当前配装贡献实例的初始化和响应共用黑板；不同实例隔离，即使使用同一模板也不共用计数。
角色持久黑板、能力/动作黑板也不是可以随意混成一张全局表的东西。

响应还持有自己的动作序列实例，不能每次收到事件就重建，借此绕过重入或已执行状态。
同样不能用一个全局“正在响应”开关屏蔽所有嵌套事件。序列的执行规则与事件分发规则是两个层次。

| 宿主          | 特有职责                                        | 共用内容                           |
| ------------- | ----------------------------------------------- | ---------------------------------- |
| Buff          | 实例、启用/结束、子 Buff 等生命周期             | 原生事件、条件、动作、响应作用域   |
| 干员被动      | 能力安装、黑板、启用门禁与释放                  | 同上                               |
| 武器/装备贡献 | 按等级得到能力值、每个贡献实例的启用和黑板      | 同上                               |
| 技能临时监听  | 随所属动作注册，结束或中断时注销                | 同上                               |
| 连携条件      | 根据事件更新连携可用状态、保留自身窗口/等待语义 | 事件身份、相关条件与目标上下文规则 |

主要能力宿主采用“先注册、再安装启动效果、成功后启用响应”的门禁，而不是注册后立刻响应一切。
注册失败须清理本组已有句柄，结束后须注销。这是生命周期职责，不能仅靠总线排序解决。

注销与本次分发中的有效性检查也不同。分发器取得响应快照后，前一响应可能结束后一响应
的宿主；后一响应仍须检查宿主是否有效，不能以“已从注册表删除”代替检查。
Buff 响应现在检查 `!isFinished`，对应原生 `isActionValid`；另一个原生属性
`canExecuteAction` 还要求启用。现已确认原生在每个动作执行前检查后者，两仓公共序列
也逐项读取宿主许可：例如响应的第一个动作结束了自身 Buff，后续动作便不能继续执行。
已开始动作的清理不受这一入口门禁阻止。它们不是同一属性，不能把所有宿主的门禁
统一成一个布尔公式，也不能只在收到事件时检查一次。
临时监听在序列外求值的前置条件也读取同一许可；投射物回调属于另一个宿主，
不把发射者的启用状态当作自己的许可。来源施法信息的继承不等于宿主状态的继承。

干员被动与配装响应也把自己的实时许可交给同一个公共序列执行器，不仅在响应入口
检查一次。响应中途释放宿主会阻止后续动作，但已经执行的动作仍会清理；这不改变
其他宿主的响应，也不表示所有宿主的 Disable/dispose 调用顺序已核实完成。
Buff 完整启用/禁用顺序仍在核对中。

## 7. 哪些东西不应强行统一？

1. **原生能力事件、组件内部处理和模拟回执。** 伤害修正钩子、展示记录未必都是可配置的能力事件。
   反过来，未列入公共枚举也不证明它在游戏中无效。
2. **事件事实与画面显示。** UI 从模拟回执投影 hit、Buff 图标和持续时间。不能为了补一个图标
   虚构战斗事件，或者用展示段是否结束决定实际效果是否结束。
3. **正常事件与人工外部标记。** Endaxis 把敌人简化为木桩，不模拟敌人主动攻击；必要的外部事实
   可以显式标记，但不能伪造完整受击上下文。治疗仍可发生，包括满血时的治疗行为。
4. **自由编辑与严格模拟。** 用户放置的操作可以不合法；模拟应给出真实告警，不应偷偷替换技能、
   删除效果或禁止编辑，只为让结果看起来正常。

空间简化也不意味着事件语义可以随便简化。距离、范围和唯一敌人可以按项目模型折叠，
但谁消费了 Buff、事件顺序、黑板值以及伤害修改仍会影响模拟结果，必须保留。

## 8. 当前还差什么，怎样才算完成？

### 近期必须收束

- **SkillAffix 引用保留：**目前直接技能结束回调已经修正为空来源，但仍缺实体/投射物/
  输出 Buff 的完整引用保留。已证实原生跟踪的是实体 reset 回调和 Buff recycle 回调，
  不能拿能力实体结束事件或 Buff 结束事件冒充。动作注销只解除跟踪，不结束被跟踪对象；
  引用耗尽则以 Other、空施法来源结束所属 Buff。这是现有机制的技术债，尚未完成。

- **Buff 结束与点燃：**Environment 当前实例结束已贯通显式来源和动作环境施法信息；
  点燃外层的消费补发已删除，映射结束标志改为遍历后统一收尾。原生消费保护与禁止结束
  是不同机制；当前来源仅见未接入的敌人 Buff 使用消费保护，本轮不新增该能力。
  其他直接结束调用者仍需核对，不能据此宣称所有结束路径完成。
- **剩余 Buff 上下文：**其他直接结束调用者、事件 Buff 黑板的未确认子类仍需逐项核对。
  正向增强已确认是“增强尝试”：后置动作后发布本次来源与+1，满层也发布、定时增长不发布。
  实际增强先增层、执行内部动作，再刷新属性；内部动作与对外增强尝试事件不是同一个阶段。
  结束/消费/吸收事件黑板已改读原事件携带的实际实例，发布时快照不再替代同步状态；
  已有 Target + Context 切片也检查动作输入目标，缺失时失败；其他上下文子类仍待核对。
  已修正上述结束、减层、消费及增强尝试来源，不能概括成所有 Buff 事件已完整。
- **护盾值读取：**已区分原生动作的两条路径：新增量读取147事件，当前值读取显式目标的
  实时有限护盾。公共步骤保留 `target: actionOwner`，只接纳已审计的 Owner；缺目标或
  所需事件成功返回而不写入。执行统一交给 Buff 操作端口，不在黑板执行器重建目标解析。
  原生证据见 combat-spec 的 `docs/save-shield-value-to-blackboard.md`；不扩展未知目标范围。
- **兼容与类型边界：**旧语义监听、手工击飞/倒地入口仍有用途，不能因为正式生成数据不用就删除。
  响应入口的逐类识别链及 `abilityEventPayload.ts` 已删除；内部来源读取直接接受统一事件映射，
  不再降为 unknown 后重解析。2026-09-10 又移除16个事件分类读取器的 unknown 输入、
  不完整字段重验和恢复类型断言；它们只依据统一事件名收窄并返回同一对象。
  真正的外部输入校验保留。动作环境绑定也已改为整体接收强类型事件，战斗装配和连携
  共用公共端点绑定表；无目标事件不补造目标，未绑定事件不猜测。连携发布转交已在完整
  事件上收窄，去掉两处强制转换；发布准入范围仍独立于端点绑定表，不能直接等同或扩张。
- **优先级及支持范围：**共同排序机制已有实现，完整原生优先级映射和部分准入边界仍待核实。
  不为宣布“统一”而放行未知行为，也不在本轮扩展关卡脚本或敌人主动行为。

### 验收不是只看测试数量

对每条迁移链，应能回答：它由哪个原生调用点发布、在哪个实体上发布、携带什么、什么顺序、
谁注册和注销、条件如何读取、是否存在另一条重复解释或派发路径。

测试应覆盖：原对象引用、同步修改可见、发布顺序、来源不同/为空/未知、嵌套恢复、结束注销、
同模板多实例隔离，以及真实轴完整回执与告警比较。相关生成路径变动时，还要重新生成并审阅产物。

近期已有 1172 项运行时/Buff 回归及四条既有真实轴比较通过，但它们不能证明上述未完成项正确。
这是最近检查点记录，不是本文编写时重新运行的全套测试；复刻库另有依赖本地资产的测试无法通过。
