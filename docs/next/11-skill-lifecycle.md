# 技能全生命周期与编辑语义

本文从整体上说明 Endaxis Next 中一项技能从游戏数据、干员定义、技能库、时间轴技能块、用户编辑、构筑修正、编译、运行到投影的完整处理方式。本文是跨层契约；具体字段和全部组件见[SkillDefinition 数据结构蓝图](./12-skill-definition-blueprint.md)。

## 1. 核心结论

干员 TS、技能库和编辑后的技能块使用同一种 `SkillDefinition` 描述基础技能逻辑，并由同一套编译器和运行时解释。三者的区别只有来源和所有权：

```text
干员 TS 中的技能模板 ─┐
                      ├─> SkillDefinition -> 构筑修正 -> 编译 -> 运行
技能块的自定义定义 ───┘
```

必须遵守以下原则：

- 未编辑技能块只保存模板引用，不保存技能逻辑副本。
- 用户首次编辑技能逻辑时，完整复制基础模板，形成自定义 `SkillDefinition`。
- 自定义定义只包含技能自身逻辑，不包含天赋、潜能、武器、装备和活动机制。
- 模拟时在技能模板和自定义技能定义中二选一，不混用两边的字段。
- 当前技能等级和构筑修正在每次模拟前重新解析。
- 编译结果、运行时状态、伤害结果和投影数据均不进入项目存档。
- 编辑器可以产生 ViewModel，但不得建立第二套技能逻辑结构或第二套解释器。

## 2. 三种稳定身份

### 2.1 技能组 `SkillGroupDefinition`

技能组是技能库中的放置单元，负责：

- 技能大类，例如普攻、战技、连携技、终结技；
- 从干员构筑的哪个字段读取技能等级；
- 一次拖放产生一个技能块，还是按顺序产生一组技能块；
- 名称、图标和形态等展示投影的稳定入口。

普攻链可以由一个技能组包含多个 `SkillDefinition`。技能组不是执行步骤，也不参与单次技能内部的动作顺序。

### 2.2 基础技能 `SkillDefinition`

`SkillDefinition` 描述一项可独立释放或触发的基础技能：费用、冷却、可用性、动作黑板、按帧调度的有序步骤、连携窗口和事件响应。它不包含时间轴位置、颜色、锁定状态、本地化文本或模拟结果。

### 2.3 技能释放 `SkillCastDocument`

技能释放是用户放在某条轨道上的一次动作。它拥有项目内稳定 `id`、模板来源、开始帧和编辑器展示状态。其逻辑来源为二选一：

```ts
const baseDefinition = cast.customDefinition ?? catalog.requireSkill(cast.source);
```

存在 `customDefinition` 表示该技能块已脱离模板，应显示铅笔角标。即使它当前恰好与模板完全相同，脱离状态也不会自动消失。

## 3. 各层保存什么

| 层级       | 权威数据                                     | 不得保存                        |
| ---------- | -------------------------------------------- | ------------------------------- |
| 干员目录   | 官方基础 `SkillDefinition`、技能组、养成效果 | 项目位置、编译标量、运行时对象  |
| 技能库     | 对技能组和技能定义的展示投影                 | 技能逻辑副本                    |
| 项目技能块 | 来源引用、位置、展示状态、可选完整自定义定义 | 编译结果、伤害结果、运行时 Buff |
| 构筑解析   | 当前等级、天赋、潜能、武器、装备和活动贡献   | 项目文档回写                    |
| 编译器     | 本次模拟的不可变单等级程序                   | 持久化状态                      |
| 运行时     | 黑板、冷却、调度游标、资源、Buff 和事件状态  | 回写技能定义                    |
| 投影层     | 技能块、命中点、曲线、日志和诊断 ViewModel   | 修改核心运行状态                |

## 4. 从干员 TS 到技能库

干员 TS 使用共享的类型和构造助手声明 `SkillDefinition`。构造助手可以提供写作简写，但目录注册前必须得到规范化、可校验的数据结构。未知步骤、未知条件、无效等级数组和重复稳定键必须在目录加载或生成阶段失败。

技能库读取 `SkillGroupDefinition`，只派生名称、图标、技能类型、块宽和形态等展示信息。点击技能库条目不能直接改写技能定义；拖放后只在项目中创建模板引用。

## 5. 放置未编辑技能块

未编辑技能块建议保存：

```ts
interface SkillCastDocument {
  id: string;
  source: {
    kind: 'operatorSkill';
    skillGroupKey: string;
    skillKey: string;
  };
  placement: { startFrame: number };
  presentation: {
    locked?: boolean;
    disabled?: boolean;
    color?: string;
    customBars?: EditableBarDocument[];
  };
  customDefinition?: SkillDefinition;
}
```

存档的 `customDefinition` 直接使用 `core/game-data/operatorDefinition.ts` 中现有 `SkillDefinition`。TS readonly 不影响 JSON 反序列化。干员 TS、技能库、自定义技能块只有这一套结构。

移动、复制、锁定、禁用、改色和编辑自定义展示条不属于技能逻辑编辑，不应生成 `customDefinition`。

## 6. 首次编辑与写时复制

编辑面板操作本地草稿。用户首次实际修改技能逻辑时：

1. 从当前游戏数据读取技能模板，不能读取编译程序。
2. 深复制并规范化为项目可序列化的 `SkillDefinitionDocument`。
3. 在草稿中修改组件。
4. 对结构、引用、等级值和构筑修正兼容性执行严格校验。
5. 只有校验通过后才把完整自定义定义作为一次项目命令提交。

自定义定义保留 `LevelValues`，不能把当前等级倍率展开成标量后保存。技能 `key` 和来源身份不可由普通编辑器修改；新增自定义组件使用技能块内稳定局部键。

## 7. 无基线 Diff

项目不保存首次编辑时的基线。编辑器每次打开时比较：

```text
当前技能模板 <-> 当前自定义技能定义
```

Diff 表示“与当前模板不同”，不表示“历史上由用户修改”。规则如下：

- 相同稳定键、相同类型：逐字段比较。
- 相同稳定键、位置不同：标记移动。
- 仅模板存在：标记模板新增或自定义缺失。
- 仅自定义存在：标记自定义新增。
- 模板更新后重新计算，不尝试推断用户过去改过什么。
- 两边重新变得相同后字段星号消失，但铅笔角标保留。
- 恢复模板通过删除整个 `customDefinition` 完成。

可以保存模板 revision、模板指纹和构筑指纹作为来源提示，但它们不参与模拟和 Diff，也不能替代基线完成自动三方合并。

## 8. 等级与构筑修正

基础定义选定后，按以下顺序构建本次模拟程序：

```text
目录基础定义或自定义基础定义
  -> 根据当前技能等级解析 LevelValues
  -> 应用当前天赋和潜能
  -> 合并武器、装备、活动和场景贡献
  -> 严格校验最终程序
  -> 编译为运行时程序
```

自定义技能不复制构筑效果。改变技能等级、天赋、潜能、武器或装备后，未编辑和已编辑技能块都重新编译并接受当前构筑修正。

如果自定义技能定义删除了某个养成效果要求修改的目标，编译必须报告具体来源和缺失键，不能静默跳过，也不能从技能模板补回缺失组件。例如：

```text
潜能 3 需要修改 damage:ultimate-final，
但技能块 cast:42 的自定义定义中不存在该组件。
```

## 9. 编译边界

编译是已知项目的一次模拟所需的纯派生步骤。它负责：

- 把 `LevelValues` 解析为当前等级标量；
- 解析动作黑板初值和组件引用；
- 应用并验证构筑贡献；
- 生成有序、不可变、运行时可直接消费的程序；
- 提前拒绝未知组件、缺失键和不支持的组合。

编译不判断战斗中才知道的条件，不计算最终伤害，也不把产物写回项目。等级或构筑变化通过重新编译生效；性能优化只能缓存纯编译结果，缓存键必须包含定义、构筑和数据 revision。

## 10. 运行时执行

一次释放创建独立 `SkillRuntime`：

1. 预占冷却，并记录冷却或费用合法性诊断。
2. 恢复本次释放的动作黑板。
3. 分配运行时释放身份并执行第 0 帧。
4. 到达 `costFrame` 时先尝试扣费，再执行同帧调度步骤。
5. 调度项按 `startFrame` 升序执行，同帧按定义来源顺序执行。
6. `ActionSequence.steps` 严格按数组顺序同步执行；失败步骤截断该序列后续步骤。
7. 有 `endFrame` 的区间步骤逐帧推进并在边界结束；点步骤执行后立即结束。
8. 所有调度项完成后技能自然结束；新技能可以按已恢复规则中断旧技能。

`timelineBlockFrames` 只控制编辑器技能块宽度，不决定运行时自然结束时间。

## 11. 合法性诊断与模拟的关系

`availability`、连携窗口、资源和冷却检查用于诊断。Endaxis 的产品规则是：用户放入时间轴的动作视为已经成功操作，诊断不删除技能块，也不阻止后续模拟。结构错误、未知组件和无法编译的自定义定义则属于作者数据错误，必须阻止模拟。

## 12. 加载、更新、复制和删除

- 加载未编辑技能块：按来源读取当前模板并重新编译。
- 加载自定义技能块：严格校验完整定义，再应用当前构筑并编译。
- 游戏数据更新：未编辑块自动采用新模板；自定义块保持不变，Diff 改为对比新模板。
- 修改技能等级或构筑：所有相关技能块重新编译，自定义定义本身不变。
- 复制未编辑块：继续保存模板引用。
- 复制自定义块：深复制完整定义；局部键可保留，因为作用域由新 `castId` 隔离。
- 删除技能模板：未编辑块失效；完整自定义块仍保留逻辑，但原技能身份或养成效果无法解析时必须明确报错。

## 13. 不允许的实现

- 存档中同时保存完整默认序列和字段级 `edited` 标记。
- 模拟时把当前模板的一部分与旧快照的一部分混合。
- 编辑器使用与干员 TS 不同的技能逻辑结构。
- 用任意 `Record<string, unknown>` 组件绕过判别联合和校验。
- 在投影层重新解释条件或战斗顺序。
- 在运行时按需访问干员 TS 的等级数组。
- 自定义技能静默吞掉无法应用的天赋、潜能或装备效果。

## 14. 玩家操作、技能解析与替换技能契约（首条竖切已实现）

时间轴首先表达玩家在某个现实时间执行的输入，而不是直接调用某个内部技能。操作身份不另建枚举，
直接复用技能等级来源 `SkillLevelSource` 的四个值：

- `basicAttack`：鼠标左键；普通攻击连段、下落攻击和处决的具体技能均归此操作与等级来源；
- `battleSkill`：当前操控干员对应数字键的短按；
- `comboSkill`：E；
- `ultimate`：当前操控干员对应数字键的长按。

数字 1–4 只是在实时游戏中选择对应队伍位置，不是项目需要持久化的技能槽身份。具体键位也属于 UI
映射，不得进入战斗数据契约。一个技能形态的操作身份与技能等级来源必须是同一个字段；不能再保存一份
命令类型、再保存一份可能分歧的 `levelSource`。

同一种输入在不同前序状态、技能槽替换状态和连携窗口下可能解析为不同技能。Endaxis 不再采用“时间轴
只保存第一形态或稳定槽位，模拟时悄悄换成另一技能”的隐式方案。所有可由上述操作解析出的技能形态都
必须作为技能库中的显式放置项，用户放置时同时声明：

1. **操作身份/等级来源**：`basicAttack`、`battleSkill`、`comboSkill` 或 `ultimate`；
2. **预期技能身份**：用户期望该操作在此刻实际释放的 `skillKey/sourceSkillId`；
3. **模板或自定义定义**：只属于该预期技能形态，不借用第一形态的定义。

编译和模拟准备阶段必须按该帧之前的状态，使用已取证的原生输入解析规则计算：

- 此操作当前是否允许执行；
- 原生当前会把该操作解析成哪个技能；
- 解析结果是否与技能块声明的预期技能完全一致。

失败或不一致属于技能块合法性诊断：保留技能块，在右上角显示感叹号，并把具体原因写入感叹号的
`title`。不得回退到第一形态、静默重绑或把运行时替换后的身份反写进项目。为继续计算构筑结果，现阶段
仍可按技能块显式声明的技能运行，但必须同时保留诊断，不能把强制运行冒充原生输入成功。

当前已实现的强制排轴口径为：槽位不一致、费用不足和冷却未就绪都只产生事实诊断，显式技能仍继续
执行。费用实际结算时，共享技力可以扣到负数，终结技能量使用资源账本既有下限钳制，最低为 0。
`replacementSkills` / `routedReplacementSkills` 只表达运行时换槽关系，不能推出技能库展示语义。生成清单
必须逐个替换技能声明 `replacementPlacements`：`sequence` 表示与前段组成有序链，`standard` 表示普通
独立操作，`enhanced` 表示强化形态，`internal` 表示不接受玩家输入且不进入技能库。具名 variant 和单独
技能组也必须通过 `libraryPresentation` 明确声明是否强化；UI 不按结构、角色名、技能 key 或命名后缀
猜测。强化卡片大字显示“强化 + 操作类型”，左上小字保留具体技能标题；普通独立形态仍显示自身操作
类型。弭弗战技一/二/三段属于可按块宽连续放置的 `sequence`；洛茜后续连携虽然有前置依赖，但必须
由前段开启精准衔接窗口后在正确现实时刻手动放置，因此仍是独立的 `standard` 卡片。庄方宜强化战技/
连携属于 `enhanced`，诀的奥义、梨诺结束战技和卡缪跨组路由属于 `standard`。庄方宜 `ultimateEnd` 是强化 Buff 结束时改为
`AttachSkill` 后内部强制施放的退场清理技能，属于 `internal`，不是“强化终结技”。基础块不再连带编译
或预览其他形态的程序与 hit。该规则只定义 Endaxis 如何计算一条用户已声明的轴，并不声称原生游戏会
接受这次操作。

原生规则尚未完成取证。下一步应先从原生 HUD 中的技能替换提示、连携窗口、按键可用性和图标变化入手，
再沿 UI 查询调用追到输入处理、技能槽、替换优先级、连携候选和释放准入。只有确认后的状态与优先级
才能进入解析器；不能仅凭技能组数组、`ChangeSkillSlotAction` 或当前生成结果猜测输入语义。

该模型落地前，不对弭弗、伊冯或莱万汀做角色专用 Inspector 修补。
