# Endaxis Next 开发与维护规范

## 1. 设计取舍顺序

发生冲突时，严格按照以下顺序决策：

1. 尽可能精准、完整地模拟已经确认的游戏行为；
2. 保持代码清晰，易于理解、验证、扩展和维护；
3. 在不牺牲前两项的前提下提高性能。

不能为了统一抽象而抹平真实执行差异，也不能为了未经测量的性能收益引入复杂缓存、隐式生命周期或难以审计的状态同步。旧版 Endaxis 只能作为交互兼容参考和待核验样本，不能作为 Next 战斗规则的最终证据。

## 2. 开始修改前先判断职责

| 需求                       | 首选位置          |
| -------------------------- | ----------------- |
| 用户可保存的输入           | `core/project`    |
| 游戏目录结构               | `core/game-data`  |
| 具体版本数据               | `data` 或生成器   |
| 等级展开、build 和面板解析 | `core/compiler`   |
| 单场战斗状态与行为         | `core/combat`     |
| 活动/关卡规则适配          | `core/mechanics`  |
| 曲线、诊断和分析           | `core/projection` |
| 用例组合、历史和环境选择   | `application`     |
| 展示、交互、i18n 和主题    | `ui`              |

如果一个功能同时修改三个以上层，先检查是否把派生数据、翻译文本或运行时状态放错了位置。

## 3. 代码形式

- 非测试文件顶部说明本文件在整体系统中的作用和调用注意事项；干员纯配置文件除外。
- 重要类型说明所有权、生命周期和是否持久化，而不只复述字段名。
- 使用可辨识联合和有限枚举表达领域值；稳定身份键才使用开放 string。
- CombatStep 使用有序 sequence，不新增平行的 before/after 效果槽。
- 公共 helper 只减少真实重复，不能隐藏干员专属机制。
- 中文注释说明设计原因和边界；名称保持清晰英文领域语义。

## 4. 错误处理

- 未知游戏数据、步骤、条件和目录引用默认失败。
- 编译错误携带项目或目录路径。
- 能力子集在运行前预检，避免产生部分副作用。
- UI 展示的失败使用稳定 code 进入 i18n，core 不生成最终用户文案。
- 不使用空回调、单位倍率或静默跳过伪装功能支持。

## 5. 状态和所有权

- 项目只由应用命令修改。
- 目录只读并带 revision。
- 编译产物不可变。
- 每次模拟创建新运行时。
- 同一实体同一种状态只有一个所有者。
- Receipt 只追加；projection 无副作用。
- UI 选择、焦点和弹窗不进入项目。

## 6. i18n 和主题

- core、compiler、runtime 和项目存档中不得调用 i18n。
- 游戏文本按稳定身份在渲染层查询。
- UI 文本集中在 i18n 资源，不创建零散翻译常量。
- 组件使用语义主题 token；主题、语言不影响模拟缓存。

## 7. 测试策略

按风险选择测试层次：

- 纯模型/公式：单元测试和边界值。
- 编译器：输入定义到精确产物快照。
- 运行时：帧顺序、状态变化和 receipt。
- 应用入口：真实场景从编译到结果。
- UI 命令/ViewModel：不依赖 DOM 的行为测试。
- 复杂交互和视觉：浏览器截图与交互回归。
- 生成器：未知输入失败、代表样本和全量审计。

测试应断言行为和契约，不硬性要求内部代码文本保持不变。

## 8. 性能

- 先测量，再优化。
- 优先使用 Map/索引、不可变编译产物和稀疏投影。
- 缓存键必须覆盖项目 revision、游戏目录 revision、编译器 revision 和运行环境事实。
- 不缓存可变运行时对象，不把 UI 主题和语言加入战斗缓存。
- Worker 只作为阶段执行适配，不改变核心 API。

## 9. 新增能力检查清单

1. 是否有解包、反编译或实机依据？
2. 它属于项目、目录、编译、运行时还是投影？
3. 是否需要稳定身份或 schema 版本变化？
4. 是否需要新的 step/condition/event？
5. 编译器和执行器是否同时支持？
6. 能力预检是否需要开放或继续拒绝？
7. Receipt 是否足够支持 UI，不够时应补什么事实？
8. 是否影响旧项目迁移或 game-data revision？
9. 是否更新了测试、专题证据和本文件库状态？

## 10. 完成定义

一个 Next 功能只有在以下条件全部满足后才算完成：

1. 输入、输出、所有权和依赖边界明确；
2. 核心行为有解包、反编译、运行时探针或实机验证支撑；
3. 未知和暂不支持的情况会被明确暴露，不会静默降级；
4. 稳定输入能够重建全部派生状态；
5. 定义、编译、执行和需要的投影已经形成实际调用链；
6. 相关单元测试和端到端数据流测试通过；
7. UI 只消费稳定项目或投影，并保留 i18n 与主题边界；
8. 代码没有为单个干员、装备或活动破坏通用层级。

仅仅存在类型、文件或测试桩不算“已接入”。尚未进入正式环境装配的模块，应在状态文档中标为“部分接入”或“设计中”。
