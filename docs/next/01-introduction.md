# 为什么要建设 Endaxis Next

## 1. Next 是什么

Endaxis Next 是与旧版并行的新实现。它仍然服务于同一个目标：让用户配置干员、武器、装备和敌人，在时间轴上安排动作，并得到资源、状态、伤害和合法性结果。但它不继续沿用旧版的项目 Store、动作对象、模拟器和 UI 状态之间的耦合结构。

新版的核心思路是：

```text
用户项目 + 版本化游戏目录
        ↓
解析与编译
        ↓
不可变战斗程序
        ↓
单场战斗运行时
        ↓
只追加事实回执
        ↓
按需投影为曲线、诊断、日志和 UI
```

这条链路中的每个对象只有一种明确身份。存档不冒充运行时快照，目录定义不携带 UI 状态，模拟器不直接写 Vue Store，UI 也不重新推导战斗规则。

## 2. 为什么不能只在旧版继续修补

旧版已经完成了大量可用功能，其交互和视觉仍是 Next 的兼容目标。但长期演进中暴露出几类结构问题：

1. **稳定输入与派生结果混存**：动作名称、命中、面板和模拟结果可能被保存，加载后又需要判断哪些应沿用、哪些应重算。
2. **领域身份不够稳定**：部分动作依赖翻译后的名称或临时 ID 恢复身份，导致 i18n、撤销和存档兼容相互影响。
3. **规则分散**：干员特殊逻辑、通用模拟规则、投影告警和 UI 判断容易重复实现。
4. **顺序语义不自然**：一个命中内的 Buff、伤害和资源行为使用专用前后字段表达，难以覆盖游戏真实的有序动作序列。
5. **运行时与界面耦合**：全局 Store、Watcher 和组件生命周期参与模拟与历史管理，使局部改动产生较大影响面。
6. **证据边界不清**：旧实现中部分规则来自人工经验，难以区分已反编译验证、近似实现和纯展示逻辑。

在这些边界上继续局部修补，会让每项新机制同时修改更多模块。Next 选择平行建设，既保留旧版可用体验，也允许从项目格式和战斗核心重新建立清晰契约。

## 3. 新版的主要优势

### 3.1 可验证

战斗行为必须来自解包数据、反编译结果、运行时探针或可复现实机验证。未闭环能力会在编译、预检或执行边界明确失败，不能用默认值冒充支持。

### 3.2 可维护

项目、目录、编译器、运行时、投影和 UI 单向依赖。修改伤害公式不需要改项目存档；修改时间轴外观不需要触碰战斗状态。

### 3.3 可扩展

干员、武器和装备使用声明式定义；活动机制通过受控 Contribution 接入；新投影从回执读取事实，不必侵入模拟循环。

### 3.4 可兼容

旧版视觉和交互是 UI 迁移基准。Next 不是为了重新设计产品，而是用新的底层实现尽量保持用户熟悉的工作流。旧项目通过专用迁移边界进入 V2 文档，不让兼容代码污染核心模型。

### 3.5 可优化

解析、编译、模拟和投影天然形成缓存边界。性能优化可以基于 revision 和真实热点实施，而不是依赖全局可变对象或隐式 Watcher。

## 4. 设计优先级

发生取舍时，顺序固定为：

1. 尽可能准确、完整地模拟已确认的游戏行为。
2. 保持代码和数据清晰、可理解、可测试、可维护。
3. 在不牺牲前两项的前提下提高性能。

这意味着 Next 不追求和反编译代码逐字同名，也不追求最少文件或最强抽象。它追求行为有依据、边界能解释、扩展不需要推翻已有结构。

## 5. 当前边界

Next 目前处于并行开发阶段：项目 V2、目录接口、部分构筑和面板解析、时间轴编辑基础、战斗核心、资源投影及标准生命伤害场景已有实现；全干员数据、完整 Buff/元素反应/失衡装配、完整模拟结果和旧版全部 UI 能力仍在迁移。

因此：

- 旧版仍是生产入口；
- Next 页面用于持续贯通和验证；
- 旧版模拟结果只能作为待核验参考，不是新规则的最终依据；
- Next 的“严格失败”是设计能力，不是临时缺陷掩盖。
